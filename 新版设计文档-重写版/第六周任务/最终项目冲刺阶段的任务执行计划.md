# 最终项目冲刺阶段的任务执行计划

状态：负责人已确认执行顺序；待冲刺阶段正式开始

适用范围：比赛 Demo 最终功能闭合、证据整理、部署复现和提交材料收口

本计划不扩大生产化范围，不新增登录、多租户、公网部署、高并发、云数据库或生产级运维能力。

## 一、冲刺目标

在比赛提交前形成一个可以运行、可以演示、可以复核的最终候选版本，完成以下闭环：

```text
补齐核心功能和数据
→ 形成差异化案例
→ 设计并执行关键测试
→ 完成网页优化和部署复现
→ 制作真实演示材料
→ 统一版本和证据
→ 安全审计、打包、复现、提交
```

最终候选版本必须满足：

- 核心学习流程能够从画像、诊断、路径、教学、活动一直走到总结；
- 多智能体协同过程和中间决策有安全可展示的证据；
- 至少两组差异化学习者拥有完整的输入、决策和最终资源案例；
- 客观题、代码题、重试、失败降级和恢复行为与实际代码一致；
- README、PPT、视频、测试报告和源码绑定同一版本；
- 未执行的测试明确登记为 `NOT_RUN`，不伪造通过数字；
- 最终提交包可在干净环境中按 README 启动和复现。

## 二、执行原则

### 1. 比赛 Demo 优先

优先保证比赛要求的确定性闭环、现场演示稳定性和可复算证据。生产化能力不属于本轮冲刺范围。

### 2. 先功能和证据，后样式和材料

PPT、视频和最终报告可以先写草稿，但定稿必须以最终运行结果、截图、日志和哈希为准。

### 3. 真实结果和未运行结果分开

以下状态必须严格区分：

- `PASS`：有命令、输入、输出和可复算证据；
- `FAIL`：实际运行失败，保留失败记录；
- `BLOCKED`：有明确阻塞原因；
- `NOT_RUN`：没有执行，不能推导为通过；
- `DEFERRED`：明确延期到提交后，不属于本次验收结论。

不得将预计结果、手工填写数字、录制响应或固定题回放写成真实模型或真实测试通过。

### 4. 最终候选版本单一来源

截图、视频、PPT、报告、案例、部署说明和压缩包必须来自同一个提交、同一个 Profile revision、同一个环境和同一组提示词配置。

## 三、第一阶段：负责人完成仍未闭合的功能和数据

### 3.1 本阶段真正需要补齐的内容

负责人只负责补齐尚未闭合、或由负责人最新提出并登记的问题，不重复开发已经存在的基线能力：

- 多智能体协同调度与交互过程的安全可视化，也就是每一轮 Generator、Hunter、Defender、Judge 的顺序、状态和裁决结果；
- 多智能体协同决策中间数据导出；
- 学情画像 Agent 与动态决策更新联动：画像 Agent 记录正式 Evidence、薄弱知识点和进步情况，重做题组围绕最新错误知识点生成，并兼顾当前正文知识点，尽量避免重复；
- 问题清单中负责人新发现的界面和流程问题，例如客观题首次打开时进度条不应提前前进；
- 为上述新增或修订功能补充必要的案例输入、中间决策和最终输出证据。

学情画像 Agent 与动态决策更新不得拆开验收：必须同时证明“错误进入画像 → 下一轮题目针对错误知识点 → 新结果回写画像和路径 → 最终总结反映变化”的闭环。

多智能体安全可视化同样不得只在阶段3末尾补一个静态页面。它是贯穿阶段0至阶段5的独立交付线，状态登记为：

```text
FEATURE_AGENT_SAFE_VISUALIZATION=OPEN / REQUIRED_BEFORE_STAGE5
```

必须依次完成现状复现、公开合同、界面骨架、真实运行接线、安全导出和完整案例验收。阶段5结束时，如果页面不能展示真实Agent执行顺序，或展示内容无法和服务端轨迹复算，本轮功能补齐不得判定完成。

### 3.1.2 多智能体安全可视化贯穿阶段0—5的独立计划

#### 目标与用户可见结果

用户在等待AI生成和审核题组时，应当持续看到系统正在进行哪一步、已经等待多久、每个Agent得出了什么安全结论，以及最终展示的是实时AI审核题、录制响应还是固定保障题。页面不能暴露模型私有推理，也不能用预先写死的动画冒充实际Agent运行。

建议页面使用一条安静、可扫描的纵向执行时间线，并与当前题组生成区放在同一工作流中：

```text
Generator  已完成  7.8秒  已生成5道候选题
Hunter     已完成  5.1秒  发现1项答案歧义
Defender   已完成  3.6秒  接受质疑并提交修订
Judge      已完成  4.4秒  修订后通过
结果来源    实时AI审核题组
```

无争议时，Defender明确显示“未触发：Hunter未发现实质争议”；模型或审核失败时，时间线显示失败阶段和“已切换固定保障题”，不能把降级结果标记为实时生成成功。

#### `VIZ-0`：现状复现与威胁建模

1. 用正常无争议、Hunter提出争议、模型失败降级三条输入复现当前Generator/Hunter/Defender/Judge链。
2. 核对现有私有checkpoint、`adaptive-trace`、录制响应和公共API，确认哪些字段来自真实执行，哪些只是调试数据。
3. 列出所有可能包含系统提示词、原始模型响应、正确答案、hidden tests、Rubric、reference solution、API Key、绝对路径和个人信息的字段。
4. 保存现有页面截图、请求响应和trace哈希，明确当前缺少的是服务端投影、实时更新、页面展示还是导出能力。
5. 形成最小受影响文件清单，不直接把整个私有trace对象序列化到浏览器。

#### `VIZ-1`：安全合同与界面骨架

建立专用公共DTO，例如`SafeAgentRunView`和`SafeAgentStageView`。字段采用白名单，至少包括：

```text
runId
sessionId
activityId
profileRevision
role
stageOrder
status
startedAt
finishedAt
durationMs
issueCategories
publicSummary
decision
sourceClaimIds
artifactSha256
resultOrigin
```

其中`status`至少区分`queued`、`running`、`succeeded`、`revised`、`rejected`、`failed`、`fallback`和`skipped`。`resultOrigin`至少区分`live_model`、`recorded`和`fixed_fallback`。

本阶段完成React时间线组件骨架和fixture测试：

- 用图标、文字和状态色共同表达，不能只靠颜色；
- 运行中显示当前阶段和累计秒数；
- 默认展示角色、状态、耗时和一句话摘要，详细安全信息可展开；
- 支持键盘焦点、屏幕阅读器状态和`prefers-reduced-motion`；
- 手机端单列展示，长摘要换行，哈希和ID允许复制但不撑破容器；
- 空状态明确写“本活动尚未启动Agent协同”，不显示虚构阶段。

#### `VIZ-2`：版本、会话与确定性事实绑定

1. 每次Agent运行绑定当前`sessionId`、`activityId`、Profile revision、题组目标、Evidence版本和路径版本。
2. 刷新、重启和从服务端恢复后，时间线读取同一服务端安全投影，不在前端重新拼接历史。
3. 同一会话并发或重复请求按`runId`隔离；旧请求晚返回时不得覆盖当前运行。
4. 页面明确区分“确定性程序已计算的诊断/路径事实”和“Agent对事实的解释”，不得把PathEngine步骤伪装成Agent协同。
5. 版本冲突、过期run和恢复失败均返回结构化状态，不静默展示另一会话的轨迹。

#### `VIZ-3`：真实运行接线与安全导出

1. 服务端在每个真实Agent阶段开始和结束时写入私有执行记录，并立即生成白名单安全投影。
2. Web通过现有服务端接口轮询或消费项目已有更新机制，展示真实状态；不为了可视化新增外部依赖或第二套状态源。
3. Hunter报告只公开问题类别、严重度和摘要；Defender只公开是否触发、回应类型和摘要；Judge只公开接受、修订或拒绝及理由摘要。
4. 时间线最终显示题组来源、题组哈希、总耗时和fallback原因，并与页面实际展示题组一致。
5. 提供“导出协同记录”命令，导出与公共DTO同级的安全JSON；导出由服务端生成，不能从DOM反向抓取，也不能包含私有checkpoint。
6. Agent失败时保留已完成阶段，失败阶段显示原因码；切换fallback后新增明确的降级事件，不篡改前序失败为成功。

#### `VIZ-4`：安全与边界验证

至少覆盖以下负例：

- 原始模型响应中出现正确答案、提示词或伪造字段时，公共投影仍只保留白名单字段；
- Hunter或Judge摘要过长、包含控制字符或类似HTML文本时，页面按纯文本安全展示；
- hidden tests、reference solution、Rubric、私有CSV期望输出和API Key不出现在DTO、DOM、网络、Worker、日志、source map、bundle和导出JSON；
- 两个会话同时生成题组时，时间线不交叉；
- Defender未触发、模型超时、Judge拒绝、固定保障、刷新恢复和版本冲突均有稳定状态；
- 公开耗时来自服务端时间戳，前端读秒只用于运行中反馈，不回写或伪造正式耗时。

#### `VIZ-5`：完整案例与提交证据

每组差异化案例必须同时保存：

- 脱敏学习者输入和输入哈希；
- `runId`、Session、Profile、Evidence和路径版本；
- 页面时间线截图；
- 公共安全轨迹JSON及SHA-256；
- Defender是否触发及原因；
- Judge裁决、最终题组来源和题组哈希；
- 刷新或服务端恢复后的同一轨迹；
- DOM、网络、日志和导出泄漏扫描结论。

案例A至少展示正常审核通过；案例B至少展示Hunter争议与Defender/Judge处理；另补一条模型失败进入固定保障题的降级证据。PPT和视频只能使用这些实际运行轨迹，不得用fixture时间线或静态Mock冒充真实协同。

#### 独立完成标准

```text
FEATURE_AGENT_SAFE_VISUALIZATION=VERIFIED
```

只有同时满足以下条件才能填写上述状态：

1. 页面阶段顺序与服务端真实编排一致；
2. 正常、争议、Defender未触发、失败和fallback均能正确表达；
3. 运行中状态和秒数持续更新，完成后显示服务端正式耗时；
4. 页面和导出使用同一安全DTO事实；
5. 刷新、重启、恢复、并发和版本冲突不串轨迹；
6. 安全扫描确认零私有答案、隐藏评测、提示词、密钥和个人信息泄漏；
7. 至少两组完整案例和一条降级案例具有截图、JSON、日志和哈希证据。

#### 阶段0：现状复现和合同核对

这一阶段不急于写代码，先把当前事实固定下来：

1. 在新的临时 Demo 数据目录中复现客观题首屏进度、不同诊断回答的路径/时长、当前代码活动样例数量和体量。
2. 对照问题清单第20至22项、`DiagnosticRuntime`、`KnowledgeState`、`PathEngine`、活动合同和现有 Agent 编排代码，列出最小受影响文件。
3. 保存每个复现输入、当前输出、Session 版本、Profile revision、seal和截图哈希。
4. 明确哪些是旧Session、录制响应或固定fixture造成的现象，哪些是当前正式组合根真实行为。
5. 同步执行`VIZ-0`，复现现有Agent轨迹、页面空缺和潜在泄漏字段，不能把“服务端已有trace”误写成“安全可视化已经完成”。

阶段0没有复现证据时，不得直接声称“诊断Agent缺失”或开始改路径规则。

#### 阶段1：先修复客观题进度语义（`ISSUE_20`）

进度条是独立的界面合同，可以先完成，避免和画像、动态题逻辑同时变更：

1. 将已作答数量定义为答案草稿中具有有效选择的唯一题目数量，不能使用`questionIndex + 1`。
2. 首次打开第1题显示`0/4`；选择答案后显示`1/4`；进入未作答的第2题仍显示`1/4`。
3. 返回修改、刷新和服务端恢复时从同一份答案草稿重算，不在前端事件处理中累加计数。
4. 分离“当前位置”“已形成答案草稿”“已保存”和“已提交”四种状态，进度条只表达第二种状态。
5. 增加组件测试和浏览器测试，核对真实进度条宽度或可访问值，并覆盖重复点击和恢复。
6. 并行完成`VIZ-1`的公共安全DTO和时间线组件骨架；本阶段只用fixture验证显示合同，不宣称已接通真实Agent运行。

本阶段不改题目生成、判分、Evidence或路径合同。

#### 阶段2：修复诊断到路径的确定性事实链（`ISSUE_21`前置部分）

学情画像 Agent 不能用来掩盖诊断输入没有生效的问题，先把事实底座打通：

1. 核对诊断题答案到知识点的映射、正确性、权重和 Evidence 写入；为每个诊断结果保存可追溯的题目 ID、答案、知识点 ID和证据版本。
2. 确认路径确认时读取当前诊断草稿、目标、讲解偏好、Profile revision和最新Evidence，不复用旧Session或固定路径缓存。
3. 让`PathEngine`继续作为路径唯一权威；`mastery/confidence/KnowledgeState`仍由确定性程序计算，Agent不得改写。
4. 核对`skipEligible`、先修关系、目标节点和安全跳过条件，解释为什么某些`1.00 ready`节点仍需学习；只有合同允许跳过时才减少路径。
5. 预计时长由最终路径节点的`estimatedMinutes`确定性求和，页面展示计算依据和路径版本。
6. 用至少两组明显不同的诊断输入做矩阵验收：输入差异、Evidence差异、KnowledgeState差异、路径差异和时长差异逐列记录；如果规则导致路径相同，必须记录相同的确定性原因。
7. 同步完成`VIZ-2`，让后续Agent轨迹绑定正确的Session、Profile、Evidence和路径版本，并在公共展示中区分程序事实与Agent解释。

阶段2只解决“诊断是否真正驱动事实”，不把模型文字当成路径决定依据。

#### 阶段3：联动实现学情画像 Agent、动态决策和Agent轨迹

阶段3是一个整体功能包，不能只完成画像摘要或只完成下一轮题目：

1. **建立学习事件入口**：所有正式诊断、客观题提交、代码判分、最终实操、重试、放弃和带缺口继续都从服务端正式提交产生事件，至少绑定`sessionId`、`evidenceVersion`、知识点 ID、结果、Attempt ID和来源。
2. **建立画像 Agent 安全输入**：只向画像 Agent 传递脱敏的学习事件、KnowledgeState摘要、路径摘要、变化原因和Evidence ID；不传hidden tests、私有答案、Rubric或参考实现。
3. **建立画像 Agent 安全输出**：输出薄弱知识点、已掌握知识点、进步点、未完成点、依据引用和总结文案；输出只能作为解释和展示投影，不能直接写入mastery、路径或正式判分。
4. **接通动态决策**：客观题失败后先由确定性程序识别错误知识点并更新Evidence/KnowledgeState，再把错误知识点、当前RichLesson、已用题目 ID和重试次数传给题组生成器。
5. **接通生成与审核链**：动态题必须经过`Generator → Hunter → Defender（有争议时）→ Judge`；接受结果绑定当前Session、章节、目标知识点、题组哈希和`generationRunId`，失败、超时、审核拒绝才进入固定题保障。
6. **导出协同中间数据**：沿用现有私有checkpoint和`adaptive-trace`，增加安全投影，只展示角色、阶段顺序、状态、耗时、问题摘要、裁决结果、来源 ID和哈希，不展示私有答案。
   - 本项必须落实`VIZ-3`的实时页面时间线和服务端安全JSON导出，不能只在日志中保存trace；
   - 页面必须区分`live_model`、`recorded`和`fixed_fallback`，并正确展示Defender“已触发”或“未触发”；
   - 导出与页面使用同一公共DTO，禁止前端读取或清洗私有checkpoint。
7. **更新最终总结**：总结页先读取确定性事实快照，再显示画像 Agent 的可选解释；必须同时呈现初始诊断、学习前后状态、错误知识点、补救题组、通过/未掌握/跳过、Evidence变化、最终路径和后续建议。
8. **统一降级**：画像 Agent或动态题生成失败时，确定性状态和固定题保障继续可用；页面明确标记解释降级或固定题来源，不能把录制响应写成实时成功。

阶段3只有在下面四段都能连起来时才算通过：

```text

→ 画像 Agent记录薄弱点
→ 动态题组绑定错误知识点并完成审核
→ 新结果回写画像、路径和最终总结
```

- Defender是条件节点。没有争议时必须显示“未触发”及确定性原因，不能把未触发节点伪装成成功执行。
- 任何失败都保留前序真实事件；切换固定题保障时增加独立fallback事件，不得把失败链改写成实时AI成功。

### 15.2 产品视觉方向

视觉主题：`数据清洗实验室生产线`。

页面的唯一强识别元素是一条真实工序轨道。流水线以“教学依据进入生产线，经过画像、生成、检查、找错、答辩、裁决后发布”为结构，不增加与任务无关的插画、渐变球、装饰卡片或营销文案。

建议视觉Token：

| 角色 | 颜色或字体 | 用途 |
|---|---|---|
| 页面底色 | `#F3F6F4` | 安静的实验室灰绿背景 |
| 工作面 | `#FFFFFF` | 当前工位和详情背景 |
| 主文字 | `#17231F` | 标题、正文和关键数据 |
| 运行/通过 | `#087F5B` | 当前节点、通过状态和主操作 |
| 修订/争议 | `#B7791F` | 修复、争议、等待人工理解的状态 |

- 图标使用项目现有或Lucide中可识别的生成、搜索、盾牌、辩护、裁决、发布图标；状态不能只靠颜色表达。
- 当前连接段允许使用轻微的定向短线移动，表示数据正流向下一工位；已完成连接段为稳定实线，未开始连接段为低对比线。
- 状态切换动画控制在160至220毫秒；用户开启`prefers-reduced-motion`时连接线和图标完全静止。
- 标题、长摘要、ID和哈希在桌面、平板和手机端均不得重叠或撑破容器。

### 15.3 三级信息密度

为同时满足美观和信息具体，页面采用三级信息密度：

1. **流水线总览**：快速显示八个节点的角色、状态、完成顺序和短耗时。

### 15.4 八个真实工位及公开信息

#### 工位1：教学依据准备

默认信息：

- 当前章节和知识点中文名称；
- 选中的正文版本`guided / concise / practice`及中文标签；
- 正文模块数量和公开来源数量；
- Profile revision、路径版本和安全来源绑定状态；
- 首次学习或重做轮次。

运行摘要示例：

```text
正在读取“读取CSV数据”的逐步讲解版正文
已绑定6个正文模块和3个公开来源
```

不得显示完整系统提示词、宿主路径或私有Profile文件位置。

#### 工位2：学情画像分析

默认信息：

- 画像来源：`学情画像Agent`或`确定性事实画像`；
- 上一轮作答数量、错题数量和安全薄弱知识标签；
- 当前Evidence版本和引用数量；
- 画像Agent公开补救建议；
- Agent不可用时的降级原因码和确定性摘要。

运行摘要示例：

```text
画像Agent正在分析本轮2道错题和当前正式Evidence
重点：带引号字段、分隔符处理
```

不得显示正确答案、完整Evidence正文、个人敏感信息或模型原始响应。

#### 工位3：Generator生成题组

默认信息：

- 实际模型公开标识，不显示API Key、URL凭据或请求头；
- 目标题量、当前生成轮次、Provider重试次数和候选修复次数；
- 正文版本、错题数量、薄弱知识数量、排除旧ID数量和排除旧题干数量；
- 当前任务：首次生成、Provider重试或定向修复；
- 候选返回后只显示题量和公开结构状态，不显示正确答案。

运行摘要示例：

```text
Generator · 运行中 · 09.4秒
任务：生成4至6道全新单选题
输入：guided正文、2道错题、2项薄弱知识
约束：不得复用6个旧ID和6道旧题面
当前进展：首次候选已返回，正在检查
```

修复事件示例：

```text
首次候选复用了旧题ID
正在执行第1次定向修复，保留薄弱知识但更换ID和题面
```

#### 工位4：确定性安全检查

默认信息：

- JSON Schema和字段白名单；
- 题量、ID唯一性、旧ID排除和旧题干逐字重复检查；
- `correctAnswer`是否属于选项的私有检查，只公开“通过/失败”，不公开答案；
- 来源白名单和sourceAnchor闭合；
- 敏感信息、权限字段和私有资产泄漏检查；
- 失败类别及是否回到Generator修复。

摘要示例：

```text
结构检查 7/7通过
来源绑定 5/5题通过
发现1道题复用旧ID，已退回Generator修复
```

#### 工位5：Hunter反向找错

默认信息：

- 已审核题数/候选总题数；
- 发现问题数量、严重度分布和安全问题类别；
- 是否存在争议以及是否需要Defender；
- 对正文依据、答案唯一性、解析一致性、题面清晰度和错题覆盖的检查结论；
- 一句话公开摘要，不复述答案或私有解析。

完成摘要示例：

```text
Hunter · 已完成 · 05.1秒
审核进度：5/5题
发现问题：1项
问题类别：答案歧义
严重程度：中
需要答辩：是
```

#### 工位6：Defender答辩

触发时显示：

- 触发原因和争议数量；
- 已回应争议数量；
- 接受质疑、反驳质疑和残余风险数量；
- 一句话公开答辩结论。

未触发时必须显示：

```text
Defender · 未触发
原因：Hunter未发现需要交叉答辩的实质争议
```

不得显示完整内部辩护文本、正确答案或私有推理过程。

#### 工位7：Judge最终裁决

默认信息：

- `accepted / revise / rejected`中文状态；
- Hunter问题数量、已闭合争议和阻塞问题数量；
- 是否经过Judge结构修复；
- 最终公开裁决摘要；
- 候选题组安全哈希短值和来源绑定结论。

摘要示例：

```text
Judge · 修订后通过 · 04.4秒
Hunter提出的1项争议已经闭合
题组具备唯一答案依据，可以发布
```

Judge只裁决候选资源能否发布，不得在页面暗示其直接修改学习者得分、KnowledgeState或路径。

#### 工位8：发布题组或固定保障

默认信息：

- 最终来源：实时AI、AI录制响应或固定题保障；
- 最终题量、总耗时、Attempt ID短值和题组哈希短值；
- 是否为重做题组及覆盖的薄弱知识数量；
- fallback时的安全失败阶段、原因码和保障来源；
- 页面题组来源必须与服务端记录、导出JSON和实际展示内容一致。

成功摘要示例：

```text
已发布5道实时AI审核题
覆盖2项上一轮薄弱知识
总耗时：24.8秒
```

失败摘要示例：

```text
Generator两次候选均未通过结构校验
已切换为本章节固定保障题组
```

```text
  profileRevision
  pathVersion
  evidenceVersion
  status
  currentStage
  startedAt
  finishedAt

  role
  label
  status

  finishedAt

  publicSummary
  metrics[]
  issueCategories[]

```

运行状态至少包含：

```text

succeeded
revised
rejected
failed

```

事件规则：

- `eventId`和`sequence`由服务端生成，前端不得修改。
- 每个阶段开始先写`running`事件，结束后追加正式结果事件；不原地篡改历史事件。
- Provider重试、Generator修复、Judge修复和fallback必须产生独立事件。
- `durationMs`完成后以服务端时间戳为准；前端读秒只在运行期间展示，不回写服务端。
- 完成快照必须可由按sequence排序的安全事件确定性重建。
- 公共DTO只能从私有事实经过白名单投影生成，前端不能读取或清洗私有checkpoint。

严禁进入公共DTO、SSE、DOM、网络日志、导出JSON或前端bundle：

- 系统提示词、完整模型输入和原始模型响应；
- 模型私有推理或思维链；
- 候选正确答案、私有解析和未公开答案键；
- hidden tests、Rubric、reference solution、gold和私有CSV期望输出；
- API Key、Token、Authorization、宿主绝对路径和未脱敏个人信息；
- 未经白名单处理的Evidence内容和私有checkpoint。

### 15.6 实时传输与恢复方案

采用原生SSE（Server-Sent Events），不引入WebSocket或新的外部依赖。当前需求是服务端单向推送阶段状态，SSE足以满足，且支持浏览器自动重连和`Last-Event-ID`恢复。

建议接口：

```text
POST /api/activities/{activityId}/generation-runs
GET  /api/agent-runs/{runId}
GET  /api/agent-runs/{runId}/events
GET  /api/agent-runs/{runId}/export
```

接口语义：

1. `POST generation-runs`只负责以幂等请求创建或复用运行，立即返回`202`、`runId`、当前状态和事件地址，不等待整条多Agent链结束。
2. `GET agent-runs/{runId}`返回当前安全快照，用于首次加载、刷新和SSE失败降级。
3. `GET events`持续推送安全事件，支持`Last-Event-ID`补发；服务端每10秒发送不含业务数据的心跳保持连接。
4. `GET export`由服务端生成与页面同级的安全JSON，不能由前端从DOM反向拼装。
5. 运行完成事件只通知“活动内容已就绪”；前端再通过正式活动接口取得公共题组，不在SSE中携带正确答案或私有Attempt。

实时性能目标：

- 点击后200毫秒目标时间内显示“已进入队列”；本机极端负载下不得超过1秒仍无任何反馈。
- 服务端阶段开始或结束后，页面目标1秒内更新。
- 运行中累计秒数每秒更新；网络心跳不冒充业务进展。
- SSE断开后自动重连；重连期间显示“正在恢复实时状态”，不显示网页卡死。
- SSE持续失败时退回1秒一次的安全快照轮询；恢复后停止轮询，禁止双状态源竞争。
- 刷新、服务重启、旧请求晚返回和两个并发Session均不得串run或覆盖当前结果。

### 15.7 前端解耦要求

为后续替换前端，流水线功能必须分为三层：

```text
服务端Agent编排与事件事实
→ 公共SafeAgentRunView / SSE合同
→ 前端AgentRunClient
→ 纯展示AgentPipeline组件
```

要求：

- React页面不得直接导入Application、Repository、Agent服务或私有trace类型。
- `AgentRunClient`集中负责启动、快照、SSE重连、序号去重和导出；页面不直接拼接SSE协议。
- `AgentPipeline`只接收安全ViewModel和用户展开/收起事件，不负责调用Agent、计算裁决或修复数据。
- Session、Profile、Path和Evidence版本绑定由服务端合同负责，前端只展示。
- 新前端只要实现同一HTTP/SSE合同即可复用后端，不重新实现Generator、Hunter、Defender、Judge、路径或判分。

### 15.8 响应式、交互与无障碍

桌面端：

- 顶部使用单行工序轨道；当前工作台为左右两列，左侧显示正在做什么和最新事件，右侧显示本轮安全输入和指标。
- 八个节点具有稳定宽度，短标签不换行；长摘要只在下方工作台出现。

平板端：

- 工序轨道允许分为两行，每行四个节点，但sequence和连接方向必须清楚。
- 当前工作台改为单列，指标使用二至三列自适应网格。

手机端：

- 改为纵向流水线；当前节点在原位展开，完成节点默认紧凑显示。
- 不使用横向滚动承载主要状态；哈希和ID允许独立横向滚动或复制。
- 按钮文字、计时和长中文摘要不能互相遮挡。

无障碍要求：

- 当前状态区使用`aria-live=polite`，只播报阶段变化，不每秒播报读秒。
- 每个节点以图标、状态文字和颜色共同表达。
- 展开按钮可键盘操作，焦点顺序与sequence一致。
- 屏幕阅读器能够读出角色、状态、正式耗时和公开摘要。
- `prefers-reduced-motion`下关闭连接线和图标动画，不影响状态理解。

### 15.9 分阶段执行顺序

#### 阶段5-A：高保真视觉原型与信息架构

- 使用安全fixture制作桌面、平板和手机三套高保真流水线页面。

- 只使用模拟安全事件验证视觉，不宣称接通真实Agent。
- 由负责人先审查页面美观程度、信息密度、中文措辞和移动端布局，再进入后端改造。

预期效果：用户在3秒内能看懂当前步骤、已经完成的步骤、下一步和题组最终来源；当前工作台信息具体，但页面不显得拥挤。

阶段出口：

```text
PHASE_5A_VISUAL_PROTOTYPE=OWNER_ACCEPTED
REAL_AGENT_EVENTS=NOT_CONNECTED
```

预期效果：页面和未来新前端都只消费稳定合同；任何私有字段即使存在于模型响应，也无法进入公共View。

```text
PHASE_5B_SAFE_EVENT_CONTRACT=VERIFIED
```

预期效果：即使没有Web页面，也能从服务端安全事件按sequence复算真实流水线，不再只有一轮结束后的聚合`stageOrder`。
