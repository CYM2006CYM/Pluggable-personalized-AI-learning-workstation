## 1. 路径个性化表达与实质不足

### 1.1 已观察事实

1. 诊断画像中部分知识点显示`1.00 ready`，但学习路径仍安排这些知识点完整学习，学习者难以理解原因。
2. 当前`1.00`主要表达一次诊断作答形成的mastery数值，不等于系统已经获得足够证据允许跳过。现行跳过判断还受confidence、证据数量、证据形式和目标必修约束影响。
3. 当前目标把六个Pandas核心知识点及对应活动列为目标必做。诊断结果主要改变难度、脚手架和先修状态，没有让高基础学习者看到足够明显的路径长度或学习动作差异。
4. 页面直接展示`ready`、`locked`、`goal_required`、`prerequisite_gap`等内部状态词，无法向普通学习者解释“为什么已经会了仍需学习”。

### 1.2 负责人期望

路径必须真实体现诊断结果和学习者差异，而不是只改变标签或样式。系统既不能把“一道题答对”误判为完全掌握，也不能让高基础学习者与初学者走视觉和学习负担几乎相同的路径。

### 1.3 整改要求

1. 保留多证据、跨形式验证和confidence约束，不采用“一题答对即可永久跳过”的简单放宽方案。
2. 对证据不足但诊断表现较好的知识点，显示“快速巩固”或“快速验证”，并提供较短正文、较少脚手架或快速验证活动。
3. 对存在明确缺口的知识点，继续安排完整教学、示例、练习和重试。
4. 路径节点必须展示安全、可理解的中文安排原因，至少区分：已具备先修、目标要求、仍需补证据、存在先修缺口、需要完整学习。
5. 将内部英文状态转为中文学习者文案；内部机器值可以保留在服务端合同中，但不应直接作为主要页面说明。
6. 诊断Agent只能提供审核后的个性化解释或建议，不得自行改写KnowledgeState、Evidence、路径合法性或掌握度。路径顺序、跳过资格和状态更新仍由确定性程序计算。

### 1.4 验收标准

1. 三类学习者对同一目标产生有依据且可解释的路径或学习动作差异。
2. 高基础学习者的强项显示快速巩固或快速验证，弱项仍进入完整教学。
3. 初学者不会因为一次猜对而直接跳过关键知识点。
4. 每个节点能够用中文说明安排原因，并能追溯到安全诊断摘要、KnowledgeState和确定性规则。
5. 刷新、恢复和重试后，路径解释与服务端事实保持一致。

## 2. 缺少返回、回看和上一节导航

### 2.1 已观察事实

当前主要学习流程缺少稳定、统一的回退入口。学习者进入诊断结果、学习路径、教学正文或课后练习后，不能自然返回上一层，也不容易回看已经完成的章节。

诊断问卷内部也只有“保存并继续”等向前操作。学习者进入下一道题后，无法返回上一题查看或修改尚未最终提交的答案；“跳过并保持未验证”的题目也缺少方便的回访入口。这使逐题草稿虽然被保存，却不能由学习者正常复查和修正。

会话总结页同样缺少明确的“返回主菜单”按钮。即使页面显示“开始新会话”等后续文字，用户仍没有清楚的页面级出口；当总结中存在`fail`、`partial`、`support_needed`等未解决项目时，也没有直接返回这些项目继续处理的主操作。

### 2.2 负责人期望

学习过程应允许学习者返回上一节或上一个界面。返回属于导航，不应被解释为撤销学习记录或重新计算服务端状态。

### 2.3 整改要求

1. 在页面固定位置提供清晰的返回入口，优先使用熟悉的返回图标并配合可访问名称或提示。
2. 至少闭合以下关系：诊断结果返回会话设置、学习路径返回诊断结果、教学正文返回学习路径、练习返回教学正文。
3. 教学正文提供“上一节”和“返回学习路径”；第一节没有上一节时应明确禁用或隐藏对应操作。
4. 已完成节点允许从学习路径中重新进入回看，不能因为完成状态而变成不可访问。
5. 返回操作不得撤销Attempt、Evidence、KnowledgeState、mastery、路径状态或已完成标记。
6. 未正式提交的本地草稿在返回后应保留；刷新后的恢复范围必须与既有草稿合同一致。
7. 桌面端和移动端都必须保证按钮不遮挡正文、不溢出且可操作。
8. 诊断问卷和其他多题活动提供“上一题 / 下一题”导航；第一题的“上一题”和最后一题的“下一题”按位置正确禁用或替换为最终确认操作。
9. 在诊断最终提交前，学习者可以返回任意已访问题目，查看并修改该题草稿；再次向前后切换时使用最新草稿，不丢失其他题目的选择。
10. 对“跳过并保持未验证”的题目保留未回答状态，并允许学习者在最终提交前返回补答。页面应能区分已回答、未回答和跳过，不能把跳过显示为已经完成。
11. 题目间切换只更新诊断草稿及其版本，不得提前生成正式Attempt、Evidence、KnowledgeState或学习路径。
12. 最终提交前增加整组确认视图或等价的题号导航，使学习者能发现未回答题并直接返回；不得强迫用户连续点击多次“上一题”才能定位遗漏。
13. 诊断最终提交成功后，答案进入权威历史记录。此后允许只读回看，但不得通过返回按钮修改已提交答案；需要重新诊断时必须建立新的正式尝试或版本，不能覆盖旧证据。
14. 连续点击、快速前后切换、刷新和服务端恢复必须保持草稿幂等，不能产生重复题目、错位答案或草稿版本回退。
15. 会话总结页提供真实可点击的“返回主菜单”按钮。返回只改变当前页面位置，不删除、重置或覆盖本次Session、Attempt、Evidence、KnowledgeState、路径和总结快照。
16. 总结页存在未解决项目时，主要操作应为“继续处理未完成项”，按服务端路径事实返回首个合法补救位置；“返回主菜单”作为稳定出口同时保留。
17. 总结页可以提供“开始新会话”，但必须与“返回主菜单”清楚区分。开始新会话创建新的Session，不能复用旧Session ID或清空旧记录；返回主菜单则不创建新Session。
18. 所有总结页操作都使用按钮或语义明确的链接，具有焦点、悬停、禁用和触摸状态，不能只用标题文字或整块无提示区域冒充操作。

### 2.4 验收标准

1. 学习者可以沿主要流程逐层返回，并能再次进入原页面。
2. 返回前后服务端权威状态逐字段一致，不产生重复Attempt或重复Evidence。
3. 已完成章节可回看，但回看不会重复记分或改变路径。
4. 草稿、正式提交和已完成状态的边界清楚，刷新和会话恢复后行为一致。
5. 桌面和移动视口均完成真实点击验证。
6. 在包含多道题的诊断中完成“第1题作答 → 进入第2题 → 返回第1题 → 修改答案 → 再进入第2题”，第1题显示修改后的最新草稿，第2题状态不丢失。
7. 跳过一道题后能够从确认视图或题号导航直接返回补答；未补答时仍明确标记为未验证。
8. 最终提交前的逐题切换不产生正式Attempt或Evidence；最终提交只产生一次权威结果。
9. 最终提交后回看为只读状态，历史答案、Evidence和KnowledgeState不会因页面导航而改变。
10. 在全部活动完成和存在未解决项目两种总结状态下，均能点击“返回主菜单”；返回后可以从服务端恢复原会话，数据逐字段一致。
11. 存在未解决项目时点击“继续处理未完成项”，进入正确的补救节点而不是新会话或已经通过的活动。
12. 点击“开始新会话”只创建一个新Session，旧会话仍出现在可恢复历史中；重复点击或网络重试不创建多个新Session。

## 3. AI动态题退化为固定题，未充分体现多智能体产品能力

### 3.1 已观察事实

1. 当前截图中的课后题组来自固定题保障资产，而不是一组完整的AI个性化生成题。
2. 现行流程名义上优先使用动态候选，但当前录制响应只提供一题动态候选；完整题组要求四至六题，补充候选后仍不足最低数量，因此整组回退到固定题。
3. 当前出题上下文主要包含知识点、活动、来源锚点和简短来源摘要，没有完整消费增强后的章节正文、学习目标、代码示例、反例、常见错误以及当前正文版本。
4. 当前普通Demo使用录制响应保障演示，真实在线模型尚未运行，必须继续登记`LIVE_MODEL=LIVE_NOT_RUN`。

### 3.2 负责人裁决

动态题应恢复为主要来源，固定题只承担故障保障。方案必须吸收原多智能体设计中的Generator、Hunter、Defender、Judge和最终程序硬门禁，不允许用大量硬编码题目冒充Agent产品能力，也不允许为了突出Agent而删除确定性安全规则。

目标流程如下：

```text
RichLesson公开教学正文
→ Generator一次生成四至六道完整候选题
→ 确定性Schema、来源、隐私和泄漏检查
→ 低风险题通过程序硬校验后采用
→ 高风险题或高风险候选答案进入Hunter质疑
→ Defender逐项辩护、修正建议或承认问题
→ Judge作出accept / revise / reject裁决
→ 最终程序硬门禁
→ 发布合格题组，失败时使用固定题保障
```

### 3.3 整改要求

1. 新增安全结构化`QuizGenerationContext`，至少包含学习目标、当前正文版本、核心概念、公开代码示例、反例、常见错误、KnowledgeState安全摘要、本次错题主题、排除题目ID和允许使用的来源锚点。
2. Generator一次生成四至六道题，至少覆盖概念理解、代码应用和错误辨析，不能依赖一题候选再由固定题补成主要题组。
3. Generator同时给出候选答案键、解析和来源依据；这些均属于服务端私有产物，不得进入公共卡片、DOM、日志或前端bundle。
4. 高风险候选题、答案键或解析执行`Hunter → Defender → Judge`博弈。这里审核的是系统准备发布的候选答案，不是让Agent直接决定学习者最终得分。
5. Judge只决定候选题、答案键和解析能否发布，无权直接修改Attempt得分、Evidence、KnowledgeState、mastery、路径、先修关系或Rubric。
6. 审核通过的答案键写入服务端Attempt私有快照。学习者提交后，由确定性程序进行权威比较、记分并生成Evidence。
7. 低风险客观题保留`Generator → 程序硬校验 → 采用`的轻量路径；风险升级时才启用完整博弈，避免所有题目无差别增加延迟。
8. 只有模型错误、超时、Schema不合格、来源越界、隐私或泄漏检查失败、Judge拒绝、题量不足等情况，才允许切换固定题。
9. 六个知识点的首次练习和重试练习都应准备完整四至六题的录制响应及可复验多智能体审核轨迹，保证现场无网络或模型失败时仍能演示Agent流程。
10. 页面明确显示题目来源：`AI个性化生成`、`AI录制响应`或`固定题保障`；发生回退时显示安全、简短的中文原因。
11. 录制响应不得宣传为实时模型生成。真实模型未运行时继续登记`LIVE_MODEL=LIVE_NOT_RUN`。

### 3.4 固定程序与Agent边界

为体现Agent产品能力，应减少固定题作为正常内容来源的比例，但不得删除下列确定性程序职责：

- 权限和越权拒绝；
- Schema与稳定ID校验；
- 来源白名单和引用闭合；
- 隐私、敏感信息和私有答案泄漏检查；
- Agent调用顺序、超时、幂等、checkpoint和恢复；
- Attempt私有快照、权威判分和Evidence生成；
- KnowledgeState、路径和先修状态写入；
- fixed fallback的触发条件和可复现选择。

Agent负责生成、质疑、辩护和裁决；确定性程序负责边界、事实写入和权威判分；固定题只负责最后保障。

### 3.5 验收标准

1. 正常录制演示中，六个知识点均能取得四至六道审核通过的个性化题，且首次与重试题目有依据地不同。
2. 题目能够追溯到当前RichLesson内容和允许的sourceAnchor，不出现正文没有教授且没有来源支持的考点。
3. 至少覆盖一个高风险候选答案被Hunter质疑、Defender回应、Judge接受或拒绝的完整可复验轨迹。
4. 审核拒绝、超时、题量不足和模型失败均能确定性回退，且不伪造AI成功状态。
5. 学习者答案仍由确定性程序判分；重复提交、重试和恢复不会产生重复Evidence。
6. DOM、网络响应、日志和构建产物中不出现候选答案键、私有解析、hidden tests、Rubric或reference solution。

### 3.6 负责人现场复核：默认Demo尚未接入实时AI API

1. 当前默认`npm run demo`在组合根中使用`RecordedModelExecutionAdapter`，从`fixtures/model-responses/w6/recorded-quiz-responses.json`读取预先录制的题组。
2. 录制题组中的`modelId=deepseek-chat`只是录制响应的来源标识，不等于运行时真的调用过DeepSeek或其他在线模型。
3. 当前普通Demo运行时没有把正在学习的RichLesson正文发送给AI，也没有在用户进入章节时通过API实时生成题目。
4. 真实模型端口只在显式`demo:live`模式下读取`OPENAI_MODEL`、`OPENAI_BASE_URL`和`OPENAI_API_KEY`；当前环境未发现这三个变量，项目状态仍为`LIVE_MODEL=LIVE_NOT_RUN`。
5. 因此现有“AI动态题”证据只能证明录制响应、审核轨迹和固定fallback可复现，不能证明“根据当前正文实时调用API生成题目”已经完成。

负责人期望的正式运行方式是：

```text
用户进入章节
→ 服务端读取当前章节正式RichLesson正文
→ 调用配置的AI API
→ AI根据正文生成题组
→ Generator → Hunter → Defender → Judge审核
→ 审核通过后展示题组
→ API失败、超时、Schema不合格或审核拒绝时使用固定题保障
```

必须明确区分三种来源：

- `AI个性化生成`：本次运行真实调用API并根据当前正文生成，具有请求、模型响应和审核轨迹证据；
- `AI录制响应`：离线预先保存的响应，只用于无网络演示和回归测试；
- `固定题保障`：AI生成或审核失败后的确定性fallback。

录制响应不得宣传为实时模型运行，固定题不得作为正常动态题来源，缺少真实API请求和`LIVE_MODEL`证据时不得登记为在线模型通过。

### 3.7 本地修订结果

1. 启动器现在根据宿主配置选择模型模式：三个`OPENAI_*`变量全部存在时自动使用`live_model`；三个变量都不存在时使用`recorded_response`，保持无网络演示稳定。
2. 只配置部分模型变量时启动直接报出中文配置错误，不再静默退回录制题，避免把“配置错误”误认为“AI调用成功”。
3. 显式`--live`仍可强制走真实模型端口；API Key只从宿主环境读取，不能写入代码、Profile、会话、日志或前端。
4. 当前本机没有配置三个`OPENAI_*`变量，因此本次只证明模式选择和安全边界，仍未运行真实在线模型。

### 3.8 新增负责人裁决：多智能体协同调度与交互过程必须安全可视化

当前服务端已有checkpoint、`adaptive-trace`或录制响应，不等于用户已经能够看到多智能体协同过程。该能力必须作为`ISSUE_3_AGENT_FIRST_DYNAMIC_QUIZ`的独立子项重新打开，并与[最终项目冲刺阶段的任务执行计划](./最终项目冲刺阶段的任务执行计划.md)中的`VIZ-0`至`VIZ-5`同步实施：

```text
ISSUE_3_AGENT_SAFE_VISUALIZATION=OPEN / REQUIRED_BEFORE_STAGE5
```

负责人要求页面根据服务端真实执行记录展示：

- Generator、Hunter、Defender和Judge的实际执行顺序；
- 排队、运行、成功、修订、拒绝、失败、降级和未触发状态；
- 当前阶段、累计等待秒数和完成后的服务端正式耗时；
- Hunter发现的问题类别和安全摘要；
- Defender是否触发、回应类型和安全摘要；
- Judge接受、修订或拒绝的裁决摘要；
- 最终题组属于`live_model`、`recorded`或`fixed_fallback`；
- `runId`、Profile revision、来源ID和产物哈希等可复算标识；
- 与页面同源的安全中间数据JSON导出。

页面不得显示或通过公共接口、DOM、网络、Worker、日志、source map、bundle和导出文件泄漏：

- 系统提示词或模型私有推理过程；
- 候选答案键、私有解析和未到公开阶段的正确答案；
- hidden tests、Rubric、reference solution和私有CSV期望输出；
- API Key、Token、宿主绝对路径和未脱敏个人信息；


### 3.9 负责人现场复核：重做题组未正确绑定画像与上一轮错题

负责人在“使用新题组重试”现场观察到第二轮显示`固定题保障`。对对应Attempt和服务端私有运行轨迹复核后确认：

1. 第二轮不是“完全没有调用AI”。对应运行先后执行了`generator`和`generator-repair`，但两次候选均复用了上一轮已排除的题目ID，最终以`candidate_question_id_excluded_1`被服务端硬门禁拒绝。
2. 候选被拒绝后，系统按既有安全合同切换为四道章节固定题，因此页面显示`固定题保障`。这是失败降级结果，不是AI生成成功。
3. 原重做请求只排除上一轮题目ID，没有把上一轮错题、旧题干和学情画像Agent结论作为结构化上下文传给Generator。
4. 原错误知识目标可能从整个诊断Evidence中取值，导致当前章节的重做请求混入其他章节知识；这不符合“围绕当前正文和本轮错题补救”的要求。

本地整改后的正式流程为：

```text
上一轮客观题未达标
→ 服务端读取上一轮私有Attempt和正式Evidence
→ 只提取当前章节上一轮答错题目的题干、正文解析和公开来源
→ 构建确定性学情画像
→ 调用学情画像Agent生成安全的补救重点说明
→ Agent不可用时保留确定性画像，不阻断重做
→ Generator同时接收当前章节RichLesson正文、错题上下文和画像说明
→ Generator生成四至六道新题，重复考察每个错误知识，同时更换ID、题面、场景或代码片段
→ Hunter检查错题覆盖、题面差异、答案唯一性和正文依据
→ 高风险争议触发Defender
→ Judge进行最终审核
→ 程序硬门禁拒绝任何旧ID或逐字复用的旧题干
→ 审核通过后展示AI新题组；任一环节失败才使用章节固定题保障
```

本地实现结果：

- `QuizActivityRuntime`在重做前调用`LearnerProfileAgentPort`；成功时采用Agent说明，失败、超时或录制模式无响应时使用确定性画像。
- 重做上下文新增`excludedQuestionPrompts`、`missedQuestions`、`learnerProfileSummary`和`learnerProfileEvidenceRefs`；错题上下文不包含正确答案。
- 目标知识只绑定当前活动的主知识点，不再把诊断中其他章节的错误Evidence混入当前章节重做请求。
- Generator、Hunter和Judge都收到同一份重做上下文；提示词版本升级为`w4-d2-v9`，旧缓存不会冒充新合同结果。
- 服务端新增旧题ID和旧题干的确定性拒绝；Generator有一次针对具体失败类别的修复机会，修复失败后才进入固定题保障。
- 公共DTO不返回画像摘要、Evidence引用、错题上下文、候选答案或私有审核内容。

当前状态：

```text
ISSUE_3_RETRY_REMEDIATION=RESOLVED_LOCAL / LIVE_API_RETEST_REQUIRED
LEARNER_PROFILE_AGENT_ON_RETRY=IMPLEMENTED_WITH_DETERMINISTIC_FALLBACK
RETRY_SCOPE=CURRENT_LESSON_AND_PREVIOUS_MISSES_ONLY
OLD_QUESTION_ID_REUSE=DETERMINISTICALLY_REJECTED
OLD_QUESTION_PROMPT_REUSE=DETERMINISTICALLY_REJECTED
LIVE_MODEL=LIVE_NOT_RUN_IN_THIS_VALIDATION
GIT_STATUS=UNCOMMITTED / NOT_UPLOADED
```

上述状态只证明本地合同和自动化回归已经建立。负责人使用正确API配置重启服务后，还需完成一次真实链路复验：第一轮故意答错至少一题，点击“使用新题组重试”，确认来源为`AI个性化生成`，新旧题目ID和题干均不同，且错题知识在第二轮再次出现；若仍显示固定题，应以本轮`generationRunId`和`detailCode`定位具体失败阶段，不得笼统登记为AI不可用。

### 4.2 负责人期望

4. 页面刷新以及前后端重启后，仍能从服务端恢复到一致状态。

6. 对能够读取历史学习证据、但不能沿用旧路径的会话，允许提供“按当前资料包重新计算路径”。重新计算不得删除或改写旧Attempt和Evidence，必须建立清楚的新路径版本关联。
7. 恢复接口必须保持幂等；连续点击、刷新和重启不能重复创建会话、Attempt、Evidence或路径版本。
8. 无法恢复时保留原始记录，不自动清理、不静默覆盖，也不把客户端残留状态冒充服务端恢复成功。

### 4.4 验收标准


同时验证：

1. 完整会话能够恢复到原来的可继续学习位置。
2. 不完整或不兼容会话不会显示虚假的可恢复状态。
3. 旧资料包会话的兼容或降级原因可理解、可复验。

5. Web与TUI读取同一服务端会话事实。

## 5. 诊断前错误要求用户选择“可用时间”

### 5.1 已观察事实

1. 当前开始页在学习者尚未完成诊断时提供“可用时间”选择，并显示类似`400分钟`的选项。
2. 此时系统还不知道学习者对六个知识点的掌握情况，也没有确定哪些章节需要完整学习、快速巩固、快速验证或允许跳过，因此无法形成有依据的学习所需时长。
3. 将“可用时间”作为诊断前路径输入，容易让页面表达成“用户先选一个时长，系统再把内容塞进这个时长”，与先诊断、再生成个性化路径的产品逻辑相反。

### 5.2 负责人裁决

“学习所需时长”是诊断和路径计算的输出，不是学习者在开始页自行选择的输入。系统必须先判断学习者需要学习什么，再根据实际路径向学习者说明预计需要多长时间。

目标流程如下：

```text
选择资料包和学习目标
→ 填写必要的基础背景
→ 完成知识诊断
→ 生成KnowledgeState
→ 确定完整学习、快速巩固、快速验证和可跳过节点
→ 生成个性化路径
→ 确定性计算预计学习时长
→ 在路径确认页展示总时长、分项时长和计算依据
```

### 5.3 整改要求

1. 从开始页和诊断前会话设置中删除“可用时间”选择，不再让学习者选择`400分钟`等固定值。
2. 检查公共DTO、会话创建接口、PathEngine和页面状态，移除“诊断前可用时间决定学习路径”的行为；如果合同为兼容旧数据暂时保留该字段，运行时也不得让它改变必学知识、证据要求或路径合法性，并应登记清理范围。
3. 预计时长必须由确定性程序根据实际路径计算，至少考虑节点类型、完整教学或快速验证模式、活动数量和已冻结的活动时间估算。Agent可以生成通俗解释，但不能自行填写或修改权威分钟数。
4. 路径确认页展示“预计总学习时长”和各章节预计用时，使学习者能够理解时间来自哪些学习任务。
5. 时间应显示为诚实的预计值或区间，例如“约180至220分钟”，不得使用没有测量依据的伪精确数字。
6. 三类学习者因诊断结果产生不同学习动作时，预计时长应随实际路径变化；不能预先硬编码三类展示数字冒充个性化。
7. “每天愿意学习多少分钟”属于未来的学习节奏安排，不等同于“完成当前路径需要多少分钟”。本轮比赛Demo不实现每日计划功能，也不允许该偏好删减必学内容、Evidence要求或正式活动。
8. 学习者重试或新增补救节点后，系统可以基于当前服务端路径事实重新估算剩余时长，但不得倒改历史Attempt和Evidence。

### 5.4 验收标准

1. 开始页和诊断前流程不再出现“可用时间”输入。
2. 完成诊断前，页面不展示伪装成诊断结论的学习总时长。
3. 完成诊断并生成路径后，路径确认页展示可复算的总预计时长及章节分项。
4. 同一输入和同一KnowledgeState重复计算得到一致结果。
5. 三类学习者的预计时长与各自完整学习、快速巩固或快速验证节点相匹配；路径相同时不得为了展示差异而强行给出不同时间。
6. 刷新、服务端恢复和重新进入路径页后，预计时长与服务端权威路径一致。
7. 删除界面字段后，会话创建、诊断、路径生成、恢复、Web与TUI流程均无合同断裂。

## 6. “讲解偏好”错误提供`uncertain`选项

### 6.1 已观察事实

|---|---|---|
| 重点速览 | `concise` | `concise` |
| 逐步讲解 | `step_by_step` | `guided` |
| 案例优先 | `example_first` | `practice` |

这里的“三个版本”指同一知识点的三套教学正文和讲解方式，不代表三个模型可以提供互相冲突的知识事实、答案或业务规则。三套正文必须覆盖相同的canonical rules和来源依据。

4. 只修改“讲解偏好”的可选值。Python经验和Pandas经验仍可保留`uncertain`，因为学习者确实可能无法准确判断自己的技术基础，诊断仍需纠正自报信息。
5. 对历史会话或旧客户端传入的`explanation_preference=uncertain`，服务端不得报500或产生空版本。兼容层应确定性映射为`step_by_step → guided`，并在下一次正常写入时保存为有效值；页面不得继续展示`uncertain`。
6. 学习者进入章节后仍可在三套正文间本地切换。切换只改变展示版本，不修改KnowledgeState、路径、Attempt、Evidence、mastery或正式判分。
7. Agent只能根据已经选择的正文提供可选个性化学习提示，不能擅自覆盖用户偏好或把三套权威正文改成第四种动态正文。

### 6.4 验收标准

## 8. 代码补全题目合同不完整，失败后无法修改和重试

### 8.1 已观察事实

1. 当前活动标题为“补全按列缺失处理”，代码编辑区提供`clean_missing(df)`骨架和`TODO_BEGIN / TODO_END`范围，因此它在合同上属于代码补全活动。
2. 页面只显示一句“按冻结规则处理order_id、customer_id、amount、order_date和note缺失”，没有清楚展示公开输入、期望输出、逐字段冻结规则、允许修改范围、函数返回合同、公开示例和判分维度。学习者难以仅凭当前页面理解具体要补全什么。
3. 正式提交失败后，结果页显示`fail`、`0 / 1`、`test_failed`和英文通用文案，但没有给出安全、可操作的错误反馈。
4. 失败结果页只提供“进入下一活动”，没有“返回修改代码”“重新提交”“返回教学内容”或回看题目入口。
5. 点击“进入下一活动”会进入下一章节，失败的当前活动没有形成补救或重试闭环。这容易让学习者误以为失败也等于完成，并可能导致页面推进状态与KnowledgeState、路径门槛不一致。

### 8.2 负责人期望

代码活动必须先把公开题目合同讲清楚，再由Node/Python进行权威评测。评测失败后，学习者应获得不泄漏私有答案的有效反馈，能够返回原题修改并重试；失败不能被“进入下一活动”静默跳过。

目标流程如下：

```text
阅读当前知识点教学正文
→ 进入代码补全活动
→ 阅读完整公开题目合同和示例
→ 在允许范围内编辑并保存草稿
→ 正式提交给Node/Python权威评测
→ PASS：记录Attempt与Evidence并解锁下一活动
→ FAIL：记录本次Attempt和安全反馈，但不宣告掌握
→ 返回原代码草稿或教学正文
→ 修改代码并创建关联重试Attempt
→ 通过后再按路径规则继续
```

### 8.3 代码补全题目展示要求

1. 页面明确标注“代码补全题”，并使用中文显示活动类型；内部`code_completion`枚举可以保留。
2. 题目至少展示：业务背景、本题目标、函数签名、输入数据约定、返回值约定、逐字段公开规则、允许编辑范围、禁止事项、公开最小示例和公开验收项。
3. `TODO_BEGIN / TODO_END`必须与服务端允许修改范围一致。前端提示、提交校验和后端执行器不得各自维护互相冲突的范围。
4. 逐字段规则必须来自当前Profile公开活动合同，与教学正文的canonical rules一致；不能要求学习者猜测所谓“冻结规则”。
5. 公开示例应展示最小输入、关键操作意图和期望输出性质，但不得包含hidden tests、reference solution、完整Rubric、私有答案或能够反推出隐藏数据的内容。
6. 页面说明“保存草稿”不会正式评分，“提交正式评测”才创建权威Attempt，避免学习者混淆两种操作。
7. 题目和最近草稿在刷新、返回教学内容和服务端恢复后保持一致。

### 8.4 失败、反馈与重试要求

1. 正式评测失败时，主操作应为“返回修改代码”或“修正并重试”，同时提供“返回教学内容”；不得把“进入下一活动”作为失败状态下唯一或主要操作。
2. 失败状态默认不解锁依赖当前知识点通过结果的下一活动或下一章节。若路径合同允许带缺口继续，必须由确定性PathEngine明确生成补救安排并用中文说明，不能由页面按钮自行越过门槛。
3. 返回修改时恢复刚才提交的代码或其明确标识的可编辑副本，不应清空为初始`pass`骨架。
4. 每次正式重试创建新的Attempt ID，并通过`parentAttemptId`或既有等价字段关联上一次尝试；不得覆盖失败历史，也不得重复写入同一次Attempt。
5. 失败反馈至少提供公开测试结果、错误类别、失败阶段和针对当前知识点的安全改进方向。不能只显示`test_failed`或“One or more deterministic checks did not pass.”。
6. 反馈不得泄漏hidden test名称、隐藏输入、期望私有输出、完整Rubric、reference solution或候选答案。必要时由确定性错误映射生成中文提示，Agent只能在安全投影范围内补充解释。
7. 失败Attempt可以作为错误证据或补救依据，但不能写成通过Evidence、不能提升为已掌握，也不能把活动标记为成功完成。
8. 通过重试后，服务端按确定性规则生成新的通过Evidence并重新计算KnowledgeState和路径；旧失败Attempt保持可追溯。
9. 重复点击提交、网络超时后重试、服务重启恢复和浏览器刷新都必须保持幂等，不能重复判分或生成重复Evidence。
10. 结果页将`fail`、`test_failed`、`completed`等机器状态转换为清楚的中文。执行进程完成不等于答案通过，页面必须区分“评测已执行”和“答案已通过”。

### 8.5 验收标准

1. 学习者不查看仓库文件也能从页面完整理解代码补全任务、输入输出和逐字段公开规则。
2. 使用错误代码提交后，结果页显示中文失败原因和安全改进方向，并提供“返回修改代码”“返回教学内容”。
3. 返回代码页后保留失败提交内容；修改并再次提交形成新的关联Attempt。
4. 失败后不能通过普通“下一活动”按钮静默进入依赖当前通过结果的下一章节。
5. 重试通过后才按确定性路径合同解锁后续活动，并只生成一次对应通过Evidence。
6. 失败、重试、通过、刷新和服务重启后，Attempt链、草稿、KnowledgeState和路径状态可以复算且保持一致。
7. Node/Python继续承担正式权威评测；Pyodide关闭态不影响提交、重试和恢复。
8. DOM、网络、Worker、日志和构建产物不泄漏hidden tests、完整Rubric或reference solution。

## 14. 第二次题组未达标后无法再次重做，继续学习也未保留“未掌握”事实

### 14.1 已观察事实

1. 学习者第一次完成客观题组但未达到通过要求时，结果页提供“使用新题组重试”，该行为符合当前期望。
2. 学习者使用新题组完成第二次作答后，如果仍未达到通过要求，结果页只提供“继续下一步”。
3. 第二次未达标结果页不再提供“使用新题组重做”，学习者失去了继续补救当前知识点的选择。
4. 点击“继续下一步”会直接进入下一个章节，但当前页面没有说明本节将以“未掌握”状态继续，也没有证明该缺口会进入最终总结。
5. 如果推进时把未达标活动当作普通完成，将导致页面流程与Attempt、Evidence、KnowledgeState和最终总结事实不一致。

### 14.2 负责人裁决与目标流程

第一次未达标后仍按当前方式引导学习者优先补救，只提供“使用新题组重做”。第二次及之后仍未达标时，必须同时提供两种选择：

1. “使用新题组重做”：继续补救当前知识点，创建新题组和新Attempt。
2. “暂时跳过，进入下一章节”：允许学习者带着当前知识缺口继续，但当前知识点必须保持“未掌握”，并在最终总结中明确体现。

目标流程如下：

```text
首次题组未达标
→ 记录失败Attempt与安全复盘
→ 使用新题组重做
→ 第二次仍未达标
→ 选择A：使用新题组重做，可继续多次补救
→ 选择B：暂时跳过并进入下一章节
→ 选择B时保留当前知识点“未掌握”及全部Attempt历史
→ 最终总结列出未掌握章节、作答次数、结果和建议复习入口
```

### 14.3 状态与合同要求

1. 首次未达标时只提供“使用新题组重做”，不提供普通下一章节入口，保持优先补救行为。
2. 从第二次未达标开始，每次结果页同时提供“使用新题组重做”和“暂时跳过，进入下一章节”。不得再次取消重做入口，也不限制后续重做次数。
3. “使用新题组重做”必须生成与当前知识点和Session绑定的新题组。正常情况下继续遵循AI生成与多Agent审核；生成或审核失败时使用固定安全fallback，不得重复冒充同一题组为新题组。
4. 每次正式作答创建新的Attempt ID，并通过现有父尝试字段或等价关系形成可追溯链；不得覆盖第一次或第二次失败记录。
5. 选择进入下一章节是一项明确的学习者决定。服务端必须记录结构化的“带缺口继续”事实，包括知识点、对应活动、最后Attempt、选择时间和未达标原因，不得只依靠前端跳转。
6. 带缺口继续后，当前知识点的KnowledgeState保持`not_mastered`或现有等价未掌握状态；不得写成`mastered`、不得生成通过Evidence，也不得用“流程已推进”冒充“知识已掌握”。
7. 路径引擎可以根据本裁决允许后续章节变为可进入，但路径节点必须用中文区分“已掌握”和“暂时跳过/未掌握”，不能统一显示为“已完成”。
8. 后续学习产生的新Evidence不得反向覆盖该缺口。只有学习者重新完成当前知识点并达到确定性通过门槛后，才能按合同更新为已掌握。
9. 刷新、浏览器返回、服务重启和“从服务端恢复”后，重做次数、当前选择、未掌握标记、Attempt链和后续章节位置必须保持一致。
10. 重复点击“暂时跳过”或网络超时后的重试必须幂等，不得重复推进章节、重复记录缺口或重复生成Evidence。

### 14.4 最终总结要求

1. 最终总结增加清楚的“尚未掌握/建议复习”区域，列出所有带缺口继续或最终仍未达标的知识点。
2. 每项至少显示中文章节名、通过要求、作答次数、最佳成绩或正确题数、最近一次结果和“返回复习/重新挑战”入口。
3. 总结中的完成进度必须区分“已经学习过”和“已经掌握”，不得因为用户走到最后一页就显示全部掌握。
4. 未掌握结论来自服务端Attempt、Evidence和KnowledgeState的确定性聚合，不能由前端根据访问过的页面数量推测。
5. 如果所有章节均达到通过门槛，明确显示没有待补知识点；如果存在缺口，不得使用“全部完成”“全部掌握”等误导性结论。

### 14.5 验收标准

1. 第一次未达标结果页只显示“使用新题组重做”；第二次及后续未达标结果页同时显示“使用新题组重做”和“暂时跳过，进入下一章节”。
2. 第二次未达标后选择重做，能够获得新题组并创建第三个关联Attempt；第三次仍未达标时两种选择继续存在。
3. 第二次未达标后选择进入下一章节，能够进入下一章节，但原知识点显示为“暂时跳过/未掌握”，且不存在通过Evidence。
4. 完成后续流程进入最终总结，未掌握区域准确列出该章节、作答次数、最佳或最近结果及复习入口。
5. 从最终总结返回重新挑战并达标后，服务端重新计算KnowledgeState和总结，未掌握项按确定性事实消除或更新。
6. 覆盖刷新、服务端重启、重复点击、网络超时、AI题组生成成功、审核拒绝和固定fallback；状态均可恢复且不重复写入。
7. Web与TUI消费同一服务端未掌握事实和推进规则，不维护两套重试次数或总结逻辑。
8. 全流程不得泄漏私有答案、hidden tests、完整Rubric或reference solution，也不得把失败Attempt写成PASS。

### 15.5 输入/输出样例与CSV下载要求

1. 每个代码活动至少提供一组公开样例，包含样例名称、处理前CSV、处理后CSV、样例说明和对应的公开验收要点。
2. 对`inspect_orders`题，样例必须体现七个目标列加一个额外列的输入，以及只保留七列且顺序固定的输出，并说明原始输入不变。
3. 页面应按“任务背景、函数签名、输入、输出、规则、禁止事项、编辑范围、输入样例、输出样例、样例解释、公开验收要点”的顺序组织题面。
4. 输入和输出样例使用独立的等宽容器；数据较长时提供“下载样例输入CSV”和“下载样例输出CSV”，下载文件使用稳定UTF-8编码和`.csv`扩展名。
5. 页面展示内容与下载文件逐字节一致，下载链接使用安全样例资产ID或安全路径，不暴露宿主绝对路径、临时目录或私有定位符。
6. 下载不创建Attempt、不改变KnowledgeState或路径；Web和TUI消费同一份结构化公开样例合同。
7. 样例不得包含hidden tests、隐藏输入、完整Rubric、reference solution或私有答案；缺少样例ID、文件名、版本或来源时合同检查失败。
8. 页面、下载资产、公开测试、代码草稿和错误反馈必须绑定同一活动版本，不能随AI题组或固定fallback切换而漂移。

## 16. 活动内容确认保存失败后进入加载/失败循环

### 16.1 已观察事实

1. 代码活动页面突然进入“活动内容未确认保存”失败界面，并显示`FAILED TO FETCH`。
2. 失败界面说明本地服务没有完成本次请求，并声称最后一次安全输入仍保留在当前页面，但当前截图没有显示可恢复的题面、草稿或请求编号。
3. 点击“重试”后进入“正在加载活动内容”界面，随后又回到同一个“活动内容未确认保存”失败界面，形成失败→加载→失败的循环。
4. 用户无法判断这是活动快照不存在、Session版本冲突、服务端暂时不可用、请求超时，还是当前活动内容已经改变；也没有看到明确的下一步恢复方式。
5. 在失败和重试过程中，系统必须避免重复创建Attempt、重复提交答案、覆盖最后安全草稿或把未确认的内容当作已保存事实；当前页面没有给出足够证据说明这些边界已经满足。

### 16.2 负责人期望

活动内容请求失败时，应给出一次可解释、可恢复的降级流程，而不是无限回到同一错误页。最后一次已确认的题面、代码草稿和Session事实必须保留；如果无法恢复，应允许用户明确返回教学内容、回到路径或重新选择当前活动，并说明当前提交是否产生Attempt。

### 16.3 整改要求

1. 服务端为活动内容读取和确认保存定义稳定的请求关联标识、Session版本和活动版本；前端错误页只显示安全的中文状态，不暴露内部堆栈或宿主路径。
2. “重试”必须有有限次数或退避策略，并区分可重试错误、版本冲突和不可恢复错误；连续失败后不能无限自动跳转。
3. 重试期间保留最近一次已确认的题面、代码草稿、活动ID和Session快照；不得清空编辑器或回退到未经确认的初始骨架。
4. 如果服务端确认保存成功，页面应明确显示“已保存”并恢复活动；如果确认失败，必须明确显示“未保存”，并说明最后安全草稿的时间或版本。
5. 重试、刷新、浏览器返回和服务重启恢复必须幂等：不得重复创建Attempt、重复提交、重复写Evidence或推进路径。
6. 失败页面至少提供“再次尝试”“返回教学内容”“返回学习路径”三个清楚动作；无法恢复时不得只提供“返回开始页”而丢失当前Session上下文。
7. 若活动内容确实不存在或版本已失效，应进入确定性的缺失活动分支，说明需要重新选择活动或重新建立Session，不得在加载页和失败页之间循环。
8. Web和TUI读取同一服务端活动快照、草稿和错误分类；不允许一端显示已保存、另一端显示未保存。
9. 该错误流程不能泄漏私有答案、hidden tests、完整Rubric、reference solution、Token或设备信息。

### 16.4 验收标准

1. 模拟服务端超时、连接拒绝、活动版本冲突和活动不存在时，页面分别显示中文、可理解且不泄漏内部信息的状态。
2. 点击重试后成功时回到同一活动，题面版本、草稿、Session和Attempt上下文保持一致。
3. 连续重试达到上限后不再循环，显示返回教学内容/路径的恢复选项，并保留最后安全草稿。
4. 刷新、浏览器返回、服务端重启恢复后，不重复创建Attempt、不重复提交、不重复Evidence，状态可复算。
5. 失败过程中用户已输入的代码不会被静默丢失；若输入尚未确认保存，页面明确标注其未保存状态。
6. 正常成功路径、失败后重试成功、失败后返回教学内容、活动缺失和Session恢复均通过桌面、平板和手机验证。
7. 浏览器网络、DOM、日志和构建产物不出现私有答案、hidden tests、reference solution或宿主绝对路径。

## 17. Agent等待期间缺少进行中状态与计时反馈

### 17.1 已观察事实

1. 点击“使用新题组重试”后，系统会重新读取当前教学正文并执行动态题生成与审核，但页面在等待期间没有清楚显示当前正在处理的阶段。
2. 按钮长时间没有可见变化，学习者无法判断请求是否已经发出、是否正在等待Generator、Hunter、Defender或Judge，还是页面已经失去响应。
3. 实时模型模式下，生成和审核可能需要几十秒；当前页面没有显示已等待秒数，也没有显示预计超时、固定题fallback或失败后的下一步。
4. 如果学习者在等待期间再次点击、刷新或返回，容易产生重复请求、重复生成Attempt，或误以为第一次点击没有生效。

### 17.2 负责人期望

本项设计的核心宗旨是：让学习者在等待Agent或实时模型处理时明确知道系统仍在工作，避免因为页面长时间没有视觉变化而误以为网页卡死、请求丢失或按钮没有生效。状态反馈不是装饰性动画，而是对当前服务端处理进度和可用降级路径的可理解投影。

凡是会触发Agent或实时模型处理的按钮，都必须在请求进行期间进入明确的处理中状态。按钮文字应能让学习者知道系统正在做什么，并可在括号中显示已经处理的秒数，例如：

```text
正在生成新题组（已处理 12 秒）
正在审核题组（已处理 38 秒）
正在准备结果（已处理 51 秒）
```

等待状态必须与服务端事实一致，不能用静态动画或无期限的“加载中”冒充实际进度。超时、模型失败、审核拒绝和固定题fallback都要给出明确中文状态。

### 17.3 整改要求

1. 所有触发Agent、模型或可选异步能力的按钮，在请求开始后立即变为禁用状态，并显示当前阶段和已等待秒数。
2. 动态题生成至少区分：`正在生成题组`、`正在检查题目`、`正在处理争议`、`正在准备题组`和`正在使用固定题保障`；不要求暴露内部Prompt、私有答案或完整Agent轨迹。
3. 秒数从本次用户操作真正发出请求时开始计算，显示整数秒，刷新后不得凭客户端时间伪造服务端已经完成的阶段。
4. 页面应显示安全的阶段说明和等待提示，例如“请勿重复点击，当前请求仍在处理”；按钮不得在等待期间允许重复提交。
5. 运行时必须保留请求关联ID、Session版本、活动版本和幂等键；重复点击、浏览器返回、刷新或网络重试不得创建重复Attempt、重复Evidence或多个并行正式题组。
6. 当达到模型等待阈值时，页面必须明确进入“正在切换固定题保障”或“模型超时，使用固定题保障”状态；不能继续显示普通的实时AI成功状态。
7. API失败、审核拒绝、题量不足和不可恢复错误分别显示可理解的中文结果，并提供“返回教学内容”“重试”或“使用固定题保障”等符合当前合同的动作。
8. 如果后台任务仍可恢复，页面应允许恢复同一个`generationRunId`的checkpoint，不得因刷新而从零创建无法区分的新请求；如果任务已放弃，必须明确标记为失败或fallback完成。
9. Web和TUI消费同一服务端阶段、状态和超时事实，不维护两套独立的计时或Agent进度。
10. 计时和状态文本不得包含API Key、Token、宿主路径、私有答案、hidden tests、Rubric或reference solution。

### 17.4 验收标准

1. 点击“使用新题组重试”后，按钮立即显示处理中状态，并持续显示“当前阶段（已处理 N 秒）”；按钮不可重复点击。
2. 录制响应、实时AI成功、模型超时后fallback、审核拒绝和网络失败五种情形均显示不同且可理解的结果。
3. 等待期间刷新或返回后，服务端不会产生重复Attempt、重复题组或重复Evidence；能够恢复则恢复同一请求，不能恢复则明确失败并提供安全出口。
4. 实时模型请求超过合同阈值后，页面不无限等待，能够显示超时并按确定性规则进入固定题保障或失败恢复分支。
5. 题组生成阶段至少能复验Generator、Hunter、Defender、Judge阶段顺序，但前端只显示安全摘要，不泄漏私有审核内容。
6. 桌面、平板和手机视口下，最长阶段文案与秒数不重叠、不溢出，按钮宽度稳定，焦点和禁用状态清楚。
7. 测试覆盖快速成功、慢响应、超时、重复点击、刷新、服务重启和API失败；所有结论以服务端日志、状态快照和页面结果交叉复验。

### 17.5 本地整改结果与Demo边界

1. 新增统一的异步动作进度Hook。用户点击进入客观题或“使用新题组重试”后，按钮立即禁用，并显示`当前状态（已处理 N 秒）`；计时从本次点击真正发出HTTP请求时开始。
2. 学习页显示“正在生成并审核题组”；重试链先显示“正在确认重试条件”，真正进入新题组生成请求后显示“正在生成并审核新题组”。代码活动和带缺口继续也使用同一等待反馈，不再保持无变化按钮。
3. 同一结果页存在“重试”和“放弃”两个按钮时，只改变本次实际点击按钮的文字；另一个按钮保持原文并禁用，避免两个动作同时显示成同一状态。
4. 本轮不新增SSE、轮询协议或服务端Agent阶段DTO。单次HTTP请求期间，浏览器无法证明Hunter、Defender、Judge分别完成到哪一步，因此页面只显示真实可证明的聚合状态，不伪造内部阶段进度；实际Agent顺序继续由服务端审核轨迹复验。
5. 按钮设稳定最小宽度、正常中文换行和独立可访问状态区。最新Web构建已由真实浏览器加载；桌面与390像素宽视口均无页面横向溢出。
6. 页面自动化覆盖首次进入题组和“使用新题组重试”的延迟响应，证明等待期间按钮立即禁用并显示`已处理 0 秒`。实时模型超时及固定题切换仍须结合真实API运行单独复验；本轮不得据此登记`LIVE_MODEL_PASS`。

## 18. 客观题复盘缺少原题题干

### 18.1 已观察事实

1. 客观题提交后进入“提交后安全复盘”区域，目前复盘卡片主要显示“回答正确/需要复习”、正确答案和正文解释。
2. 复盘卡片没有再次显示本题原始题目，至少没有显示完整题干。
3. 复盘时学习者只能看到答案和解释，无法可靠回忆这道答案对应的具体问题；即使解释本身正确，也难以完成有效的错题复盘。
4. 该问题对实时 AI 题和固定题都成立：复盘必须使用本次实际展示并提交的题目快照，不能重新生成一遍题目代替原题。

### 18.2 负责人期望

客观题提交后，每个复盘卡片必须先显示本题原始题干，再显示作答结果、正确答案和正文解释。复盘可以不再次展示选项，或者将选项放在可展开区域，但不能省略题干。

推荐的显示顺序为：

```text
原题题目
→ 我的作答结果
→ 正确答案
→ 正文明确/知识点解释
→ 是否需要复习
```

### 18.3 整改要求

1. 服务端在提交结果和复盘安全 DTO 中保留本次题目的安全题干快照；题干必须来自同一题组、同一活动版本和同一 Attempt。
2. 复盘 DTO 可以省略选项、私有答案细节和审核内部轨迹，但不得省略题干、题目顺序和题目身份绑定。
3. Web 和 TUI 使用同一个复盘事实；Web 不得只从当前页面临时状态读取题目，刷新或恢复后仍能显示原题题干。
4. 实时 AI 题、录制题组和固定 fallback 均必须遵守相同复盘结构，不能因为来源不同而丢失题干。
5. 复盘页面应区分“原题题目”和“正确答案”，避免把答案文字误当成题目；题干较长时允许换行，但不能截断到无法理解。
6. 复盘区域不得泄漏 hidden tests、私有答案、完整 Rubric、reference solution、API Key、Token 或宿主路径。

### 18.4 验收标准

1. 提交一组客观题后，每一道复盘卡片都能看到对应的原始题干。
2. 题干与提交时展示的题目逐题对应；刷新、返回、服务端恢复后对应关系不变。
3. 正确题、错误题和需要复习题均显示原题题干、作答结果、正确答案和正文解释。
4. 选项可以隐藏或折叠，但隐藏选项不能导致题干缺失；题干在桌面、平板和手机视口下不重叠、不溢出。
5. AI 生成题、录制题和固定题 fallback 的复盘结构一致，不能用重新生成的题目冒充提交时原题。
6. 自动化测试检查复盘安全 DTO 包含题干且不包含私有评测资产；浏览器测试检查实际页面可见题干。

### 18.5 本地整改结果

1. `QuizActivityResult.answerReview`新增安全题干字段`prompt`。确定性题组运行时从本次Attempt的私有题目快照复制题干，与`questionId`、答案键、解释和来源锚点保持同一题组绑定。
2. Web复盘卡片按“原题 → 回答结果 → 正确答案 → 正文解释”的顺序展示；不重复传输选项，也不从当前页面临时状态或新一次模型生成中重建原题。
3. 新生成结果必须携带题干；页面对历史旧快照保留明确的兼容提示，不把空字符串或其他题目冒充原题。
4. 自动化已验证每道复盘题干可见、题干位于正确答案之前，并更新六知识点合同字段断言。私有答案仍只在提交后的当前Attempt安全复盘中返回，未改变提交前零答案泄漏边界。

## 19. 代码补全二次失败后缺少“重试或放弃”选择

### 19.1 已观察事实

1. 代码补全第一次提交未通过时，页面显示评测结果并提供修改代码后重试，这一阶段的方向是正确的。
2. 负责人要求代码补全和客观题保持一致：第一次未通过必须进入重做/修改流程，不能直接推进到下一活动。
3. 修改代码后再次提交仍未通过时，页面不能只留下单一的“修改代码后重试”或直接进入下一环节，而应给学习者两个明确选择。
4. 当前观察到的代码结果页需要补齐二次失败分支：继续修改代码重试，或放弃本次活动并进入下一个教学/活动环节。

### 19.2 负责人裁决与目标流程

```text
第一次代码提交未通过
  → 显示评测反馈
  → 修改代码并重试
第二次代码提交仍未通过
  → 修改代码重试
  → 放弃本次活动，进入下一个教学/活动环节
```

“放弃并继续”不是判定通过，也不是静默跳过。它必须记录本节代码活动未掌握/未达标事实，后续最终总结要能够明确显示该知识点未完成或需要复习。

### 19.3 整改要求

1. 第一次未通过时，保留当前代码草稿、Attempt 结果和公开评测反馈，提供“修改代码后重试”；不得直接显示进入下一活动作为唯一主动作。
2. 第二次及以后未通过时，页面同时提供两个并列且含义清晰的动作：
   - “修改代码重试”：回到同一代码活动，保留现有草稿和失败反馈；
   - “放弃并进入下一环节”：结束本次活动但标记为未掌握/未达标，再推进到合同允许的下一教学或活动节点。
3. “放弃并进入下一环节”必须由服务端确认，不能由前端直接修改路径游标；服务端应写入可复算的跳过原因、最后一次 Attempt、活动 ID、知识点 ID 和 Session 版本。
4. 放弃后不得生成通过 Evidence、mastery 或完成该知识点的正向路径证据；最终总结必须展示“本节未掌握/暂未完成”及必要的复习入口。
5. 重试和放弃都必须幂等。重复点击、刷新、浏览器返回和服务端恢复不能重复创建 Attempt、重复推进路径或覆盖已有失败事实。
6. 如果活动已经达到合同规定的最大尝试次数，仍要显示两个安全出口或明确说明不可继续重试的原因；不能无限提交，也不能无提示自动跳过。
7. Web 和 TUI 必须读取同一个服务端结果和下一步状态；按钮文案、尝试次数和未掌握状态不能一端有、一端没有。
8. 失败结果页不得泄漏 hidden tests、reference solution、完整 Rubric、私有答案、Token 或宿主路径。

### 19.4 验收标准

1. 第一次提交失败后，能看到评测反馈和“修改代码后重试”，不会直接推进下一活动。
2. 第二次提交仍失败后，同时看到“修改代码重试”和“放弃并进入下一环节”两个选项。
3. 选择重试时回到同一活动，代码草稿和失败上下文保留；选择放弃时进入正确的下一节点。
4. 放弃后，当前知识点在路径和最终总结中明确标记为未掌握/未完成，不得显示为通过。
5. 刷新、返回、重启服务和重复点击后，Attempt 数量、Session 版本、路径游标和未掌握事实保持一致。
6. 桌面、平板和手机下两个动作不重叠，主次关系清楚，最长中文文案不被截断。
7. 自动化测试覆盖第一次失败、第二次失败重试、第二次失败放弃、恢复和幂等；浏览器测试覆盖真实按钮和最终总结展示。

### 19.5 本地整改结果

1. 代码活动第一次学习者失败后仍只进入修改重试流程；只有同一活动至少存在两次Attempt、最新Attempt已经完成且结论为`fail/partial`时，服务端才接受“放弃并进入下一环节”。
2. 第二次失败页面同时显示“修改代码后重试”和“放弃并进入下一环节”。两个动作共享服务端Session事实，按钮处理中禁用，前端不能直接改路径游标。
3. 放弃操作复用现有`continue-with-gap`合同，服务端写入`status=insufficient`、`continuedWithGap=true`、`currentAttempt=null`并以`error_remediation`重算合法路径后缀；既有两次失败Evidence、KnowledgeState和evidenceVersion保持不变，不产生通过Evidence。
4. 相同`requestId`重放返回同一提交结果，不重复推进Session；第一次失败、非最新Attempt、未提交结果或通过结果均被稳定拒绝。
5. 总结页消费同一`continuedWithGap`事实并显示“暂时跳过 / 未掌握”，同时保留复习入口。页面自动化已验证第二次失败出现两个动作、放弃调用服务端接口、进入下一节点以及总结未掌握文案。

## 20. 客观题首次打开时进度条提前前进

### 20.1 已观察事实

1. 首次打开四题客观题时，页面显示“第1题 / 共4题 · 尚未保存”，但顶部进度条已经出现了非零进度。
2. 此时学习者还没有选择或保存第1题答案，进度条不应根据当前题目序号直接前进。
3. 当前视觉表达容易让学习者误以为第1题已经完成，或者误以为系统已经保存了答案；这与“尚未保存”的状态文案矛盾。

### 20.2 负责人裁决与目标流程

客观题进度条应表示“已形成答案草稿的题目数量 / 题目总数”，而不是“当前正在查看的题目序号 / 题目总数”。

```text
首次打开第1题，未选择答案
  → 0 / 4，进度条为0%
选择第1题答案
  → 1 / 4，进度条前进到25%
进入第2题但尚未选择答案
  → 仍为1 / 4
返回第1题并修改答案
  → 仍为1 / 4，不重复计数
四题均形成答案草稿
  → 4 / 4，允许提交完整题组
```

“形成答案草稿”表示学习者已经为该题选择了一个答案；它不等同于服务端已经提交题组。页面仍应分别显示草稿状态、保存状态和提交状态，不能用进度条替代这些状态。

### 20.3 整改要求

1. 首次打开题组时，进度计算必须从已选择答案的题目集合开始，不能使用`questionIndex + 1`作为已完成数量。
2. 未选择答案的当前题不计入进度；仅查看、滚动或进入题面不计入进度。
3. 选择答案后，进度应立即反映该题已经形成草稿；如果产品合同要求先保存再计入，则必须在保存成功后计入，并同步更新文案，不能出现进度已前进但仍显示未保存的矛盾状态。
4. 在题目之间前后切换、修改已有答案、刷新和恢复时，进度必须根据同一份答案草稿事实重算，不得重复计数或回退错误。
5. 进度条旁应明确说明分子含义，例如“已作答1/4题”；“第1题/共4题”只表示当前位置，不能代替作答进度。
6. 未完成全部题目时，提交按钮继续遵守现有完整题组合同；不能因为当前题序已到最后一题而伪装成全部完成。
7. Web 和 TUI 如展示该进度，必须消费同一份答案草稿事实；不能一端按题目序号、一端按已作答数量计算。

### 20.4 验收标准

1. 新建四题题组并首次打开第1题，未选择答案时显示`0/4`，进度条为0%。
2. 选择第1题答案后显示`1/4`，进度条前进一次且不重复计数。
3. 进入第2题但不选择答案时仍显示`1/4`，不能因为题目序号变化而前进。
4. 返回第1题修改答案后仍显示`1/4`；刷新或服务端恢复后保持一致。
5. 依次选择四题答案后显示`4/4`，提交按钮才满足完整题组的可提交条件。
6. 未选择答案时页面不显示“已作答”或“已保存”等误导文案；保存状态与答案草稿状态一致。
7. 桌面、平板和手机视口下，进度百分比、题目序号和保存状态不重叠、不截断。
8. 自动化测试覆盖首次打开、选择答案、切题、返回修改、刷新恢复和重复点击；浏览器测试核对真实进度条宽度或可访问值。

## 21. 诊断结果和学习时长对不同回答不产生差异，缺少贯穿全程的学情画像 Agent

### 21.1 已观察事实

1. 负责人在不同诊断回答下重复创建或确认学习路径，页面仍展示几乎相同的全部章节、相同的先修提示和约290分钟预计学习时长。
2. 当前现象无法证明诊断答案已经被正确映射到知识点 Evidence、KnowledgeState、PathEngine 输入和预计时长计算。
3. 页面展示了“诊断画像”和“能力画像修订”，但还不能从页面和运行记录确认：诊断 Agent 是否真实接收诊断结果、是否持续记录后续客观题、代码题和最终实操证据，以及最终总结是否使用了完整学习轨迹。
4. 如果不同且有意义的诊断答案总是得到完全相同的路径和时长，可能存在诊断答案映射、会话草稿、缓存、路径输入或演示数据绑定问题，不能直接把原因归结为“缺少 Agent”。

### 21.2 负责人裁决与目标架构

本问题同时包含“诊断结果没有驱动路径差异”和“学情画像 Agent 全程记录与总结”两个整改方向。

目标流程为：

```text
背景问卷 + 诊断作答
  → 确定性程序生成诊断 Evidence
  → KnowledgeState / mastery / confidence
  → PathEngine 计算合法路径和预计时长
  → 学情画像 Agent 解释初始画像和路径依据
  → 学习过程中的客观题、代码题、实操结果写入正式 Evidence
  → 确定性程序重新计算 KnowledgeState 和路径后缀
  → 学情画像 Agent 更新薄弱点、已掌握点、进步点和未完成点
  → 最终总结使用完整事实快照生成多维学习报告
```

学情画像 Agent 的职责：

- 解释诊断结果和路径原因；
- 根据正式 Evidence 形成可读的薄弱知识点、已掌握知识点和进步说明；
- 记录客观题错误对应的知识点和后续补救情况；
- 记录代码题、最终实操、重试、放弃和带缺口继续事实；
- 在最终总结中组织学习前后对比、掌握情况、未掌握内容、跳过章节和后续建议；
- 输出可展示的结构化画像摘要、依据引用和安全解释。

学情画像 Agent 不得直接修改：

- `mastery`、`confidence` 和 `KnowledgeState` 的程序计算结果；
- PathEngine 的节点、先修关系、活动顺序或预计时长；
- 正式判分结果、Evidence 事实、答案键、Rubric 或隐藏测试；
- 学习者是否通过、是否跳过和是否完成的权威状态。

这些字段必须由确定性程序从正式输入和 Evidence 复算。Agent 负责解释、归纳和呈现，不能用模型意见替代事实底座。

### 21.3 整改要求

1. 先用两个以上具有明显差异的诊断输入，核查诊断答案是否进入正确知识点、选项权重和 Evidence；不能先添加 Agent 来掩盖确定性映射错误。
2. 核查确认路径时是否读取了当前诊断草稿、目标、讲解偏好、Profile revision 和最新 Evidence，而不是复用旧 Session、固定 fixture 或缓存路径。
3. 核查预计时长是否由实际路径节点求和得到；相同的290分钟只能在路径确实相同且节点时长总和相同的情况下出现。
4. 为诊断 Agent 建立结构化输入和输出合同，至少包含`sessionId`、`profileRevision`、`evidenceVersion`、知识点状态摘要、路径摘要、变更原因和来源 Evidence ID。
5. 每次正式客观题、代码题、最终实操、重试、放弃或带缺口继续后，产生可复算的学习事件；画像 Agent 只能消费这些已提交事件，不能读取浏览器临时草稿作为事实。
6. 用户答错客观题后，先由确定性程序识别错误知识点并更新状态，再把错误知识点摘要传给动态题生成和审核链；下一轮题组必须记录目标知识点和题组来源。
7. 最终总结必须同时展示：初始诊断、初始路径、学习前掌握情况、每个知识点的学习结果、客观题和代码题表现、重试与跳过、Evidence 变化、最终路径、未掌握内容和后续建议。
8. 最终总结的数值、状态和路径来源于服务端事实；Agent 生成的文字必须引用对应事实，生成失败时仍显示确定性摘要，不得生成无依据的“已掌握”或“学习成果”。
9. Web 和 TUI 读取同一份画像安全视图；不得一端展示诊断 Agent 结果、另一端展示旧的固定摘要。
10. 画像 Agent 的请求、响应和错误状态必须脱敏保存；不得包含私有答案、hidden tests、Rubric、Token、绝对路径或原始敏感个人信息。

### 21.4 验收标准

1. 构造至少两组诊断答案明显不同的输入，确认诊断 Evidence、KnowledgeState、路径节点、原因代码或预计时长至少产生一项可解释差异；若业务规则确实导致路径相同，必须展示相同的确定性依据，不能只返回相同数字。
2. 相同诊断输入重复运行时，路径和预计时长保持稳定，证明结果不是随机漂移。
3. 诊断提交后的服务端快照能关联诊断 Evidence、KnowledgeState、路径版本和画像 Agent 运行记录。
4. 客观题答错后，错误知识点进入正式 Evidence，下一轮题组目标知识点与错误点绑定，且经过既有 Generator → Hunter → Defender（如触发）→ Judge 链。
5. 代码题失败、重试、放弃或带缺口继续后，画像和最终总结能准确区分“通过、未掌握、暂时跳过、未完成”，不把跳过写成通过。
6. 至少一个学习过程完成后，最终总结能展示学习前后对比、已掌握点、仍需帮助点、跳过节点、题目表现和后续建议，并能追溯到 Evidence ID。
7. 画像 Agent 超时、拒绝或模型关闭时，确定性路径、状态和总结事实仍可用，并明确标记 Agent 解释降级。
8. 自动化测试覆盖诊断差异、相同输入稳定性、旧 Session 恢复、答错后动态题目标绑定、最终总结事实引用和 Agent 失败降级；浏览器测试覆盖真实画像和总结页面。

### 21.5 边界说明

现有设计文档要求“诊断 Agent”解释程序计算出的学情，而不是允许 Agent 直接改写路径事实。此次整改是把该 Agent 从“只解释初始诊断”扩展为“消费全程正式 Evidence、持续更新画像摘要并生成最终学习报告”，不是用模型替换确定性诊断、KnowledgeState 或 PathEngine。

### 21.6 与动态决策更新的联动关系

学情画像 Agent 和最终冲刺计划中的“动态决策更新”属于同一个联动功能包，必须一起设计、一起实现、一起验收，不能只完成其中一项：

```text
用户诊断或活动作答
  → 正式 Evidence 记录知识点表现
  → 确定性程序更新 KnowledgeState
  → 学情画像 Agent 更新薄弱点、掌握点和进步记录
  → 动态决策根据最新错误知识点生成下一轮目标
  → Generator → Hunter → Defender（如触发）→ Judge
  → 新题组或补救活动
  → 新结果再次回写 Evidence、画像和路径
```

联动验收至少要证明：

1. 诊断或客观题错误能够进入画像记录，而不是只改变页面文字；
2. 动态题组的目标知识点来自最新错误 Evidence，而不是固定题组或手工指定；
3. 动态题组审核完成后，学习结果能够再次更新画像和路径；
4. 最终总结同时使用画像更新和动态决策结果，能说明哪些知识点被补救、哪些仍未掌握；
5. 画像 Agent 或动态题生成失败时，确定性状态、固定题保障和降级说明仍然成立；
6. 只完成画像解释、但下一轮题目不随错误知识点变化，不能登记为该联动功能通过；只生成新题、但画像和总结不更新，也不能登记为通过。

### 21.7 新增裁决：全客观多证据诊断与用户自主跳过

负责人现场确认：当前每个核心模块通常只有一道诊断题，单条、单一形式的诊断 Evidence 无法形成章节跳过资格，导致诊断结果主要改变标签和脚手架，不能明显压缩学习路径。

本轮裁决如下：

1. 增加诊断题数量，但诊断题必须全部是客观题，只允许单选题或判断题，不加入问答、编程填空、代码提交等主观作答。
2. 六个核心 Pandas 模块分别覆盖至少两类独立诊断证据：`概念理解`和`代码/应用辨析`。两类题必须是不同题目、不同 `questionId` 和不同诊断 Evidence，不能把同一答案复制成两条证据。
3. 同一模块两类客观诊断题均答对，才生成`diagnosticSkipEligible=true`；只答对一类、答错、跳过或证据冲突时，不提供跳过资格。
4. 获得资格后由学习者逐模块选择“跳过”或“继续学习”，系统不得默认替用户跳过。刷新和服务端恢复后，已生成路径中的选择必须保持一致。
5. 选择跳过普通模块时，省略该模块教学正文和普通课后活动，并从预计学习时长中扣除；选择继续学习时仍保留完整章节。
6. 最终综合实操继续属于全局必做评测。若其所在模块获得并选择诊断跳过，只跳过该节教学和普通练习，最终综合实操不得被绕过。
7. 诊断跳过属于学习路径安排，不等于正式代码实操已经通过。最终画像和总结必须区分“诊断后主动跳过”和“经正式学习活动掌握”。
8. 诊断答案键继续仅保存在服务端私有资产；公共 DTO、DOM、网络响应、日志和前端 bundle 不得包含正确答案。

目标流程：

```text
完成全部客观诊断题
→ 按模块聚合概念理解与代码/应用辨析 Evidence
→ 两类均正确的模块获得可选跳过资格
→ 学习者逐模块选择跳过或继续学习
→ PathEngine 校验资格并生成确定性路径
→ 跳过教学节点，保留最终综合实操
→ 总结区分诊断跳过、正式通过和未掌握
```

本项是`ISSUE_21`的新增子问题，与确定性诊断、路径预计时长、学情画像 Agent 和动态决策更新共同修改，不另建一套旁路画像。

## 22. 代码补全输入输出样例数量和体量不足

### 22.1 已观察事实

1. 当前代码补全活动已有输入输出样例，但样例数量偏少，数据规模也偏小，主要只能说明最基本的成功路径。
2. 小样例不足以覆盖真实代码补全中常见的多行数据、额外列、边界值、重复记录、缺失值、顺序保持和结果规模变化等情况。
3. 这不是要改变题目要求或把题面变复杂，而是测试资产覆盖不足；题面中已经存在的公开小样例必须继续保留，不能删改。
4. 额外的大样例用于服务端测试和权威评测，不应直接展示在题面页面、前端 bundle、网络响应或学习者可下载的公开资源中。

### 22.2 负责人裁决与目标范围

在不改变题目正文、函数签名、`TODO_BEGIN/TODO_END` 编辑范围、公开验收合同和判分规则的前提下，每个代码补全活动至少形成五组输入输出测试样例：

```text
现有公开小样例（保留原样）
+
新增大体量或边界测试样例（服务端测试夹具）
=
每个活动至少五组可复算输入输出样例
```

### 24.7 首页“上次读到”断点恢复修复

记录时间：2026-08-30。

问题与根因：

- 首页原来直接使用 `recoverableSessions[0]`，服务端会话列表按目录名而不是最近保存时间排列；存在多个未完成会话时，卡片可能指向旧会话。
- 原恢复函数只根据Session阶段、Attempt和路径节点推算页面，没有记录学习者在RichLesson中处于“课前简报”还是“正文”，也没有记录正文读到第几站。
- 未提交Attempt虽然比笼统的`stage`更具体，但旧逻辑仅在`stage=activity`时恢复Attempt；阶段字段暂未同步时可能错误返回教学正文。

实际修复：

- `FileLearningSessionRepository.listBoundSnapshots()`按`checkpoints/latest.json`最后修改时间倒序返回，首页无浏览器断点时优先展示最近正式保存的未完成会话。
- Web新增版本化的本地阅读定位记录，只保存安全的站内学习路由、Session ID和时间；案例页、开始页等非学习路由不会覆盖断点。
- RichLesson正文使用语义Hash记录当前模块，例如`#study/walkthrough`；切换正文站点时实时更新，恢复后直接回到同一章节、同一站点。
- 恢复时仍由服务端事实兜底：未提交Attempt优先于浏览器阅读位置；已完成、已跳过、不存在或损坏的节点断点会被拒绝，不允许本地记录修改完成状态、Evidence或路径事实。

验证：

- 阅读定位、首页、RichLesson、Session仓储和Bootstrap定向测试共`91/91`通过；三套TypeScript检查和Vite生产构建通过。
- 真实浏览器执行“第2节正文第3站 → 案例 → 开始 → 上次读到”，最终恢复到同一Session、同一节点和`第3站 · 共4站`，活动模块为`walkthrough`，页面只有一个活动正文卡。
