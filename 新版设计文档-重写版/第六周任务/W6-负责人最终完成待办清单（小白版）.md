## 一、先说结论

现在不是“所有东西都没做完”，也不是“只差点样式”。当前情况是：

- 产品技术主链已经基本闭合；
- 代码、教材、诊断、路径、题目、代码评测、恢复和 Web/TUI 主流程已经存在；
- 但比赛要求的正式评测证据和最终提交材料还没有全部闭合；
- 当前本机终端没有正确绑定合同 Python 环境，因此直接运行完整门禁出现了 `environment_mismatch`，这必须先复验；
- 历史上曾经真实生成过 AI 题，但新版提示词升级后的六章节质量还没有重新形成最终验收证据。

简单说：

> 系统主体已经造出来了，现在要把它在规定环境中完整跑一遍，用数字和材料证明它确实满足比赛要求，然后打包提交。

## 三、第一优先级：修复并确认运行环境

### 为什么先做这个

代码评测器会检查实际 Python 和 pandas 版本。当前终端没有绑定合同环境时，测试会报：

```text
environment_mismatch
```

这表示“评测环境不符合合同”，不是学习者代码答错。

### 必须达到的环境

- Node.js：`v22.23.1`；
- Python：`3.13.7`；
- pandas：`3.0.5`；
- Python 环境名称：`pi-study-py313`；
- `PI_PYTHON_EXECUTABLE`：指向该环境中的 `python.exe`。

### 完成标准

- 能打印以上版本；
- 能在该环境中执行正式代码任务；
- W5 C 的 Node/Python 测试不再因为环境不匹配失败；
- W5 E 的网页代码提交链可以正式判分；
- 全量 `verify` 的失败项被逐项分类，不能把环境错误写成代码通过。

## 四、第二优先级：补齐 W5-D5 评测彩排和 W5-D6 门禁

### W5-D5 是什么

它不是普通测试，而是把比赛正式评测流程完整预演一次：

```text
自动测试
→ 案例评测
→ 幻觉复核
→ 组内盲评
→ 指标计算
→ 报告生成
```

### 必须留下的材料

- `development-20` 彩排报告；
- 彩排版 `metrics.json`；
- 每项指标的分子、分母、排除数和失败原因；
- 幻觉/事实复核表；
- 20 组盲评候选和回避安排；
- 单个案例的人工复核耗时；
- 问题责任表；
- E 的彩排运行日志和命令结果；
- D 的 Agent 轨迹、视频分镜和审核材料；
- 负责人对 V5-1 至 V5-8 的独立复核记录。

### W5-D6 的负责人动作

负责人不能只看“测试大概通过”，需要逐项确认：

- 干净目录 Web 闭环通过；
- TUI 深链和恢复通过；
- 三类学习者路径确实不同且都合法；
- Node 正式提交连续三次结论一致；
- 模型失败、刷新、重启和磁盘失败能恢复或明确降级；
- 敏感资产扫描零命中；
- `development-20` 六环节真的跑完；
- 彩排指标可以人工复算；
- 试用者和盲评安排已经确定。

最后只能签：

```text
W5_GATE=GO
```

或者：

```text
W5_GATE=NO-GO
```

不能用“差不多”“基本通过”代替门禁结论。

## 五、第三优先级：重新验收六节实时 AI 客观题

### 必须证明的流程

每个章节都应符合：

```text
当前章节正式教学正文
→ Generator 生成题目和候选答案
→ Hunter 检查题面、选项、答案、解析和正文依据
→ 有争议或高风险时进入 Defender
→ Judge 裁决
→ 通过后展示 AI 题组
→ 失败、超时或审核不通过时才使用固定题
```

### 需要检查的六件事

1. 六个章节都能生成题，不是只有某一节成功；
2. 题目内容确实来自当前显示的正文；
3. 答案由生成/审核链形成，不是前端硬编码答案冒充；
4. Hunter 和 Judge 能看到审核所需的私有答案视图，但浏览器和普通日志看不到答案；
5. 真实 API 请求、模型响应、审核轨迹和 `LIVE_MODEL` 状态都有证据；
6. 只有失败时才显示“固定题保障”，不能把录制题组写成实时 AI 成功。

### 完成标准

- 新建一份全新的学习会话；
- 运行六个章节；
- 保存每节的题组来源、提示词版本、模型 ID、审核轨迹和结果；
- 对错误答案语义进行人工复核；
- 发现失败时保留失败记录，不删除并改写成 PASS；
- 最终形成一份新的、明确标注 `LIVE_MODEL` 的六章节运行报告。

## 六、第四优先级：执行正式 60 案例评测

### 60 个案例是做什么的

不是让系统演示 60 次，而是用三类不同学习者输入，检查系统是否真的做出合适的路径和难度安排。

### 必须输出的结果

- 60 个案例的逐行运行记录；
- 每个案例的输入哈希和输出哈希；
- 路径是否合法；
- 选择的活动和难度；
- 与 gold 标准是否匹配；
- 失败案例及失败原因；
- 三类画像的分组统计；
- 新的 `evaluationId`。

### 四项关键结果

- 幻觉率 `<5%`；
- 难度适配准确率 `≥85%`；
- 核心知识覆盖率 `≥90%`；
- 路径合法率 `100%`。

最终报告中不能只写“86%”，必须写成类似：

```text
难度适配：553/640 = 86.41%
```

## 七、第五优先级：完成 20 组多 Agent 盲评

盲评的目的，是证明多 Agent 审核确实比单次生成更可靠，而不是只在文档中声称有 Hunter、Defender、Judge。

必须做到：

- 单 Agent 和多 Agent 结果组成配对；
- 评审者看不到“哪一个是多 Agent”；
- 左右顺序随机；
- 生产者不能评价自己的内容；
- 20 组全部收回后才能解盲；
- 保存胜负、严重错误、理由、成本和延迟；
- 负面结果不能删除。

## 八、第六优先级：完成至少 6 人真人试测

每位试用者需要留下匿名化记录：

1. 学习前测；
2. 使用系统学习；
3. 学习后测；
4. 迁移题；
5. 操作阻塞和可用性反馈；
6. 中途退出或未完成记录（如果发生）。

这部分只能说明 Demo 的可用性和趋势，不能夸大成严格的因果实验。
