## 2. Profile revision 3合同


- `contentEstimatedMinutes`存在时必须是正整数。
- 字段缺失时固定解释为`select_one`；revision 2读取结果不得变化。

W4题组型mcq活动使用`fixedQuestionGroupId/supplementalQuestionGroupId/evaluatorRef`引用上述资产；revision 2继续使用既有`subtype/options/evaluatorRef`单题字段，两种形状不能混写。公开题组文件不得含`correctAnswer/explanation/privateAnswerRef`；私有答案文件只能由服务端白名单读取。

- 有效题组为4—6题，阈值固定`Math.ceil(totalCount * 0.75)`。
- `correctCount >= requiredCorrectCount`为`pass`；`1 <= correctCount < requiredCorrectCount`为`partial`；`correctCount === 0`为`fail`。不得由模型或页面解释这些边界。
- 0—3题返回`insufficient`；推进活动游标但不创建Evidence。
- 有效题组`pass/partial/fail`均创建一条`form=selected_response`正式Evidence；Evidence按整组聚合，不逐题创建。
- `pass`立即结束题组；首次`partial/fail/insufficient`推进到同一题组的一次重试游标，第二次非通过结果才结束题组并进入下一活动。第二组`questionId`与第一组不得相交；重试次数由服务端进度保存，调用者不能覆盖。
- 打开阶段不得返回正确答案、解释或私有来源映射；只有正式提交完成后返回`answerReview`安全投影。
- revision 2旧单题继续按原格式读取和判定，不被强制补成4题。
- 每次打开题组都生成新的`attemptId`并把当次题目ID集合保存在服务端Attempt快照；重试不得复用首次Attempt。
- quiz提交必须恰好覆盖Attempt绑定的全部题目，每题出现一次；缺题、重复题、陌生题、题型不匹配或调用者提交题面/正确答案统一作为422语义输入错误。`insufficient`只由服务端形成的题组题量决定，不能由学习者少交答案制造。
- 有效题组Evidence固定`source=deterministic_quiz/form=selected_response/score=correctCount/totalCount`；outcome按`pass/partial/fail`映射为`correct/partial/incorrect`。幂等身份仍为`requestId + attemptId`。
- 动态候选先经程序硬校验；候选1—3题时只能用尚未使用的supplemental题补位。补位后仍不足4题且完整fixed组尚未使用时，整组切换到fixed；fixed已经使用时返回`insufficient`。不得从完整fixed组拆题与动态题混合，也不得跨两次Attempt重复`questionId`。

## 5. activityProgress与会话事务

```ts
type ActivityProgressStatus = "pending" | "in_progress" | "completed" | "insufficient";

interface ActivityProgressEntry {
  activityId: string;
  status: ActivityProgressStatus;
  attemptIds: string[];
  result?: "pass" | "partial" | "fail" | "insufficient";
  quizRetryCount: 0 | 1;
  updatedAt: string;
}

interface NodeActivityProgress {
  nodeId: string;
  card?: {
    cardId: string;
    status: "pending" | "acknowledged";
    acknowledgedAt?: string;
  };
  activities: ActivityProgressEntry[];
}
```

- 会话快照的`activityProgress: NodeActivityProgress[]`是运行游标唯一权威；缺省卡片和活动条目视为`pending`。
- `getNextStep()`先返回首个未确认卡片及其后第一个未终止活动；卡片已经确认时只返回第一个未终止活动。不得固定取`activityIds[0]`。
- `openActivity`可携带服务端刚返回的`acknowledgedCardId`；应用服务在同一事务中确认卡片并打开首个活动。该确认不创建Attempt结果、第三种提交结果或mastery Evidence；重复确认必须幂等，错误卡片ID返回生命周期冲突。
- `pass/partial/fail/insufficient`都推进确定性游标：首次非通过且重试未使用时推进到同一题组重试，`pass`或第二次结果才终止当前活动并推进下一活动；`evaluator_error`完全不推进。
- 路径结构快照不可变；节点状态只由其活动进度确定性投影。
- HTTP和Facade调用者不得提交`evidenceCandidate/knowledgeStates/pathCandidate/activityProgress`。
- 应用服务在一次会话事务内计算并公开Attempt、Evidence（若有）、KnowledgeState、路径后缀、activityProgress、版本和checkpoint；任一步失败不得半写入。
- 最终综合实操得到任何正式学习者判定后可结束会话；总结必须列出`fail/partial/insufficient/unverified`对应的未掌握项。

首次`partial/fail/insufficient`时，进度保持`in_progress`、记录本次结果并把`quizRetryCount`置为1；`pass`或第二次结果才把活动置为`completed`，第二次`insufficient`可使用`status=insufficient`。因此“首个未终止活动”由`status + quizRetryCount`共同判定，不把第一次`insufficient`误当成题组结束。

## 7. Agent审核、缓存与画像

- 低风险题：Generator → 程序硬校验 → 采用；只有硬校验判定高风险才进入Hunter→条件Defender→Judge。
- 动态卡片：Generator→Hunter→条件Defender→Judge，不得跳过。
- 15秒仍未完成则本次绑定固定卡片；60秒内晚到且合格只写私有缓存，超过60秒不采用。
- checkpoint和缓存键必须含`artifactKind`；D运行时生成的私有答案、原始轨迹、晚到产物和缓存位于Profile族`_user`。B封存的固定答案随revision 3私有资产进入active只读副本，不迁入浏览器或Agent上下文。
- 运行时CIDPP关闭。构建期`development-20`原型不得进入学习请求主链。
- 诊断完成和节点完成异步触发画像任务。画像快照状态仅`complete/partial/unverified`；任务状态仅`not_updated/stale/failed`。

## 8. HTTP合同

- 只使用Node内建HTTP，绑定`127.0.0.1:4310`；请求体最大64KiB。
- `GET /api/bootstrap`映射`AppBootstrapFacade.getBootstrap()`；其余每个资源化路由只调用一个Facade短用例。
- 200：同步业务结果，包括pass、fail、fallback、insufficient、path_infeasible和已完成归因的evaluator故障；评测器故障不得伪装成HTTP内部错误。
- 202：异步内容准备或画像任务已接收。
- 400：JSON、Content-Type、请求大小或传输字段形状错误。
- 404：资源不存在。
- 409：版本、幂等或生命周期冲突。
- 422：传输有效但业务语义输入无效。
- 500：内部存储或未分类内部错误。
- 503：服务初始化尚不可用；不得用于模型、评测器或学习者业务失败。

响应和日志只记录安全错误码、requestId和必要计数，不写原始提交、答案、Agent上下文或绝对路径。

## 9. Demo与Vite安全

- `npm run demo`默认数据根`pi-study-helper/.demo-data/`、录制响应、API `127.0.0.1:4310`、Vite `127.0.0.1:5173`。
- 只有显式`PI_STUDY_DATA`才使用其他数据根；默认不得读取开发者历史数据。
- 无active时通过仓储事务激活revision 3；已有相同seal的revision 3幂等复用；其他active revision必须停止并要求负责人批准迁移。
- `npm run demo:live`才读取`OPENAI_MODEL/OPENAI_BASE_URL/OPENAI_API_KEY`；真实Key不写文件、不进入门禁。
- 端口占用直接失败，不漂移、不结束其他进程。API ready后才启动Vite；任一子进程退出或收到信号时关闭同组另一进程。
- Vite根为Web专用目录，公共DTO来自独立contracts层；不得通过URL访问工程fixtures和私有资产。

revision 3 seal固定为`quality/revision-seal.json`。seal自身不进入entries；其他文件按Profile根相对POSIX路径UTF-8字节序排序。普通文件使用原始字节SHA-256；`profile.json`先将`status`规范为`draft`，再按既有`utf8-json-keys-sorted-arrays-preserved-no-whitespace-v1`计算，使active副本只改变生命周期状态而不改变seal。资产树流逐项使用`path\0hashMode\0sha256\0byteLength\n`并取SHA-256。B生成并验证seal，A的仓储在发布前后复算，C只比较仓储返回的revision和tree SHA-256。
