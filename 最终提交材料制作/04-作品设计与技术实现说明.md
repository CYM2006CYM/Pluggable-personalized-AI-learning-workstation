# Pi Study Helper 作品设计与技术实现说明（初稿）

> 多Agent审计链的当前事实、目标修订和案例解释统一参见[《09-多Agent审计链路逻辑与可视化说明》](./09-多Agent审计链路逻辑与可视化说明.md)。

> 适用范围：XH-202630 比赛提交材料。本文描述当前 `pi-study-helper` 的设计边界和实现方式，正式提交前需用最终 Git 提交号、Profile seal、案例和测试报告补齐证据索引。

## 一、作品定位

Pi Study Helper 是一个以 Pandas 数据清洗为示范领域的个性化学习工作台。它把“知识底座”“学习事实”“动态生成”“质量审核”和“代码实操”拆成可替换的模块，通过统一 Facade 同时服务 Web 和 Pi TUI。

系统的关键设计决定是：

- 权威正文、规则、来源、评分和路径事实由版本化 Profile 与确定性程序维护；
- AI 只能在公开安全上下文内生成课前导学、客观题或补救题候选，不能修改掌握度、路径、评分和隐藏评测；
- 多Agent是串行隔离的职责链，而不是把一个模型的回答直接当作最终答案；
- 实时 API、录制响应和固定保障三种来源必须在运行状态中明确区分。

## 二、总体架构

```text
React Web / Pi TUI
        │
        ▼
LearningRuntimeFacade / HTTP Adapter
        │
        ├─ Session 与版本仓储
        ├─ DiagnosticRuntime
        ├─ PathEngine（确定性）
        ├─ QuizActivityRuntime / CodeActivityFacadeAdapter
        ├─ LearnerProfileAgentService
        └─ AdaptiveContentService
                │
                ├─ ProfileAdaptiveContentSourceProvider
                ├─ ModelExecutionPort
                │      ├─ RecordedModelExecutionAdapter（离线）
                │      └─ LiveModelExecutionPort（实时 API）
                ├─ Generator → Safety（确定性）→ Hunter → 条件Defender → Judge
                └─ 私有 checkpoint / cache / trace / AgentRun 仓储
```

前端通过安全 DTO 获取当前会话和当前章节的可展示字段；答案、评分资产、隐藏测试、参考实现、完整系统提示词和 API Key 不进入浏览器 bundle。Web 与 TUI 不各自实现路径和评分，而是消费同一套应用服务事实。

## 三、Profile 资料包与版本控制

### 3.1 资料包内容

Pandas Profile revision 3 包含：

- 学习目标、知识点及先修关系；
- 六个核心知识点的三版本中文 RichLesson 正文；
- canonical rules 和 source claims；
- 全客观诊断题和课后客观题资产；
- 六个代码活动、公开样例、测试合同和评测引用；
- 资料包 manifest、Schema、revision seal和质量文件。

### 3.2 三版本正文选择

开始页调查的 `explanation_preference` 唯一决定版本：

| 调查值 | `LessonVariantId` |
|---|---|
| `step_by_step` | `guided` |
| `concise` | `concise` |
| `example_first` | `practice` |

Python经验和 Pandas 经验用于诊断背景，不参与正文版本选择。旧会话的版本快照不被静默替换；新版本验收必须新建 Session。

### 3.3 Seal与旧数据

启动器和 TypeScript launcher 会根据当前 Profile seal选择数据根目录。旧数据与新资料包不兼容时，系统主动停止并给出 `profile_data_incompatible`，而不是猜测迁移。该机制避免旧会话、旧缓存和新正文混用。

## 四、确定性学习闭环

### 4.1 诊断

诊断题全部是固定客观题，服务端依据 answer key 判分。每一次回答或显式跳过写入草稿，完成后一次性形成 Evidence、KnowledgeState和诊断快照。跳过不是答错，也不自动形成负分证据。

### 4.2 KnowledgeState与画像

KnowledgeState保存知识点状态、掌握度、置信度、证据数量、证据版本和是否具备跳过资格。学情画像 Agent 只接收裁剪后的安全事实，生成面向用户的解释和建议；它不能写入新的分数、阈值、先修关系或路径节点。

### 4.3 路径

PathEngine 读取目标、先修图、KnowledgeState、时间预算和用户跳过选择，生成带版本的路径快照。路径节点的 `available`、`locked`、`skipped`、`completed` 和 `insufficient` 状态由程序转换。用户在合法范围内可以选择是否跳过具备资格的章节；跳过记录会进入最终总结。

### 4.4 活动

每章按“正文→客观题→代码实操”的顺序推进。客观题提交后服务端保存题目、用户答案、逐题复盘和 Evidence；代码提交经过 Node 调度、Python 子进程和测试点聚合，返回测试点通过数量、错误分类和可操作反馈。

## 五、动态内容与多Agent实现

### 5.1 输入安全边界

Generator 只获得：

- 当前 Session 选中的中文教学正文；
- 公开 source summary 与允许引用的 source ID；
- 当前章节安全学情事实；
- 重做时的错题安全复盘和画像补救建议；
- 模型、提示词和活动类型约束。

它看不到 hidden tests、参考答案文件、Rubric 私有字段、宿主绝对路径、API Key或其他章节的私有答案。

### 5.2 Generator合同

客观题模式要求返回 4 至 6 道独立中文单选题，每题包含题干、选项、候选正确答案、解析和来源 ID。课前导学模式只返回结构化 card，不得改变正文、路径、掌握状态或评分。所有输出必须是严格 JSON，不得夹带 Markdown 和解释文本。

### 5.3 审核阶段

**确定性安检工位（Safety）**不是模型Agent，也不调用大模型，而是通过程序规则检查输出Schema、来源绑定、题目ID、题目和选项重复、旧题复用、跨题答案提示、越权字段及敏感信息。未通过时，候选返回Generator定向修复；重复违规则停止AI发布。

**Hunter**从反向角度检查候选是否超出正文、答案是否唯一、解析是否支持结论、题面是否清晰、是否存在错题复用和泄漏风险。Hunter只提交问题、严重度和证据，无权直接要求Generator返修，也无权发布或拒绝候选。

**Defender**用于处理无法由确定性程序直接证明的语义争议和高风险问题，针对Hunter问题逐项承认或反驳。是否触发应由程序路由器按预设规则结合问题类型、`disputed`和风险等级判断，不能完全由Hunter单方面决定。

**Judge**综合正文、候选、安检结论、Hunter问题和Defender辩护，输出 `accepted`、`revise` 或 `rejected`。Judge是唯一最终裁决者，但不能绕过安检的确定性检查，也不能修改正文、路径、判分或隐藏资产。`revise`表示问题可修复，应由流程编排程序生成受控修复要求并让Generator重新生成；`rejected`只用于安全/权威边界冲突、争议未闭合或返修预算耗尽。

### 5.4 重试、缓存和降级

动态内容的缓存键包括内容类型、Profile revision、目标、目标知识点集合、正文版本、个性化/补救上下文、重做轮次、排除题目、模型和提示词版本。只有完整键一致且缓存对象再次通过当前上下文验证时才复用。

当 Generator 超时、API 失败、候选重复不合规、Judge明确拒绝或返修预算耗尽时，服务端返回明确的固定保障或“正文仍可用”状态；页面不得把固定题或录制响应标成实时 AI。当前版本尚未接通Judge `revise` 后的Generator返修回路，现状会将该结果降级；最终版本必须修正并完成真实链路验证。

## 六、代码活动实现

代码补全题的页面由固定 starter code、明确 TODO 区域、题面、公开小样例和下载入口组成。用户只填写允许编辑的区域；服务端保存完整提交但只在受控 Python 环境中运行。

合同环境为 Node `v22.23.1`、npm `10.9.8`、Python `3.13.7`、pandas `3.0.5`。评测器检查版本、工作目录、超时和返回结构，最终以测试点结果和权威输出判断，不依赖浏览器中的 Python。

失败处理：第一次未通过要求重做；第二次仍未通过时提供“修改代码重试”和“放弃并进入下一环节”，放弃会标记本节未掌握并写入总结。评测反馈只暴露公开错误分类和测试点状态，不泄漏隐藏输入、参考实现或完整期望输出。

## 七、Web界面与状态可视化

页面层分为开始页、诊断页、路径页、学习页、活动页和总结页。学习页以“数据清洗实验手册”为视觉方向，正文、课前导学和 Agent流水线分区展示。

Agent流水线使用服务端 AgentRun 事件渲染：每个工位显示角色、状态、耗时、公开摘要、来源和必要指标。运行中的按钮显示当前阶段及已处理秒数；跨章节切换时只显示当前 `nodeId` 对应 run，避免上一章节流水线残留。流水线是结构化执行摘要，不是模型思维链。

动态资源缺失时，页面保留完整权威正文并显示明确状态；不使用空白 fallback冒充教学内容。公共响应只返回当前 Session 选中的正文版本和安全字段。

## 八、持久化与恢复

会话、路径、诊断草稿、Evidence、活动 Attempt、AgentRun和完成总结均按版本写入本地文件仓储。写入采用 requestId 幂等和 sessionVersion 比较，避免刷新或重复点击覆盖新状态。

动态内容内部还保存 checkpoint、cache 和 trace，用于恢复未完成审核链、判断是否可以复用已审核结果和审计阶段顺序。旧缓存不会跨 Profile 版本复用；同一会话的画像和补救上下文变化必须让缓存键失效。

## 九、安全与隐私

- API Key仅存在启动进程内存，不写入项目文件、预检报告或浏览器；
- 浏览器和公开 AgentRun 不包含 hidden tests、reference solution、Rubric私有字段、完整答案或本机绝对路径；
- 公开 CSV 只用于题面和演示，私有评测资产仅由服务端读取；
- Node/Python执行器是比赛MVP的本地受信任测试边界，不宣称生产级恶意代码沙箱；
- 运行目录使用 `.demo-data-<seal>` 隔离，提交包不包含本机学习记录、缓存和 Key；
- 所有指标、截图和案例必须绑定最终提交号、Profile seal和输入哈希。

## 十、部署与运行

比赛方双击 `start-competition-demo.cmd` 后，启动器：

```text
检查 Windows x64 和项目文件
→ 检查或安装合同 Node/Python/pandas
→ 按 package-lock.json 执行 npm ci
→ 清理外部旧 PI_STUDY_DATA
→ 按当前 Profile seal 选择新数据目录
→ 隐藏读取 DeepSeek API Key
→ 执行 npm run demo:live
→ 等待 API 和 5173 页面就绪后打开浏览器
```

实时模式启动标志为：

```text
PI_STUDY_READY mode=live_model ... url=http://127.0.0.1:5173/
```

`npm run demo`仅用于录制响应和离线回归；录制文件中的 `modelId=deepseek-chat`不是实时请求证据。完整步骤见同目录《比赛方部署与启动说明.md》。

## 十一、测试与最终验收

自动测试覆盖领域 Schema、诊断判分、路径重算、缓存隔离、Agent输出合同、HTTP DTO、页面状态、代码评测和安全泄漏。正式提交前还必须执行：

1. 两组以上差异化完整案例；
2. Generator原稿与多Agent终稿配对复核；
3. 幻觉率、难度匹配和核心知识点覆盖率计算；
4. 实时 API 请求、模型响应、审核轨迹和 `LIVE_MODEL` 证据检查；
5. 干净 Windows 环境部署复现；
6. 交付压缩包解压后的密钥、绝对路径、私有资产和版本一致性审计。

未完成项目必须标为 `NOT_RUN`、`OPEN` 或 `IMPLEMENTED_PENDING_FINAL_VERIFY`，不得用目标值或录制响应代替实测。

## 十二、已知限制

- 当前完整示范领域只有 Pandas 数据清洗；
- 多Agent是串行隔离协作，不是并行群体网络；
- 代码执行器适用于比赛 Demo 和受信任测试者，不是生产级沙箱；
- Pyodide公开预览不参与权威判分；
- 实时模型不可用时会进入明确标记的固定保障；
- 当前Judge `revise` 与Generator返修闭环仍待完成，未完成前不得把普通可修复问题的降级描述成Judge最终拒绝；
- 迁移能力来自 Profile 合同设计，不代表第二领域已经完成。
