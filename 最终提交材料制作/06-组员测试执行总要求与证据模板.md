# 组员测试执行总要求与证据模板

> 多Agent阶段、权限和判定口径见[《09-多Agent审计链路逻辑与可视化说明》](./09-多Agent审计链路逻辑与可视化说明.md)，测试不得自行改写 `revise`、`rejected` 或Defender触发条件。

> 用途：给测试、网页、Agent、执行器和材料组提供共同的测试边界。本文只规定必须验证的事实、最低覆盖范围和证据格式；具体用例、数据组合、自动化工具和执行顺序由各组员自行设计。
>
> 本文依据《05-测试集与效果评测方案》《08-XH-202630赛题要求对照表》以及当前 Pi Study Helper 实现整理。它是测试执行要求，不是测试结果报告。没有实际运行的项目必须写 `NOT_RUN`，不能用目标值冒充实测值。

## 一、测试要证明什么

测试最终要回答四个问题：

1. 用户能否从开始页走完诊断、路径、教学、客观题、代码活动、反馈和总结；
2. AI动态内容是否真的读取当前正文并经过完整审核链，而不是把录制题组或固定保障题误称为实时AI；
3. 学情证据是否会改变后续资源、补救建议、路径状态和最终总结；
4. 评委能否在另一台符合合同环境的 Windows 电脑部署，并依据证据复核结论。

比赛材料中的主要证明对象是：作品完整性、技术创新、用户体验和实用价值。三项官方硬指标仍按冻结口径计算：幻觉率 `<5%`、难度匹配 `≥85%`、核心知识覆盖 `≥90%`。这三项必须有分子、分母、排除原因和原始记录。

## 二、组员可以自行决定的内容

组员可以自行决定：

- 具体测试数据、用户画像组合和题目回答顺序；
- 使用手工走查、单元测试、接口测试、Playwright、脚本或混合方式；
- 每条用例的编号、文件组织、截图命名和报告排版；
- 在时间有限时先做哪些抽样，但必须在报告中写清抽样范围和未覆盖项。

组员不能自行改变：

- 正文、Profile、路径、掌握度、代码 Rubric、隐藏测试和标准答案；
- 实时AI、录制响应、固定保障三种来源的定义；
- 本文的必测项目、证据字段和 PASS 判定条件；
- 为了得到 PASS 而删除失败记录、修改标准或重复使用旧证据。

## 三、硬性必测清单

每项都必须有 `PASS`、`FAIL`、`BLOCKED` 或 `NOT_RUN`，不能留空。`BLOCKED` 必须写阻塞原因、责任人和下一步；`NOT_RUN` 必须写未运行原因。

### A. 部署与运行基线

- [ ] 在合同环境中启动：Node.js `22.23.1`、npm `10.9.8`、Python `3.13.7`、pandas `3.0.5`。
- [ ] 新建临时数据目录启动一次，证明不会依赖旧会话或旧缓存。
- [ ] 分别验证 `npm run demo`（录制/离线）和 `npm run demo:live`（实时模型）并记录启动模式。
- [ ] 实时模式必须同时记录 `OPENAI_BASE_URL`、`OPENAI_MODEL` 是否存在，但禁止记录 API Key 内容。
- [ ] 浏览器地址、API 本地端口、启动命令和进程日志互相对应；停止服务后端口释放。
- [ ] 在一台干净或近似干净的 Windows 电脑复现部署，并保存版本检查输出。

**通过条件：**网页能打开不等于实时AI成功。实时AI只有在出现真实请求、模型响应、审核轨迹和 `LIVE_MODEL` 证据时才能标记为 `PASS`。

### B. 六章学习主链

至少覆盖六个 Pandas 章节：读取 CSV、检查 DataFrame 结构、处理缺失值、处理重复订单、规范类型与格式、验证清洗结果。

每章必须验证：

- [ ] 当前 Session 绑定了正确的正文版本和章节；
- [ ] 正文、客观题、代码活动和总结能按设计顺序进入；
- [ ] 客观题确实显示题目和选项，提交后有逐题复盘；
- [ ] 代码活动有完整题面、已有代码骨架、可编辑区域、输入输出样例和提交结果；
- [ ] 活动完成后进入“下一环节”或正确的下一章节，不跳过本章尚未完成的活动；
- [ ] 刷新、关闭再打开、恢复会话后，章节、活动和版本不静默变化。

### C. 诊断、画像与路径

- [ ] 诊断题全部按确定性规则判分，跳过只表示证据不足，不直接扣分；
- [ ] 至少准备高、中、低三类诊断表现，检查路径和预计时间确实有差异；
- [ ] 对达到“两个证据类型以上”的知识模块，验证系统提供“可跳过/继续学习”的选择；
- [ ] 验证用户选择不跳过时仍能学习，选择跳过后路径有明确“已跳过”标记；
- [ ] 验证跳过章节仍可从路径或总结进入回看/重新学习；
- [ ] 客观题错误、代码测试点错误和重做结果都进入 Evidence/学情画像；提问或普通浏览不直接改变掌握度；
- [ ] 最终总结能区分已掌握、进步中、未掌握和跳过，并能追溯到学习证据。

**必留证据：**至少两种不同诊断输入的路径快照、路径原因、节点状态、预计时长、跳过操作和最终画像/总结。

### D. AI课前提醒与客观题生成

每个实时AI场景必须核对以下八个工位的中间记录：

`教学依据 → 学情画像 → Generator → 确定性安检 → Hunter → 条件Defender → Judge → 发布/返修/固定保障`

- [ ] `教学依据`记录当前章节正文、正文版本和允许来源；
- [ ] `学情画像`记录本轮画像或补救上下文的版本和证据引用；
- [ ] `Generator`记录输入摘要、提示词版本、候选输出摘要和模型来源；
- [ ] `确定性安检`记录程序规则检查结果。它不是模型Agent，不调用大模型，负责 Schema、来源、重复、答案泄漏、越权字段和敏感信息检查；
- [ ] `Hunter`记录逐题找错结果、问题类别、严重度、证据和争议标记，但不能直接触发Generator返修；
- [ ] 程序路由器按预设规则判断问题能否由代码直接验证，并结合 `disputed` 和风险等级决定是否触发 `Defender`；无争议时明确记录“未触发”；
- [ ] `Defender`只对需要辩护的争议逐项承认或反驳，不能重写题目；
- [ ] `Judge`记录 `accepted`、`revise` 或 `rejected` 及其依据；`revise`必须进入同一审计运行内的Generator受控返修，不能直接伪装成 `rejected`；
- [ ] Judge授权返修后的候选重新经过安检、Hunter、必要时Defender和Judge，返修预算耗尽后才允许固定保障；
- [ ] `发布`记录最终来源、题数、产物摘要和是否进入固定保障。

客观题必须验证：

- [ ] 六章均能生成 4—6 道独立中文单选题，题干、选项、正确答案和解析完整；
- [ ] 题目知识点来自当前正文，解析能由允许来源支持；
- [ ] 同一章节不同正文版本的题目可以有差异，但不得越出该版本正文；
- [ ] 第一轮答错后，补救题同时看到正文、上一轮错题及解析、学情画像建议；
- [ ] 重做题不复用上一轮题目 ID 或题干，并体现薄弱知识点的重复考察；
- [ ] 真实AI失败、超时、结构重复不合法、Judge明确拒绝或返修预算耗尽时，页面明确显示固定保障，不得显示“实时AI已成功”；
- [ ] Hunter第一次返回 `hunter_schema` 时记录为“审查合同重试”，不得误写成Hunter发现同一内容问题两次；
- [ ] 页面和导出记录区分 `revise` 与 `rejected`，并区分“模型不可用”和“候选未通过审核”。

**实时AI验收证据：**请求时间、模型响应摘要、每个工位的状态/耗时、最终 `resultOrigin`、`runId`、产物哈希和安全导出记录。只看到 `modelId=deepseek-chat` 不足以证明调用了 DeepSeek。

### E. 代码补全与最终实操

- [ ] 题面明确说明任务目标、输入、输出、限制、已有代码、`TODO_BEGIN/TODO_END` 可编辑范围和提交方式；
- [ ] 页面至少展示一组小输入/输出样例，并提供完整 CSV 下载；
- [ ] 每个代码活动至少验证 5 个测试点：已有小样例加上阶段4新增的大样例；
- [ ] 结果显示为“通过数量/总测试点数量”，并逐测试点显示通过、失败或评测器异常；
- [ ] 正确代码、典型错误代码、语法错误、返回结构错误和超时分别测试；
- [ ] 评测器异常不能归因于学习者，也不能生成掌握度证据；
- [ ] 第一次未通过时提供重做；第二次仍未通过时同时提供“修改代码重试”和“放弃并进入下一环节”；
- [ ] 放弃后本章标记未掌握，并在最终总结体现；
- [ ] 隐藏测试、参考答案、Rubric 私有字段和宿主绝对路径不进入浏览器、网络响应、日志或前端 bundle。

### F. 反馈、重试、恢复与总结

- [ ] 首道题尚未作答时进度为 0；选择并提交答案后才增加；
- [ ] “展开全部”和“全部收起”语义正确，单个模块展开/收起互不干扰；
- [ ] Agent等待、正式提交、总结生成和重试都有状态变化与已处理秒数；
- [ ] 发生失败时不出现无限等待、空白页或“活动内容未确认保存”来回跳转；
- [ ] 复盘同时显示原题目、用户答案、正确答案、解析和正文依据；
- [ ] 总结生成期间显示学情画像 Agent 的处理中间状态，完成后再显示完整中文总结；
- [ ] 总结提供返回主菜单、继续学习、重新学习或回看已跳过章节的入口；
- [ ] 页面不出现英文残留、句子截断、路径文字重叠、横纵重复路径或按钮含义相反。

### G. 安全与可审计性

- [ ] 运行记录是追加式的，失败、超时、回退和重试记录不能被覆盖成成功；
- [ ] 安全导出 JSON 能按 `runId`、版本、时间、阶段顺序和哈希复核；
- [ ] DOM、网络、日志、下载文件和构建产物均无 API Key、参考答案、隐藏测试和私有评分资产；
- [ ] 录制响应、固定保障和实时AI在界面、日志和报告中清楚区分；
- [ ] 旧 Profile/旧 Session 的历史快照不因新版本部署而静默变化。

## 四、建议的测试分层

组员可以按自己的实现选择工具，但建议至少分三层：

| 层级 | 目标 | 最低交付 |
|---|---|---|
| 确定性层 | Schema、路径、判分、测试点聚合、权限和版本合同 | 自动测试输出、失败负例和版本信息 |
| 集成层 | Facade、Agent审核链、Node/Python执行器、HTTP和持久化 | 请求/响应、运行轨迹、故障注入和恢复记录 |
| 产品层 | 浏览器完整流程、布局、按钮、状态、读秒和总结 | 屏幕录制或截图、操作步骤、缺陷记录 |

时间不足时可以减少每层的样本数量，但不能删掉某一层，也不能把未执行层写成通过。

## 五、统一证据记录模板

每个测试项至少保存一条记录，可使用 Markdown、JSONL 或表格：

```text
testId: TEST-<模块>-<编号>
title: <中文测试名称>
owner: <执行人>
date: <YYYY-MM-DD>
baseline: <提交号或版本标签>
environment: <Node/Python/pandas/浏览器/操作系统>
mode: <live_model | recorded_response | fixed_fallback | deterministic>
input: <案例、章节、画像、回答或故障注入说明>
steps: <实际操作或命令；可链接到详细记录>
expected: <预期结果>
actual: <实际结果>
status: PASS | FAIL | BLOCKED | NOT_RUN
evidence: <截图、视频、JSON、日志、trace、哈希文件路径>
runId: <如有 Agent 运行>
artifactHash: <如有产物>
failureOwner: <失败归因：学习者/系统/评测器/环境/外部API>
notes: <限制、抽样范围、未覆盖项和后续动作>
```

Agent 流水线记录至少另存以下字段：`runId`、`requestId`、`sessionId`、`profileRevision`、`pathVersion`、`evidenceVersion`、`resultOrigin`、当前阶段、阶段顺序、每阶段状态、耗时、公开摘要、问题类别、裁决和最终产物哈希。

## 六、缺陷归因规则

发现失败后先归因，再决定修复人：

- **学习者错误**：题目和评测器都正确，代码/选项不符合要求；记录反馈，不修改标准；
- **系统缺陷**：题面、状态、路由、保存、Agent调度或展示不符合合同；阻塞对应功能；
- **评测器异常**：执行失败、环境错误、资源不可用；不得计入学习者得分；
- **环境问题**：版本、路径、端口或依赖不符合合同；先记录环境证据；
- **外部模型/API问题**：Key、余额、网络、服务端错误或超时；记录真实失败并验证固定保障。

同一问题不能同时写成“用户答错”和“系统通过”。如果无法归因，状态写 `BLOCKED`，由负责人裁决后再进入正式报告。

## 七、组员最终交付包

每个测试组至少交付：

1. 一份测试范围和用例索引；
2. 一份原始执行记录，保留失败和未运行项；
3. 必测清单逐项状态；
4. 关键截图/录屏/JSON/日志和哈希；
5. 缺陷清单及归因、严重级别、复现步骤和修复建议；
6. 一页中文结论：已通过、未通过、阻塞、未运行、抽样限制和建议是否可演示；
7. 如计算官方指标，附分子、分母、排除原因、脚本版本和原始数据索引。

负责人最终只根据原始证据签发 PASS/NO-GO。组员的“测试完成”表示已按本要求执行并提交证据，不等同于项目已经通过最终交付门禁。
