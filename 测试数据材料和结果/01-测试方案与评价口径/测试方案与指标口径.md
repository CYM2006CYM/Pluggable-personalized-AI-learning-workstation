# 测试方案与指标口径

适用范围：Pi Study Helper 当前 Pandas 数据清洗学习模块。本文说明三类学习者案例、单智能体与多智能体对照评价的执行方法，以及各项指标的统一计算口径。

## 一、测试目的

本轮测试主要回答三个问题。

第一，系统能否根据学习者基础和学习方式的差异，给出难度、脚手架和顺序都合适的学习路径。第二，Generator 生成的内容经过 Safety、Hunter、Defender 和 Judge 后，事实错误、来源缺失和高风险表达是否减少。第三，多 Agent 带来的质量改善是否值得它增加的 Token、调用次数和等待时间。

浏览器负责完成真实学习操作，最终统计以服务端保存的 Session、AgentRun、Attempt、Evidence 和正式评测结果为准。浏览器临时状态、预览结果以及人工填写但没有证据文件的数字不进入统计。

## 二、测试对象与样本构成

本轮保留三类有明显差异的学习画像。

会话一类代表低基础学习者。Python 和 Pandas 基础均选择 `none`，解释偏好选择 `step_by_step`，使用推荐模式。该画像用于观察系统是否主动补充前置知识、降低初始难度并提供更充分的步骤提示。

会话二类代表中等基础、存在局部薄弱点的学习者。Python 和 Pandas 基础均选择 `basic`，解释偏好选择 `example_first`。该画像用于检查系统能否保留薄弱知识点，同时允许已掌握章节进入可选跳过范围。

会话三类代表高基础学习者。Python 和 Pandas 基础均选择 `comfortable`，解释偏好选择 `concise`。该画像用于检查系统能否在保留综合实操的前提下缩短学习路径，并减少不必要的基础讲解。

三个典型会话必须分别创建，不能复用 sessionId、AttemptId、草稿或浏览器缓存。每个会话依次完成背景问卷、诊断、路径生成、学习节点、客观题、代码活动和一次正式提交。代码活动中至少刷新一次页面，用于记录恢复前后的服务端事实是否一致。

为了避免只用“三个会话”作为过小分母，路径完成情况进一步拆成检查点。每个会话设置 10 个检查点，分别对应画像保存、诊断提交、诊断结果生成、路径生成、首个节点进入、教学内容读取、客观题完成、代码活动打开、正式评测提交和提交后下一步生成。三次会话合计 30 个检查点。

恢复测试每个会话设置 4 项断言：sessionId 不变、AttemptId 不变、Evidence ID 及版本不变、恢复后的下一步与服务端记录一致。三次会话共 12 项恢复断言。

## 三、执行前记录

测试开始前先记录测试编号、开始时间、代码版本、Profile revision、模型名称和数据窗口。环境信息由环境采集脚本生成，至少包含 Node、npm、Python、Pandas 和 `PYTHONNOUSERSITE` 的实际值。

测试期间不删除旧数据。新记录通过开始时间和结束时间筛选，旧 Session 和旧 AgentRun 不计入本轮分母。所有原始文件在汇总前计算 SHA-256，证据索引只保存相对文件标识，例如 `raw/agent-runs-window.json`、`raw/session-index.json` 和 `results/observable-metrics.json`，不写入测试机器的盘符或本地绝对目录。

若环境版本不符、模型密钥失效或正式评测器不可用，应保留当次失败记录并停止受影响指标的计算。不能删除失败样本后只统计成功样本。

## 四、三类真实会话的操作方法

每个会话从新的测试账号或新 Session 开始。研究人员先按预设画像填写问卷，再完成诊断题，随后记录系统给出的知识状态、路径版本和首个推荐节点。进入路径后，至少完成一个教学节点和一组客观题。

代码活动打开后，记录 activityId、AttemptId、草稿版本和页面时间。输入一段可识别但尚未提交的代码，刷新页面，检查草稿是否恢复，以及 sessionId、AttemptId 和活动版本是否改变。恢复检查完成后进行正式提交，记录提交请求、评测结果、Evidence ID、Evidence 版本、是否 committed 以及提交后的下一步。

如果 AI 内容生成失败，仍保留对应 AgentRun。若页面进入固定保障内容，则记录 `resultOrigin` 和 `fallbackReasonCode`；固定保障不能算作 AI 成功。若 Hunter 或 Judge 失败，记录失败角色、失败时间和错误码，不人工补写审核结论。

## 五、内容质量与教学适配的测量

### 1. 幻觉率

幻觉率不直接按整段回答判断，而是先把最终展示内容拆成能够单独判断真假的原子事实。例如，“`drop_duplicates()` 默认保留第一条记录”和“调用后会直接修改原 DataFrame”应拆成两条事实。

每条事实记录所属会话、内容版本、原文片段、来源引用和裁决结果。裁决结果限定为“有正式资料支持”“外部事实正确”“幻觉”“证据不足”。只有已经完成裁决的事实进入分母，“幻觉”进入分子，“证据不足”不强行归为幻觉。

单 Agent 和多 Agent 必须比较同一批事实槽位，分母保持一致。若本轮形成 247 条可裁决事实，则两种模式都以 247 为分母。幻觉率计算为：

```text
幻觉率 = 幻觉事实数 / 已裁决事实总数 × 100%
绝对下降 = 单 Agent 幻觉率 - 多 Agent 幻觉率
相对下降 = 绝对下降 / 单 Agent 幻觉率 × 100%
```

没有原子事实记录和裁决证据时，该指标写 `NOT_RUN`。

### 2. 无资料包依赖率和有效溯源率

无资料包依赖率用于判断输出能否仅凭公开正式资料和本轮输入完成核对。逐条检查原子事实，能够直接从公开来源复核的计入分子，需要额外隐藏资料才能判断的不计入。

有效溯源率进一步检查来源是否真实存在、与事实相关、版本一致且哈希可复核。仅写了来源名称但无法定位正文，不算有效溯源。

两项指标均以同一批已裁决事实为分母。比较时报告单 Agent 和多 Agent 的百分点差，不用“看起来引用更多”代替计算。

### 3. 严重错误数

严重错误包括会改变学习者结论的错误事实、会产生错误结果的代码建议、泄露答案或私有评测信息的内容，以及违反既定安全边界的指令。每条错误必须保存原文、错误类型、影响和对应版本。

分别统计 Generator 初稿和多 Agent 终稿中的严重错误数，并计算：

```text
错误消除数 = 初稿严重错误数 - 终稿严重错误数
错误消除率 = 错误消除数 / 初稿严重错误数 × 100%
```

初稿没有严重错误时，错误消除率写 `N/A`，不能写成 100%。

### 4. 事实正确性、教学清晰度和安全性

三项采用 1 至 5 分的固定量表。事实正确性重点检查结论是否与正式资料和可执行结果一致；教学清晰度重点检查步骤是否完整、语言是否有歧义、学习者能否照着完成；安全性重点检查来源、隐私、答案隔离和越权边界。

评分前先固定各分值含义。例如，5 分表示没有发现实质问题，4 分表示存在轻微表达问题但不影响使用，3 分表示需要局部修改，2 分表示存在明显错误，1 分表示内容不可用。单 Agent 初稿和多 Agent 终稿使用同一量表，最终报告平均分和分差。

### 5. 难度与脚手架适配

从三次会话的实际路径中提取节点难度和脚手架等级，与正式 gold 逐节点比对。每条记录至少包含会话画像、节点 ID、实际难度、期望难度、实际脚手架、允许脚手架范围和判定结果。

难度命中和脚手架命中分别计算。联合准确率只有在同一节点两项都命中时才进入分子。三者使用同一节点总数作为分母：

```text
难度适配准确率 = 难度命中节点数 / 比对节点总数 × 100%
脚手架准确率 = 脚手架命中节点数 / 比对节点总数 × 100%
联合准确率 = 两项同时命中节点数 / 比对节点总数 × 100%
```

路径生成失败的节点仍保留在分母中，并记录为未命中，避免只统计成功生成的路径。

## 六、学习路径与知识覆盖的测量

### 1. 路径合法率

对每条实际路径依次检查必需节点是否出现、前置节点顺序是否正确、活动是否绑定到正确知识点、跳过行为是否具备资格，以及总路径是否超出预算。每个约束形成一条检查记录。

路径合法率按约束检查计算，而不是只按三条路径计算。模拟数据可采用 180 个路径约束检查；真实结果则使用本轮实际产生的检查总数。公式为：

```text
路径合法率 = 通过的路径约束数 / 路径约束检查总数 × 100%
```

### 2. 核心知识点覆盖率

Profile 中正式核心知识点数量固定为 6，因此这一指标的分母必须保持 6。

每个知识点分别检查六类证据：诊断题、教学正文、可评分活动、代码应用、固定保障内容和参考实现。六类全部存在且绑定正确，才认定该知识点被完整覆盖。

```text
核心知识点覆盖率 = 六类证据齐全的知识点数 / 6 × 100%
```

### 3. 路径完成率

三次会话共设置 30 个流程检查点。每个检查点必须能由 Session、Attempt、Evidence 或页面操作记录确认。路径完成率计算为完成检查点数除以 30。某个会话中途失败时，已完成检查点保留，后续未完成检查点计入分母但不计入分子。

### 4. 刷新恢复一致率

每个会话完成一次刷新恢复，并检查 sessionId、AttemptId、Evidence ID/版本和下一步，共 4 项断言。三次会话合计 12 项。每项逐一比较刷新前后的值，全部保存到恢复记录中。

```text
刷新恢复一致率 = 一致断言数 / 12 × 100%
```

## 七、单 Agent 与多 Agent 的配对方法

单 Agent 指只运行 Generator 并直接取得初稿，不经过 Safety、Hunter、Defender 和 Judge。多 Agent 指使用同一份 Generator 初稿，继续经过完整协同审核链后得到终稿。多 Agent 不能重新生成另一份初稿，否则两者不再是有效配对。

每对样本必须绑定相同的输入哈希、画像版本、模型、提示版本和生成参数。保存内容时分别标记 `single-agent-draft` 和 `multi-agent-final`，同时保留二者的内容哈希。

每对样本至少比较幻觉率、无资料包依赖率、有效溯源率、严重错误数、事实正确性分、教学清晰度分和安全分。比例指标报告百分点差；错误数报告消除数和消除率；评分报告平均分差。

单 Agent 没有协同审核链，因此其审核耗时记为 `0.00 ms`。Schema 解析、输出整理和发布属于端到端开销，不计入协同审核耗时。如果实际单 Agent 流程也调用了 Safety，则该运行不能再按本方案的“纯 Generator 基线”统计，必须单独标记。

如果系统没有保存 Generator 初稿，或不能保证终稿来自同一初稿，则单 Agent 与多 Agent 的质量比较写 `NOT_RUN`，不能使用不同时间生成的两份内容代替配对样本。

## 八、模型调用与 Token 的测量

输入 Token 和输出 Token 只读取模型供应商响应中的正式 usage 字段。Generator、Hunter、Defender 和 Judge 分角色记录，重试作为新的调用单独计数。Safety 如果是本地确定性检查，不计模型调用，也不产生 Token。

```text
输入 Token = 所有实际模型调用的 inputTokens 之和
输出 Token = 所有实际模型调用的 outputTokens 之和
总 Token = 输入 Token + 输出 Token
模型调用次数 = 实际完成或返回错误的模型请求总数
```

单 Agent 通常只有 Generator 调用，多 Agent 的调用数由 Hunter、Judge、条件触发的 Defender 以及重试共同决定。因此 Token 倍率和调用次数倍率不应被预设为相同，也不应固定为整数倍。缺少 usage 字段时，Token 指标写 `NOT_RUN`，不能按字符数换算。

## 九、耗时性能的测量

所有耗时直接读取 AgentRun 的时间字段或阶段 `durationMs`，不使用人工计时替代。每项保留单次样本，同时报告平均值、P50 和 P95。

Generator 耗时从 Generator 请求开始计算到初稿可用。单 Agent 和多 Agent 都有该项，但可能因输入上下文不同而产生差异。

审核耗时为 Safety、Hunter、实际触发的 Defender 和 Judge 阶段耗时之和。单 Agent 基线不经过协同审核链，因此审核耗时为 `0.00 ms`。Defender 被跳过时不补写虚拟耗时。

端到端耗时从内容请求开始计算到最终结果发布。它应包含 Generator、协同审核、阶段编排、结果解析和发布，因此多 Agent 的端到端耗时通常大于 Generator 与审核耗时之和。正式超时上限为 150,000 ms；超过上限的样本按超时记录，不能从耗时统计中删除。

正式复核时同时检查：

```text
单 Agent 端到端耗时 >= 单 Agent Generator 耗时
多 Agent 端到端耗时 >= 多 Agent Generator 耗时 + 多 Agent 审核耗时
```

若第二项不成立，应检查阶段时间是否重叠。只有确认系统确实并行执行相关阶段时，才能按时间轴去重，不能简单相加。

## 十、协同审核与运行可靠性

安检退回率以进入 Safety 的候选为分母，以被 Safety 明确退回的候选为分子。模型请求失败不算安检退回。

Hunter 发现问题率以进入 Hunter 的运行数为分母，以 `issue-count` 大于 0 的运行数为分子。Hunter 因供应商错误未返回可验证结论时记为失败样本，不归入“未发现问题”。

Defender 触发率以进入协同审核的运行数为分母，以 Defender 实际执行的运行数为分子。状态为 `skipped` 表示条件未满足，不计入分子。

Judge 接受率以进入 Judge 的运行数为分母，以 `decision=accepted` 的运行数为分子。Judge 调用失败或结果无法解析均不计入接受数。

固定保障降级率以全部内容请求为分母，以 `resultOrigin=profile_fixed` 或存在明确固定保障原因码的请求为分子。固定保障可以保证页面继续工作，但不算实时 AI 发布成功。

缓存命中率只有在运行轨迹明确记录缓存请求和命中状态时才计算。题目重复率需要收集完整题目 ID 或规范化后的题目文本；只有题量摘要时不能计算。阶段记录完整率检查 source、profile、generator、safety、hunter、defender、judge 和 publish 八个角色是否都有明确终态。

## 十一、结果计算与异常处理

所有百分比保留两位小数，并同时报告分子和分母。分母为零时写 `N/A`；没有执行对应测试时写 `NOT_RUN`；已执行但证据不完整时写 `BLOCKED`。这三种状态不能写成 0%。

同一个请求发生重试时，各次 AgentRun 均保留。统计成功率时以请求为单位，统计调用次数和耗时时以实际调用为单位。因网络、余额、供应商或解析错误导致的失败必须保留原始错误码；若日志只提供 `provider_error`，报告中应明确说明无法进一步区分原因。

最终量化文档中的每个数值都要能够回到一份过程性记录。汇总完成后进行三项复核：分子不得大于分母；百分比必须能由分子和分母重新计算；单 Agent 与多 Agent 的配对指标必须使用相同分母和同一初稿来源。任一项不满足时，相关指标不得发布为有效结果。

## 十二、交付材料

最终保留三类材料：三次会话的过程性运行证据、量化测试数据和本测试方案。过程性证据包含时间窗口、环境记录、AgentRun 摘要、Session 文件索引、Attempt、Evidence、正式评测结果及逐文件 SHA-256。量化测试数据只引用相对证据标识，不记录测试机器的本地目录。

模拟数据仅用于检查表格、公式和展示方式，与真实结果分开保存。真实会话没有产生的指标继续标记 `NOT_RUN` 或 `N/A`，不能用模拟数字回填。
