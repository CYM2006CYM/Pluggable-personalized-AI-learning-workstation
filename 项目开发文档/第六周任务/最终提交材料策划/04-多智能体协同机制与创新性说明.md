# 多智能体协同机制与创新性说明

> 用途：技术创新说明、PPT技术页、演示旁白和答辩问答母稿

## 1. 为什么需要多智能体

在专业学习场景中，单个大模型同时负责“生成内容、检查自己、决定是否正确”存在明显利益冲突。它容易沿用原先的错误，也可能给出流畅但缺少来源、难度不匹配或答案不唯一的题目。

Pi Study Helper把任务拆成不同责任：有人生成，有人专门挑错，有人在争议发生时回应，有人依据双方材料做最终裁决。与此同时，正确答案比较、路径约束和代码测试仍由程序掌握。系统追求的不是Agent数量，而是责任分离、相互制约和结果可复核。

## 2. 角色合同

| 角色 | 允许读取 | 必须输出 | 禁止行为 |
|---|---|---|---|
| 学情画像Agent | 脱敏学习事件、KnowledgeState、路径摘要、Evidence ID | 薄弱点、进步点、依据引用、总结建议 | 修改掌握度、判分或路径 |
| Generator | 当前选中正文、canonical rules、source claims、目标知识点、难度和已用题摘要 | 完整候选题、答案、解释、规则和来源引用 | 读取hidden tests、私有参考答案或其他正文版本 |
| Hunter | 候选题、允许规则和来源摘要 | 具体问题、严重度、证据和建议 | 笼统评价或直接修改正式状态 |
| Defender | 候选题和Hunter逐项质疑 | 承认、反驳或修订建议及依据 | 忽略质疑、引入新无来源事实 |
| Judge | 候选题、Hunter报告、可选Defender回应、硬校验结果 | 逐项裁决、最终内容、接受/修订/拒绝 | 绕过程序Schema和权威规则 |
| 学习决策Agent | 程序生成的路径、原因码和安全画像摘要 | 面向用户的安排解释 | 改写PathEngine结果 |

## 3. 结构化协同链

### 3.1 正常链路

```text
生成请求
→ Generator候选
→ 程序硬校验
→ Hunter风险检查
→ [有实质争议] Defender回应
→ Judge裁决
→ 程序最终校验
→ 保存审核题组与安全轨迹
→ 展示给学习者
```

Defender是条件触发角色。没有实质争议时不额外调用，以降低时延和成本；存在事实、答案、歧义、难度或来源争议时必须进入辩护和裁决。

### 3.2 失败链路

```text
模型未配置 / 超时 / 拒绝 / 非法JSON
→ 一次受约束格式修复（仅适用于可修复输出）
→ 仍失败或内容风险未消除
→ 固定保障题
→ 页面明确显示降级原因和来源
```

任何未完成审核的Generator原稿都不能作为正式题组。录制响应只用于离线回归和演示稳定性，不能被标记为实时模型调用。

## 4. 高风险判定

建议把以下情况定义为必须触发严格审核或拒绝：

- 正确答案与正文规则、代码行为或来源相冲突；
- 多个选项同时正确、无正确选项或答案无法从题面判断；
- 题目超出当前章节和学习者已知先修范围；
- 对缺失值、重复键、日期解析等边界作绝对化陈述；
- 代码示例无法运行、改变题目禁止改变的列或破坏输入；
- 引用不存在的source claim或越界source anchor；
- 输出包含hidden tests、Rubric、参考实现、密钥或内部提示词；
- 重试题与已使用题目实质重复，无法针对最新错误知识点。

## 5. 题目答案如何形成

AI动态题的正确答案不是人工在页面代码里临时写死，也不是由Judge凭空决定。完整过程是：

1. Generator依据正文规则生成题目、选项、建议答案和解释；
2. 程序检查答案是否属于选项、题型是否合法、引用是否存在；
3. Hunter检查建议答案是否与正文、来源和代码语义一致；
4. 发生争议时，Defender逐项说明原答案是否成立或应如何修订；
5. Judge根据候选内容、质疑、辩护和硬规则形成最终审核答案；
6. 程序再次校验并冻结题组哈希；
7. 学习者提交后，程序只和该冻结答案比较，不再临时调用模型判对错。

这种做法同时保留AI生成能力和判分稳定性，避免同一个答案今天判对、明天判错。

## 6. 与简单API串联的区别

| 简单API串联 | Pi Study Helper设计 |
|---|---|
| 多个调用使用相似提示词 | 每个Agent有明确输入、输出、权限和禁止项 |
| 自由文本互传 | 使用结构化合同和Schema验证 |
| 每轮都调用全部Agent | Defender按争议条件触发 |
| 最后一个模型说了算 | Judge仍受Profile规则和程序硬校验约束 |
| 失败后展示半成品 | 未审核内容拒绝，切换到固定保障资源 |
| 看不到执行依据 | 保存安全轨迹、来源ID、哈希和裁决摘要 |
| 路径和判分也交给模型 | 路径、Evidence和判分由确定性程序负责 |

## 7. 可视化设计

协同过程在页面上应表现为一条实时状态线，而不是暴露模型内部推理：

```text
Generator  已完成  7.8秒  生成5道候选题
Hunter     已完成  5.1秒  发现1项答案歧义
Defender   已完成  3.6秒  接受质疑并提出修订
Judge      已完成  4.4秒  修订后通过
结果来源    实时AI审核题组
```

用户可以展开查看问题类别、裁决摘要和来源，但不能看到系统提示词、私有思维过程或隐藏评测资产。等待期间按钮显示当前阶段和累计秒数，避免用户误判网页卡死。

## 8. 如何证明多智能体有用

### 8.1 公平对照

每个样本只生成一次原稿：

```text
同一Generator原稿
├─ A：不经过审核的原稿
└─ B：Hunter → 可选Defender → Judge后的终稿
```

盲评人员不知道A/B来源，分别评价事实准确、答案唯一性、难度匹配、清晰度、来源充分性和泄漏风险。这样测到的是审核链增益，而不是两次随机生成差异。

### 8.2 建议报告字段

- 样本总数和可判定样本数；
- 原稿与终稿平均分；
- 终稿胜/平/负数量；
- Hunter发现的问题总数及分类；
- Defender触发率；
- Judge接受、修订和拒绝比例；
- 修复后的事实错误数和引入的新错误数；
- 每个样本的Profile revision、提示词版本、模型ID和哈希。

最终结果格式：

```text
配对样本：【待填】
终稿胜/平/负：【待填】
事实错误变化：【待填】
答案歧义变化：【待填】
证据索引：【待填】
```

## 9. 创新边界

- 当前实现是SDK能力范围内的串行隔离协作，不宣传并行Agent群体网络；
- Agent安全轨迹是结构化执行摘要，不是模型思维链；
- Profile权威内容与固定保障题不等于“没有AI”，而是为实时生成提供边界和故障恢复；
- 录制响应用于回归，只有真实API请求和响应才能计为`LIVE_MODEL`运行；
- 学情画像Agent提供解释和建议，不能覆盖确定性Evidence、KnowledgeState和PathEngine。

## 10. 答辩简答口径

**为什么不让一个模型完成全部工作？**
因为生成者自审容易遗漏同源错误。职责隔离使质疑和裁决具有不同目标，并能保存每一步证据。

**为什么还需要固定题和固定正文？**
专业教学需要可追溯底座，模型也可能超时或失败。固定资产用于权威边界和可靠降级，实时AI负责围绕学习者状态生成题目、提示和解释。

**Judge是不是仍可能出错？**
可能。因此Judge不能越过Schema、来源、知识规则和程序校验，最终还通过正式幻觉率与盲评验证，而不是把Agent名字当作正确性证明。

**你们如何证明个性化不是换皮？**
比较差异化案例的Evidence、KnowledgeState、跳过选择、路径节点、正文版本、题组目标、脚手架和最终总结；每项差异都能回溯到输入和学习事件。
