# Pi Study Helper 作品设计与实现具体方案

> 文档用途：响应赛题“设计与实现方案文档”要求
> 编写原则：明确需求、架构、核心合同、运行链路、安全边界、测试方法和当前状态
> 状态：提交候选草案；未取得正式证据的功能和指标不得改写为已通过

## 1. 设计目标

作品选择“Pandas数据清洗职业技能学习”作为垂直领域，目标是构建一个能够诊断学习者、生成和匹配个性化资源、审核专业内容、执行客观题和代码评测，并根据学习证据动态调整后续安排的完整系统。

系统设计同时满足五个约束：

1. **专业可靠**：知识、来源、正确答案、测试和Rubric具有明确权威边界；
2. **个性化**：不同学习者在路径、讲解版本、练习重点、脚手架和补救内容上形成可解释差异；
3. **多智能体协同**：不同Agent职责明确，通过结构化中间产物完成生成、质疑、辩护和裁决；
4. **可复算**：路径、Evidence、KnowledgeState和判分由确定性程序生成，能够重复验证；
5. **可降级**：模型、磁盘、网络或单个Agent失败时不把不合格内容展示给学习者，关键学习链仍可继续或明确阻塞。

## 2. 总体架构

```text
┌──────────────────────────────────────────────────────┐
│ 交互层：React Web / Pi TUI                           │
│ 诊断、画像、路径、教学、客观题、代码活动、总结       │
└──────────────────────┬───────────────────────────────┘
                       │ 公共应用用例与安全DTO
┌──────────────────────▼───────────────────────────────┐
│ 应用编排层                                            │
│ Session / Diagnosis / Lesson / Quiz / Activity       │
│ Evidence / Learner Profile / Recovery / Summary      │
└──────────────┬───────────────────────┬───────────────┘
               │                       │
┌──────────────▼─────────────┐ ┌───────▼───────────────┐
│ 确定性领域核心              │ │ 多智能体编排           │
│ Schema、路径、状态、判分     │ │ 生成、质疑、辩护、裁决 │
│ 版本、权限、降级选择         │ │ 画像解释、路径解释      │
└──────────────┬─────────────┘ └───────┬───────────────┘
               │                       │
┌──────────────▼───────────────────────▼───────────────┐
│ 数据与资产层                                          │
│ Profile、Session、Evidence、Agent Trace、测试与日志   │
└──────────────────────────────────────────────────────┘
```

React Web和Pi TUI共享同一服务端事实，不分别实现两套路径或判分逻辑。Web负责代码编辑、数据预览和可视化学习流程；TUI保留资料包管理和文字学习入口。

## 3. Profile领域资料包

### 3.1 资料包职责

Profile是领域知识和教学资产的唯一清单。Pandas Profile集中声明：

- 领域身份、revision、seal和能力标志；
- 六个核心知识点及先修关系；
- 六节三版本中文教学正文；
- 来源、事实断言和许可证；
- 诊断题、学习后题组和固定保障题；
- 代码活动、输入数据、公开测试、隐藏测试和Rubric；
- 目标、活动顺序、时长和降级策略。

所有ID引用必须闭合，先修图必须无环，资料包路径不得逃逸，active revision必须通过Schema、来源和seal校验。Agent不能修改Profile中的权威规则、隐藏测试和参考结果。

### 3.2 RichLesson教学资产

六个Pandas章节分别保存三种版本：

| 开始页讲解偏好 | 绑定版本 | 教学侧重点 |
|---|---|---|
| 逐步讲解 | `guided` | 建立直觉，逐层解释，强调反例和常见误区 |
| 重点速览 | `concise` | 聚焦关键规则、最小正确步骤和边界 |
| 案例优先 | `practice` | 从数据任务出发，在实践中回扣概念 |

每套正文由类型化内容块组成，浏览器不解析任意Markdown。会话确认路径时选择并快照一套正文，公共DTO只返回该版本，避免将全部教学资产发送到浏览器。旧会话保留原快照，不静默更换教材。

## 4. 学情诊断、证据和路径

### 4.1 诊断输入

开始阶段收集目标、Python/Pandas经验和三种讲解偏好，不要求用户在诊断前选择可用学习时长。之后使用13道全客观题建立初始证据：六个核心模块分别具有概念理解与代码/应用辨析证据，另有必要的基础证据。

### 4.2 Evidence与KnowledgeState

正式诊断、客观题、代码活动、最终实操、重试和放弃均通过服务端正式提交生成Evidence。Evidence至少绑定会话、知识点、活动、结果、版本和来源。系统依据证据确定性计算：

- `mastery`：当前掌握程度；
- `confidence`：结论可信程度；
- `KnowledgeState`：未验证、需学习、学习中、已掌握等状态；
- `skipEligible`：是否具备自主跳过条件。

Agent只读取安全摘要并解释这些事实，不能直接写入掌握度、修改正确答案或强制改变路径。

### 4.3 路径生成

PathEngine执行以下步骤：

1. 读取当前Profile、目标、诊断Evidence和KnowledgeState；
2. 按知识先修图计算必须节点；
3. 应用安全跳过规则和最终目标约束；
4. 生成稳定排序的候选路径；
5. 对可跳过章节让用户选择保留或跳过；
6. 对最终路径节点的`estimatedMinutes`求和，得到预计学习时长；
7. 生成结构化原因码，供学习决策Agent转成中文解释。

同一输入、Profile revision和规则版本必须产生同一结果。Agent可以解释路径，但不能越过先修规则或改变路径唯一事实。

## 5. 多智能体协同设计

### 5.1 角色分工

系统至少包含赛题要求的三个职责明确Agent，实际设计包括学情画像、Generator、Hunter、Defender、Judge和学习决策等角色。每个角色使用独立上下文和类型化输入输出，避免共享隐式聊天历史造成职责污染。

### 5.2 动态题生成审核链

```text
当前章节RichLesson + canonical rules + source claims
+ 最新KnowledgeState + 错误知识点 + 已用题目摘要
                         ↓
                  Generator生成候选题
                         ↓
             程序Schema与硬规则预校验
                         ↓
            Hunter检查事实、难度、歧义、答案
                         ↓
             有实质争议时Defender逐项回应
                         ↓
                  Judge接受/修订/拒绝
                         ↓
               程序执行最终结构校验
                   ↙                 ↘
             审核题组              固定保障题
```

Generator必须输出完整题干、选项、唯一正确答案、正文依据、目标知识点、难度和来源锚点。Hunter不能只给笼统意见，必须指出问题位置、类型、证据和建议。Defender对每项质疑选择承认、反驳或提出修订。Judge输出逐项裁决、最终题目和风险结论。

程序负责检查题数、题型、选项唯一性、答案可达性、知识点引用、来源锚点和重复题。任何Agent失败、超时、输出解析失败或Judge拒绝，都不能直接展示Generator原稿，而应切换到固定保障题或明确返回不可用。

### 5.3 学情画像Agent和动态决策

画像Agent读取脱敏学习事件、KnowledgeState摘要、路径摘要、变化原因和Evidence ID，输出：

- 当前已掌握和仍薄弱的知识点；
- 学习前后变化和进步点；
- 错误类型、重试和提示使用情况；
- 主动跳过、未掌握后继续和未完成状态；
- 与事实对应的Evidence引用；
- 面向学习者的总结和下一步建议。

客观题失败后，确定性程序先识别错误知识点并更新事实，再将错误知识点作为下一轮题组的主要目标。新题组仍需覆盖当前章节核心规则并避免与已用题目重复。画像Agent失败时保留确定性摘要，不阻塞判分与路径。

### 5.4 Agent协同可视化和中间数据

页面与案例材料只展示安全投影：

- `generationRunId`；
- Agent角色与实际执行顺序；
- 阶段状态、开始时间、结束时间和耗时；
- Hunter问题类别和摘要；
- Defender是否触发及回应摘要；
- Judge结论、修订摘要和风险等级；
- source claim ID、题组哈希和结果来源；
- 实时模型、录制响应或固定保障的明确标识。

不展示系统提示词、思维链、API Key、私有答案、隐藏测试、Rubric、参考实现和未经脱敏的学习者数据。

## 6. 学习活动和判分

### 6.1 客观题

AI生成单选/判断候选题及其答案，经过审核后形成题组。学习者提交时，程序比较审核版本中的正确答案并生成复盘。复盘至少显示原题题干、学习者答案、正确答案、正文依据和对应知识点。

第一次未达标时提供新题组重做；再次未达标时同时提供“用新题组重做”和“带缺口继续”。后者必须保留未掌握事实，并在最终总结中体现。

### 6.2 代码补全

代码补全以完整函数或程序骨架呈现，仅允许学习者在明确的`TODO_BEGIN`与`TODO_END`之间补充关键逻辑。题面说明输入DataFrame、输出要求、必须保留的列、边界条件、作答方式和判分方式，并提供公开CSV输入/输出样例或下载入口。

首次失败必须允许修改重试；再次失败时提供“修改代码重试”和“放弃并继续”两个选项。放弃不会伪装为掌握。

### 6.3 最终独立实操

正式提交接口使用Node/Python权威评测，运行公开测试、隐藏测试和确定性Rubric。六个代码活动各维护五组输入输出夹具：保留原公开小样例，另有私有、大样例和边界样例。页面按“通过数量/总测试点数量”显示总体结果，并为允许公开的测试点显示状态、输入摘要、期望输出摘要、实际输出摘要和错误类型。

Pyodide关闭，不产生Attempt、Evidence、mastery或路径更新，也不作为双后端通过证据。

## 7. 状态、恢复和故障处理

### 7.1 会话一致性

会话快照绑定Profile revision、正文版本、路径版本、活动版本和生成运行ID。刷新、重启和从服务端恢复后，应恢复相同的路径、正文、答题草稿和活动游标。重复提交必须幂等处理；版本冲突明确提示，不静默覆盖。

### 7.2 用户等待反馈

调用Agent或确认路径等长操作期间，按钮显示当前阶段和已处理秒数，例如：

```text
正在生成候选题（8秒）
正在检查事实与答案（16秒）
正在完成裁决（23秒）
```

按钮进入不可重复提交状态，同时保留可访问的状态文本。用户应能区分正常处理、超时、失败和固定题降级，不能误以为页面卡死。

### 7.3 降级策略

| 故障 | 行为 |
|---|---|
| 实时模型未配置或请求失败 | 使用固定保障题/确定性摘要，并标记来源 |
| Generator格式错误 | 一次受约束修复；仍失败则降级 |
| Hunter/Defender/Judge失败 | 不展示未完成审核的动态内容，按合同降级 |
| 画像Agent失败 | 保留程序生成的事实画像，不阻塞学习 |
| 磁盘保存失败 | 不前进游标，提示重试，防止假成功 |
| 版本冲突 | 返回明确冲突状态，要求恢复或重新进入 |
| 代码运行超时或输出洪泛 | 终止进程树，限制输出并清理临时目录 |

## 8. 安全、隐私和合规

### 8.1 最小数据原则

系统不要求真实姓名等不必要身份信息。案例和日志使用脱敏学习者ID。真实API Key仅通过本地环境变量提供，不写入仓库、Profile、Session、日志、截图或前端bundle。

### 8.2 资产隔离

公开教学资产、公开样例和安全DTO可以进入浏览器；正确答案按活动阶段控制可见；hidden tests、reference solution、私有Rubric细节、私有期望输出和Agent内部上下文只保留在服务端。

### 8.3 代码执行边界

Node/Python评测实现超时、输出限制、进程树终止、临时目录清理和能力标志验证，但定位为本地受信任测试者的MVP执行器，不宣传为生产级恶意代码沙箱。

### 8.4 来源与许可证

专业事实通过source claims和source anchors绑定资料包来源；所有数据集登记来源、用途和许可证或自建说明。最终提交前扫描绝对路径、密钥、个人信息、隐藏评测资产和未授权材料。

## 9. 测试与效果评测方案

### 9.1 工程正确性

测试覆盖Schema正反例、Profile seal、诊断映射、KnowledgeState、路径不变量、偏好版本选择、会话恢复、Agent路由、题组生成与降级、代码判分、重试、幂等、磁盘失败、版本冲突和泄漏扫描。

### 9.2 赛题效果指标

| 指标 | 计算方法 | 目标 |
|---|---|---|
| 专业知识幻觉率 | 被专家判为错误或杜撰的原子事实数/全部已判定原子事实数 | `<5%` |
| 难度匹配准确率 | 资源难度/脚手架落入gold可接受集合的案例数/可判定案例数 | `≥85%` |
| 核心知识点覆盖率 | 满足requiredEvidence的核心知识点数/核心知识点总数 | `≥90%` |
| 多Agent审核增益 | 同一Generator原稿与审核终稿的20组配对盲评 | 以真实结果报告 |
| 完整案例 | 不同学情输入到最终资源与动态更新的整链证据 | 至少2组，争取3组 |

所有最终指标必须给出分子、分母、百分比、样本版本、执行提交和证据索引。未执行写`NOT_RUN`，不能只填写目标数字。

## 10. 部署与交付

最终部署说明应从干净环境覆盖：Node/Python版本、依赖安装、Profile激活、API环境变量、服务端启动、Web启动、会话创建和至少一个完整活动。最终压缩包、README、PPT、视频、案例和报告必须来自同一Git提交、Profile revision、seal、提示词版本和模型配置。

## 11. 当前实现边界

- Pandas是当前唯一完整领域包，Profile合同证明可扩展能力，但不虚构第二个已完成领域；
- 多Agent是SDK能力范围内的串行隔离协作，不宣称并行群体网络；
- 固定保障题是模型不可用时的可靠降级，不冒充实时AI生成；
- Node/Python是代码判分权威，Pyodide保持关闭；
- 学情画像Agent实时链、动态错误题组联动、Agent安全可视化和三组完整案例须以最终候选实测为准；
- `LIVE_MODEL`、幻觉率、难度匹配率和覆盖率在正式运行前保持未填写或`NOT_RUN`。
