## 版本一：逐步讲解 `guided`

### 学习目标

**需要了解**

1. “订单号重复”和“整行完全相同”不是同一件事。
2. 可解析日期、最新日期和原始第一条如何组成三级选择规则。
3. 为什么排序只是选择工具，最终输出仍要恢复原始相对顺序。

**需要掌握**

1. 使用规范后的`order_id`识别重复订单组。
2. 显式保存原始位置并严格解析日期。
3. 用稳定排序和`drop_duplicates`按三级规则选择记录。
4. 删除辅助列、恢复结果顺序，并证明输入未被修改。

### 先建立直觉：重复不是“随便删一条”

同一个订单号出现两次，可能是系统重复导出，也可能是订单后来被更新。两行的金额、状态、备注和日期可能不同。如果简单保留第一行，可能丢掉更新后的记录；如果简单保留最后一行，也可能选中日期格式错误的记录。因此，去重前必须先回答“哪一条更可信”。

本项目把选择规则冻结为三层。第一层看日期能否按规定格式解析；第二层在有效日期中选择最新日期；第三层在仍然无法区分时保留原始第一条。规则没有提金额大小、状态或备注，所以代码不能擅自拿这些字段参与排序。

### 把概念拆开

#### 1. 重复键是order_id

整行比较要求所有列都相同，而订单去重只看`order_id`是否相同。下面两行金额不同，仍属于同一订单组：

```python
duplicate_mask = df["order_id"].duplicated(keep=False)  # 标记组内所有重复行
duplicate_rows = df.loc[duplicate_mask].copy()
```

`keep=False`表示同组每一行都标记为重复，便于观察；它还没有决定保留哪条。

【术语注释：重复键】用于判断多条记录是否属于同一业务对象的字段。本项目的重复键是`order_id`。

#### 2. 原始位置必须提前保存

选择过程中会临时排序。如果不保存原始位置，就无法在最后恢复被选记录的相对顺序。

```python
work = df.copy(deep=True)          # 不修改调用者输入
work["_row"] = range(len(work))   # 保存每条记录原始位置
```

辅助列以下划线开头，只在算法内部使用，最终结果必须删除。它不是新的业务字段。

#### 3. 日期必须按冻结格式解析

日期先转换成一个只用于排名的辅助序列。原始日期列保持不变，无法按冻结格式解析的值统一成为缺失时间。

```python
work["_parsed_date"] = pd.to_datetime(
    work["order_date"],
    format="%Y-%m-%d",  # 只接受四位年-两位月-两位日
    errors="coerce",    # 无法解析时变成缺失时间
)
work["_date_valid"] = work["_parsed_date"].notna()
```

`2026-01-14`可解析，`2026/01/14`在本合同下不可解析。不能因为另一种工具“看得懂”斜杠日期就改变规则。

【术语注释：coerce】转换失败时不抛出逐值异常，而是把该值变成缺失，便于后续统一排序和检查。

#### 4. 把三级规则翻译成排序键

希望可解析日期排前、日期新的排前、原始位置小的排前：

```python
ranked = work.sort_values(
    ["order_id", "_date_valid", "_parsed_date", "_row"],
    ascending=[True, False, False, True],
    kind="stable",  # 相同排序键保持原顺序
    na_position="last",
)
```

`order_id`升序只是让同组记录相邻，不决定最终输出顺序；有效标记降序使True在前；日期降序使最新在前；原始位置升序解决最终平局。

【术语注释：稳定排序】当排序键相同时，稳定排序保持记录原有先后关系，使平局结果可预测。

#### 5. 每组保留排序后的第一条

经过复合排序后，组内第一条已经代表三级规则选出的获胜记录，此时才能使用`keep="first"`。

```python
selected = ranked.drop_duplicates(subset=["order_id"], keep="first")
```

此时的“第一条”已经经过三级规则排序，不再是原文件中无条件的第一条。单独调用这句而不做前置排名，无法满足合同。

#### 6. 恢复被选记录的原始相对顺序

选择阶段临时把同组记录排在一起，最终输出要回到获胜记录在原表中的先后位置，并移除所有辅助列。

```python
result = selected.sort_values("_row", kind="stable")
result = result.drop(columns=["_row", "_parsed_date", "_date_valid"])
```

例如O011可能选择原始较后的新记录，但它在最终表中的位置仍由该被选记录的原始位置决定。不要最后按`order_id`排序，因为那会改变行序不变量。

### 跟着三组公开订单走一遍

O011有`2026-01-12`和`2026-01-13`，两者都可解析，所以保留日期较新的金额55记录。O012有`2026-01-14`和`2026/01/14`，只有第一条符合冻结格式，所以保留金额60记录。O013的`not-a-date`和`also-bad`都不可解析，于是保留原始第一条金额70记录。

```python
probe = df[df["order_id"].astype("string").str.strip().isin(["O011", "O012", "O013"])]
print(probe[["order_id", "amount", "order_date"]])  # 先观察三个重复组
```

运行去重函数后可做公开结果检查：

```python
result = deduplicate_orders(df)
by_id = result.set_index(result["order_id"].astype("string").str.strip())
print(by_id.loc[["O011", "O012", "O013"], ["amount", "order_date"]])
```

观察结果的目的，是把三级规则与实际记录对应起来，不是展示隐藏预期。

### 把三级规则逐层推演

处理一个重复组时，不要同时比较所有字段。先问第一问：“哪几条日期严格有效？”如果只有一条有效，选择已经结束，金额和文件位置都不能推翻它。若多条都有效，再问第二问：“哪条日期最新？”只有日期仍相同，才进入第三问：“原始数据中谁先出现？”

O012很适合说明这种短路过程。第一条日期`2026-01-14`有效，第二条`2026/01/14`无效，因此第一问已经给出答案，不需要再比较金额61和60。O013两条都无效，第一问无法区分；第二问没有有效日期可比较；第三问选择原始第一条。

```python
group = work.loc[work["order_id"].eq("O012")]
print(group[["amount", "order_date", "_date_valid", "_row"]])
```

这种逐层解释比“排序后取第一条”更适合教学。代码采用排序是为了批量执行相同逻辑，业务含义仍是三次有顺序的判断。

### 为什么必须选择整行

订单的一行代表一次完整导出状态。若金额取最新记录、备注取第一条、状态再取最大值，就拼出了一条原始数据中从未存在的订单。去重不是逐列求最优，而是在真实记录之间选一个获胜者。

```python
wrong = group.groupby("order_id").agg({"amount": "max", "note": "first"})  # 可能拼接不同记录
```

`drop_duplicates`在排序后保留整行，所以金额、日期、状态和备注保持来自同一条记录。这个性质对审计很重要：可以回到原始位置解释结果，而不是面对人工组合的数据。

### 非重复记录也要保持稳定

算法不只处理重复组。没有重复的订单应原样保留，其字段和值不能因为辅助排序发生变化。恢复`_row`顺序后，所有获胜记录按照它们在输入中的位置排列，非重复记录自然回到原位置关系。

```python
unique_before = work.loc[~work["order_id"].duplicated(keep=False), "order_id"].tolist()
unique_after = result.loc[result["order_id"].isin(unique_before), "order_id"].tolist()
```

若非重复订单顺序改变，说明恢复步骤或最后的额外排序有问题，即使重复组选择正确也不能通过完整验收。

### 哪里容易错

#### 反例一：无条件保留原始第一条

这会让O011保留旧日期记录，忽略明确的最新日期规则。

```python
result = df.drop_duplicates("order_id", keep="first")  # 错误：没有日期排名
```

正确做法先排名再去重：

```python
ranked = work.sort_values(sort_keys, ascending=sort_directions, kind="stable")
result = ranked.drop_duplicates("order_id", keep="first")
```

#### 反例二：无条件保留最后一条

O012的最后一条日期格式无效，O013最后一条也不应在平局中获胜。

```python
result = df.drop_duplicates("order_id", keep="last")  # 错误：文件位置不是最高规则
```

#### 反例三：按金额最大选择

金额不在冻结优先级中，即使较大也不能成为保留依据。

```python
ranked = df.sort_values(["order_id", "amount"], ascending=[True, False])  # 错误
```

#### 反例四：使用宽松日期推断

宽松推断可能接受斜杠日期或根据地区猜测月日顺序，使相同文本在不同环境中获得不同排名。

```python
parsed = pd.to_datetime(df["order_date"], errors="coerce")  # 风险：格式可能被猜测
```

```python
parsed = pd.to_datetime(df["order_date"], format="%Y-%m-%d", errors="coerce")
```

#### 反例五：最后按订单号排序

订单号排序会让结果看起来整齐，却抹掉获胜记录在原始数据中的先后关系。

```python
result = selected.sort_values("order_id")  # 错误：破坏被选记录原始顺序
```

```python
result = selected.sort_values("_row", kind="stable")  # 正确：恢复原始相对顺序
```

### 输入不可变与重复运行

去重需要多个辅助列和排序步骤，更要避免在原表上`inplace`操作。保存深拷贝并在结束后比较，可以证明调用者输入没被改写。

```python
before = df.copy(deep=True)
result = deduplicate_orders(df)
assert df.equals(before)
assert result["order_id"].is_unique
```

已去重结果再次运行时，每组只有一条，输出不应变化。幂等性让失败恢复和重复提交更容易验证。

### 测试不能只检查唯一性

任何`drop_duplicates`写法都可能让订单号唯一，所以唯一性只是必要条件。完整测试还要覆盖每一级规则、输入不变、辅助列清除和最终行序。否则错误实现也会得到一个表面整洁的唯一结果。

```python
checks = {
    "unique": bool(result["order_id"].is_unique),
    "input_unchanged": bool(df.equals(before)),
    "helpers_removed": not any(str(c).startswith("_") for c in result.columns),
}
```

公开O011/O012/O013分别证明最新、有效和平局规则；再加入非重复订单顺序检查，才能覆盖算法的主要出口。

### 错误结果怎样归因

O011选错通常指向日期排序方向；O012选错通常指向严格格式或有效标记；O013选错通常指向`keep`或原始位置方向；所有选择正确但行序错，指向恢复步骤；输入多出辅助列，指向副本边界。按症状归因，比笼统提示“去重失败”更能帮助学习者修改代码。

处理失败时不应创建负Evidence或半写入结果。学习者修正后，新Attempt从同一输入重新计算，原始记录和排序依据都没有变化。

### 接到最终任务

缺失阶段已经保证订单号非空，本节进一步保证唯一，并保持被选记录的原始相对顺序。金额、日期dtype、城市和状态仍由类型阶段规范。

```python
dedupe_ready = deduplicate_orders(missing_ready)
typed = normalize_types(dedupe_ready)
```

最终验收关注：输入不变；`order_id`唯一；O011/O012/O013按公开三级规则选择；辅助列不出现在输出；被选记录顺序没有被订单号排序打乱。

### 术语与依据

- **重复键**：判断记录属于同一业务对象的字段。
- **排序键**：决定记录先后顺序的一组字段。
- **稳定排序**：排序值相同时保留原先先后关系。
- **平局规则**：前面条件无法区分时使用的最终选择条件。
- **原始相对顺序**：被选记录在原数据中的先后关系。

去重和排序API绑定`src-pandas-duplicates`、`src-pandas-sort-values`；三级规则绑定revision 3公开合同。

## 版本二：重点速览 `concise`

### 学习目标

**需要了解**

1. 三级选择规则可以表示为确定性的复合排序。
2. 严格日期解析、稳定排序和原始位置各自解决什么问题。
3. 分组选择顺序与最终输出顺序为什么必须分开。

**需要掌握**

1. 把可解析优先、最新优先、原始第一条翻译为排序键。
2. 使用辅助列、稳定排序和`drop_duplicates`完成确定性选择。
3. 验证输入不可变、订单号唯一、辅助列清除和行序恢复。
4. 识别宽松日期、错误平局规则和结果再排序等回归。

### 算法合同

对每个规范`order_id`，记录优先级可写成：`日期有效降序 → 解析日期降序 → 原始位置升序`。先按订单号聚组，再按优先级排序，组内第一条就是被选记录。最终再按被选记录原始位置升序恢复全表顺序。

```python
work = df.copy(deep=True)
work["_row"] = range(len(work))  # 最终平局和顺序恢复的共同事实源
work["_date"] = pd.to_datetime(work["order_date"], format="%Y-%m-%d", errors="coerce")
work["_valid"] = work["_date"].notna()
```

### 复合排序

复合排序把三级业务判断编码成四个有优先顺序的键。下面的方向数组必须与键数组逐一对应。

```python
ranked = work.sort_values(
    ["order_id", "_valid", "_date", "_row"],
    ascending=[True, False, False, True],
    kind="stable",
    na_position="last",
)
```

排序方向必须逐项解释：订单号升序仅用于聚组；有效标记和日期降序实现前两级规则；原始位置升序实现平局；stable保证完全相同时仍可预测。删掉任何一项，都可能让某个边界组选择错误。

### 选择与恢复

排序只建立组内优先级；选择保留整行；恢复再处理全表展示顺序。三步不能合并为一次无解释的排序。

```python
selected = ranked.drop_duplicates("order_id", keep="first")
result = selected.sort_values("_row", kind="stable")
result = result.drop(columns=["_row", "_date", "_valid"])
```

选择阶段的顺序服务于“谁获胜”，恢复阶段的顺序服务于“获胜记录怎样排列”。混用两种顺序，是此类算法最常见的隐蔽错误。

### 三个公开边界组

O011：两日期都有效，较新记录获胜。O012：只有`2026-01-14`严格有效，有效记录获胜。O013：两日期都无效，原始第一条获胜。这三组分别覆盖第二级、第一级和第三级规则。

```python
ids = result["order_id"].astype("string").str.strip()
by_id = result.assign(_id=ids).set_index("_id")
print(by_id.loc[["O011", "O012", "O013"], "amount"])
```

### 为什么必须严格解析

省略`format`会让解析行为受输入形状或pandas版本影响，斜杠日期可能被宽松接受，O012便失去“可解析优先”的明确边界。固定格式不是苛刻，而是让相同输入始终产生相同排名。

```python
strict = pd.to_datetime(df["order_date"], format="%Y-%m-%d", errors="coerce")
valid = strict.notna()
```

### 排名的形式化理解

可以把每条记录的优先级看成一个元组：`(是否有效, 解析日期, 原始位置的反向优先)`。比较时从左到右，前一项已经分出高低，就不再看后项。实际`sort_values`使用不同升降序表达同一含义。

这说明金额、状态和备注不在元组里。即使某条金额更高或状态看起来更“完整”，也没有资格改变获胜者。算法的确定性来自有限、冻结的比较维度，而不是“综合看起来更好”。

```python
ranking_view = work[["order_id", "_valid", "_date", "_row"]]
print(ranking_view)
```

### 缺失日期的排序位置

`errors="coerce"`会把无效日期变为`NaT`。通过`_valid`降序和`na_position="last"`，有效日期稳定排在无效日期前。仅设置`na_position`还不够清楚，因为显式有效标记同时承担业务解释和测试观察。

【术语注释：NaT】NaT是pandas用于表示缺失日期时间的标记，类似数值领域的缺失值。

当组内日期都无效时，`_valid`和`_date`均无法区分，排序自然落到`_row`升序，从而实现原始第一条。

### 为什么不能用groupby后随意取行

`groupby.first()`、`last()`或`max()`各自有不同缺失与列聚合语义，可能从不同原始行拼出一条不存在的记录。合同要求选择一整条真实记录，而不是按列组合。

```python
wrong = df.groupby("order_id").max()  # 错误：可能逐列聚合，不是选择整行
```

排序后`drop_duplicates`保留的是整行，金额、状态、备注来自同一条被选记录。

### 不变量

去重完成后至少要同时检查输入、唯一性、辅助列和行序。下面的断言分别守护不同风险。

```python
before = df.copy(deep=True)
result = deduplicate_orders(df)
assert df.equals(before)                    # 输入不变
assert result["order_id"].is_unique          # 键唯一
assert not any(name.startswith("_") for name in result.columns)  # 无辅助列
```

还要验证结果行序。可以把每条被选记录映射回输入位置，并确认位置序列单调递增。不能只检查唯一性，因为错误选择和错误排序同样可能得到唯一订单号。

```python
positions = [int(df.index[df["order_id"].astype("string").str.strip().eq(value)][0]) for value in result["order_id"]]
assert positions == sorted(positions)
```

当同一订单选择的不是首条时，上述简化映射只适合无重复或首条定位演示；正式验证应绑定被选记录的稳定标识或预先保存`_row`，避免把组内首条误当成获胜行。

### 反例矩阵

以下写法都可能产生唯一订单号，但分别违反日期、平局或行序规则，不能因为代码短就接受。

```python
df.drop_duplicates("order_id", keep="first")  # 忽略有效和最新日期
df.drop_duplicates("order_id", keep="last")   # 把文件末尾当成最高规则
df.sort_values("amount").drop_duplicates("order_id")  # 使用未授权字段
```

```python
pd.to_datetime(df["order_date"], errors="coerce")  # 宽松格式风险
selected.sort_values("order_id")                    # 破坏最终行序
```

这些代码可能通过“订单号唯一”断言，所以测试必须覆盖选择内容和行序，不允许单一指标冒充完整正确。

### 复杂度与Demo边界

当前固定数据规模很小，稳定排序的成本可接受。无需为性能引入复杂索引、数据库或分布式计算。KISS原则在这里表现为：一份原始位置、一份严格日期、一个明确排序和一次整行选择。

算法中的辅助列只存在于函数内部，不能进入公开结果、Attempt或Evidence。普通日志可以记录重复组数和删除行数，不记录私有数据正文。

### 错误归因

缺少`order_id`或`order_date`列属于结构合同错误；日期无法解析是正常排名输入；结果订单号仍重复属于去重实现错误；输入被修改属于副作用错误；结果顺序改变属于行序不变量错误。区分这些类别，反馈才能指向正确小节。

```python
duplicate_groups = int(df["order_id"].duplicated(keep=False).sum())
removed_rows = len(df) - len(result)
```

### 公开证据与私有边界

教学正文可以使用公开CSV中的O011、O012、O013解释三级规则，也可以展示公开测试允许的结果字段。但不能读取私有变体、复制隐藏断言或展示完整最终参考实现。算法规则是公开合同，私有样例仍属于评测资产。

普通日志记录输入行数、输出行数、重复组数和算法版本即可。不要记录完整订单正文，也不要把内部辅助日期或宿主路径放入公共响应。

### 选择正确与输出正确是两层结论

第一层验证每个重复组保留了正确记录；第二层验证这些记录按照原始相对顺序排列且列结构未变。只有两层都通过，去重活动才能产生正确结果。

```python
assert result["order_id"].is_unique         # 组内只剩一条
assert result.columns.tolist() == df.columns.tolist()  # 业务列结构不变
```

这两个断言仍不覆盖具体获胜者和行序，因此要与公开边界组及`_row`映射测试组合使用。测试集合的设计必须和合同维度一一对应。

### 与最终任务连接

本节只决定重复组保留哪条真实记录，并恢复全表顺序。类型和格式仍未最终规范，但严格日期副本只作为排名辅助，不写回业务日期列。

```python
dedupe_ready = deduplicate_orders(missing_ready)
typed = normalize_types(dedupe_ready)
```

### 完成性判定

去重完成不能只看`order_id.is_unique`。还必须确认每个公开边界组选择了合同规定的整行、输入没有被改写、辅助列已经移除、非重复订单未丢失、被选记录按原始相对顺序排列。若订单号唯一但O011保留旧记录，属于选择错误；若选择正确但最终按订单号重排，属于行序错误。只有这些维度同时成立，结果才可交给类型阶段。

### 术语与来源

- **复合排序**：由多个按优先级排列的排序键共同决定顺序。
- **整行选择**：保留某一条真实记录，而不是逐列聚合。
- **稳定标识**：能把输出记录可靠映射回输入位置的标记。
- **辅助列**：算法内部临时字段，最终必须删除。
- **行序不变量**：被选记录的原始相对顺序保持不变。

API来源与规则边界同共同事实表。

## 版本三：案例实战 `practice`

### 学习目标

**需要了解**

1. 重复订单可能代表更新记录，随便保留会产生金额和状态错误。
2. O011、O012、O013分别验证三级规则的哪一层。
3. 辅助排序顺序与最终业务输出顺序的区别。

**需要掌握**

1. 编写可运行的稳定去重函数并用公开重复组验证。
2. 从错误金额或日期定位优先级、格式和排序方向问题。
3. 证明输入不变、结果唯一、被选记录正确且行序稳定。
4. 形成不泄漏原始内容的重复处理摘要。

### 业务场景：同一订单出现两次，哪条才算数

O011先导出金额50、日期`2026-01-12`，后来又导出金额55、日期`2026-01-13`。较新日期说明后者是更新记录，应保留55。O012第二条金额更大，但日期`2026/01/14`不符合冻结格式，因此保留第一条60。O013两条日期都无法解析，不能靠猜测决定，只能保留原始第一条70。

这三个结果看似都是“去重”，背后理由完全不同。实战代码必须能给出同一套优先级，而不是为每个订单写特例。

### 第一步：准备工作副本

实战先建立不污染输入的工作表，再生成原始位置、严格日期和有效标记三个辅助事实。

```python
def prepare_ranking(df):
    work = df.copy(deep=True)         # 原始输入保留给重试和审计
    work["_row"] = range(len(work))  # 每条记录原始位置
    work["_date"] = pd.to_datetime(
        work["order_date"], format="%Y-%m-%d", errors="coerce"
    )
    work["_valid"] = work["_date"].notna()
    return work
```

辅助列以`_`开头，提醒开发者它们不是订单字段。严格日期解析只为排名服务，不覆盖原始`order_date`。

### 第二步：按业务优先级排名

排序键从左到右对应分组、有效优先、最新优先和原始第一条，任何方向写反都会影响特定公开案例。

```python
work = prepare_ranking(df)
ranked = work.sort_values(
    ["order_id", "_valid", "_date", "_row"],
    ascending=[True, False, False, True],
    kind="stable",
    na_position="last",
)
```

现场调试时可以只打印某个公开重复组的排名，避免整表噪音：

```python
print(ranked.loc[ranked["order_id"].eq("O011"), ["amount", "order_date", "_valid", "_row"]])
```

### 第三步：选择整行并恢复顺序

排名完成后保留每组第一条整行，再按获胜记录的原始位置恢复全表顺序。

```python
selected = ranked.drop_duplicates("order_id", keep="first")
result = selected.sort_values("_row", kind="stable")
result = result.drop(columns=["_row", "_date", "_valid"])
```

先选再恢复，不能反过来。若先恢复原始顺序再`keep="first"`，最新日期规则会失效。

### 第四步：验证三个公开案例

三个案例分别覆盖三级规则，不应只验证订单号唯一或删除行数。

```python
by_id = result.assign(_id=result["order_id"].astype("string").str.strip()).set_index("_id")
assert str(by_id.loc["O011", "amount"]).strip() == "55"
assert str(by_id.loc["O012", "amount"]).strip() == "60"
assert str(by_id.loc["O013", "amount"]).strip() == "70"
```

三个断言分别覆盖最新日期、有效日期和原始第一条。只测一个组无法证明完整优先级。

### 现场故障一：O011仍是50

通常是直接`keep="first"`，或日期排序方向写成升序。

```python
ranked = work.sort_values("_date", ascending=True)  # 错误：旧日期在前
```

```python
ranked = work.sort_values("_date", ascending=False, na_position="last")  # 新日期在前
```

还要保留`order_id/_valid/_row`等其他排序键，单列示例只解释方向。

### 现场故障二：O012错误保留61

如果省略严格格式，斜杠日期可能被解析；如果按金额排序，较大金额会越权获胜。

```python
dates = pd.to_datetime(work["order_date"], errors="coerce")  # 风险：宽松猜测
```

```python
dates = pd.to_datetime(work["order_date"], format="%Y-%m-%d", errors="coerce")
```

### 现场故障三：O013保留第二条

两日期都无效时，代码必须依赖原始位置升序。若使用`keep="last"`或`_row`降序，平局规则会反转。

```python
ascending = [True, False, False, False]  # 错误：最后一项让后出现记录优先
ascending = [True, False, False, True]   # 正确：原始第一条优先
```

### 现场故障四：结果被按订单号重排

选择记录正确，但页面顺序与输入不同，通常是忘记按`_row`恢复，或最后又按`order_id`排序。

```python
result = selected.sort_values("order_id")  # 错误：改变业务行序
result = selected.sort_values("_row")      # 正确：恢复被选记录位置
```

### 现场故障五：原始表多了辅助列

在输入上直接赋`_date`会污染调用者，也可能让重试看到不同列集合。

```python
df["_date"] = pd.to_datetime(df["order_date"])  # 错误：修改输入
work = df.copy(deep=True)                         # 正确：辅助列只加在副本
```

### 完整实战函数

把工作副本、排名、整行选择、顺序恢复和辅助列清理组合成职责单一的去重函数。

```python
def deduplicate_orders(df):
    work = df.copy(deep=True)
    work["_row"] = range(len(work))
    work["_date"] = pd.to_datetime(work["order_date"], format="%Y-%m-%d", errors="coerce")
    work["_valid"] = work["_date"].notna()
    ranked = work.sort_values(
        ["order_id", "_valid", "_date", "_row"],
        ascending=[True, False, False, True],
        kind="stable",
        na_position="last",
    )
    selected = ranked.drop_duplicates("order_id", keep="first")
    selected = selected.sort_values("_row", kind="stable")
    return selected.drop(columns=["_row", "_date", "_valid"])
```

函数只执行公开去重规则，不规范金额、城市或状态。教学示例公开透明，但不能被当成hidden tests或完整最终实操答案。

### 用排名表定位错误

当结果不符合预期时，不要立刻改`drop_duplicates`。先打印目标组的四个排名事实，逐列判断：`_valid`是否正确、`_date`是否严格解析、`_row`是否对应原位置、排序方向是否正确。

```python
debug_columns = ["order_id", "amount", "order_date", "_valid", "_date", "_row"]
print(ranked.loc[ranked["order_id"].isin(["O011", "O012", "O013"]), debug_columns])
```

O011若日期有效但旧记录排前，检查日期降序；O012若斜杠日期显示有效，检查`format`；O013若第二条排前，检查`_row`方向。排名表把业务规则变成可观察证据。

### 验证最终行序

可以在选择前保留`_row`，先验证它在最终结果中递增，再删除辅助列。这比按订单号重新搜索首个位置更准确，因为获胜者可能不是组内第一条。

```python
selected = ranked.drop_duplicates("order_id", keep="first")
selected = selected.sort_values("_row", kind="stable")
assert selected["_row"].is_monotonic_increasing
result = selected.drop(columns=["_row", "_date", "_valid"])
```

这里的递增只证明获胜记录保持原始相对顺序，不要求索引连续。是否重置索引应由最终比较合同决定，不能借重置索引重新排序。

### 非重复订单回归

现场修复重复组时，也要确认单次出现的订单没有丢失或改值。可以在输入中选一个稳定订单，比较去重前后的公开字段。

```python
before_o007 = df.loc[df["order_id"].eq("O007")].iloc[0]
after_o007 = result.loc[result["order_id"].eq("O007")].iloc[0]
assert before_o007.equals(after_o007)
```

如果非重复记录发生变化，通常是逐列聚合、辅助列未清理或后续类型逻辑错误混入了本函数。

### 故障恢复与重复提交

如果首次实现排序方向错误，修复后应从原始`df`重新运行。输入不变断言保证错误Attempt没有把辅助列或排序结果写回。

```python
before = df.copy(deep=True)
result = deduplicate_orders(df)
assert df.equals(before)
assert result["order_id"].is_unique
```

同一函数再次处理已去重结果，应保持相同记录和顺序。服务重启后也可由输入重新计算，不依赖内存中的临时排名。

### 实战摘要与演示表达

摘要展示算法处理规模和唯一性，具体公开案例再解释每一级规则为什么选中当前记录。

```python
summary = {
    "input_rows": len(df),
    "output_rows": len(result),
    "removed_duplicates": len(df) - len(result),
    "unique_order_id": bool(result["order_id"].is_unique),
}
```

演示时应解释O011、O012、O013为何分别保留，而不是只展示删除了几行。摘要不包含私有变体，不记录完整订单正文，也不修改正式Evidence。

### 失败恢复和服务重建

排名辅助列只存在于一次函数调用中，服务重启后可从冻结输入重新计算，不需要保存内部排序表。若运行中途失败，原始DataFrame不变，正式结果不应半写入。学习者修复代码后重新提交，会重新执行完整排名。

```python
before = df.copy(deep=True)
try:
    result = deduplicate_orders(df)
finally:
    assert df.equals(before)
```

这种恢复方式符合Demo边界：不建设复杂任务队列，只保证输入事实稳定、错误明确和算法可重算。

### 怎样向非专业用户解释

可以说：“同一订单出现多次时，系统先相信格式正确的日期；如果日期都正确，就选最新的一条；如果日期仍无法区分，就保留原文件先出现的记录。选完后不会按订单号打乱原顺序。”这段话应与代码排序键逐项对应。

教学页面可把三层规则画成顺序列表，并在公开O011/O012/O013旁显示命中的规则层级。不能只显示一个“已去重”标签，否则用户看不见系统怎样做决定。

### 接到最终任务

去重结果现在满足订单号唯一和行序稳定，可交给类型格式阶段。日期辅助列已经删除，业务日期仍保留原始表示，后续会严格转换。

```python
dedupe_ready = deduplicate_orders(missing_ready)
typed = normalize_types(dedupe_ready)
```

### 实战完成标准

现场验收要同时回答四个问题：删掉了多少重复行、O011/O012/O013各因哪一级规则获胜、原始输入是否保持不变、最终行序是否仍对应获胜记录的原位置。只展示行数减少或唯一性图标，会掩盖错误选择。若任一规则无法由公开输入复算，或失败后留下半成品结果，本节应明确登记未通过，而不是继续进入类型转换。

### 术语与来源

- **更新记录**：同一业务对象在较晚时间产生的新版本记录。
- **严格解析**：只接受明确声明的日期格式。
- **三级优先级**：有效日期、最新日期、原始第一条。
- **整行选择**：所有字段来自同一条获胜记录。
- **恢复顺序**：选择完成后按获胜记录原始位置排列。

API和规则来源同共同事实表，示例只使用公开订单组。
