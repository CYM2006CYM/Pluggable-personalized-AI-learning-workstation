# AI协作提示词编写方法

> 来源：团队成员“橘子zhen好吃”在项目协作对话中的经验总结与观点提炼。
> 性质：团队学习材料，不是项目合同、负责人决策或岗位任务书。发生冲突时，以06号、20号、公共合同和当周正式任务书为准。

## 1. 核心观点

在本项目中，提示词最重要的作用不是“让AI自由发挥”，而是让AI先理解自己的角色、当前阶段和权威依据，再开始执行任务。

可以概括为一句话：

```text
先让AI读对文档、认清角色和任务边界，再让AI检查或开发具体内容。

因为文档其实就是提示词，一定要强制AI去读指定的文档（比如A岗位工作的时候就一定要强制AI读27,28,29号文档）；一定要让AI知道自己是哪个岗位的什么角色，这样AI才知道要做什么。

如果不强制AI读文档、定角色，AI会乱做一气，最后输出的效果不好。
```

这样做可以减少以下问题：

- AI遗漏正式合同中的要求；
- AI把其他岗位的任务算到当前岗位头上；
- AI审核尚未开始或不属于当前阶段的工作；
- AI根据常识自行补充项目没有冻结的规则；
- AI只看测试是否通过，却没有逐项核对合同；
- AI越权修改其他岗位文件，或者提前实现后续周功能。

## 2. 提示词应反复强调“角色”和“文档”

“橘子zhen好吃”的核心做法，是在提示词中持续强调两件事：

1. AI当前扮演哪个岗位或承担什么职责；
2. AI必须依据哪些权威文档开展工作。

例如：

```text
你现在作为岗位E进行独立复验。
请先完整阅读27、28、33号文档，再依据其中V2-4和V2-5的要求审核A的D2-D3交付物。
```

角色决定AI“站在谁的职责范围内做事”，文档决定AI“按什么标准判断”。两者缺一不可。

只说“帮我检查一下”通常不够，因为AI并不知道：

- 这是负责人审计、作者自检，还是E的独立复验；
- 应以哪一版合同为准；
- 哪些内容已经完成，哪些内容尚未开始；
- 是否允许修改文件；
- 最后需要建议、报告，还是直接实施修复。

## 3. 先告诉AI当前阶段，再限定审核范围

项目任务按周、按天、按岗位拆分。提示词必须明确本次只判断哪个时间段的任务。

聊天中的典型表达是：

```text
先仔细阅读27、28、29号文档，检查A有没有完成第二周D2-D3的任务。
这里的“完成D2-D3任务”只指A在第二天和第三天应完成的内容，
不要审核尚未开始的D4-D7任务。
```

这个限制很重要。否则AI可能把以下尚未到期的事项误判为A欠交：

- D4对B冻结候选和D材料的只读审计；
- D5对C/D提交的复核；
- D6对E完整验证结果的复核；
- D7条件修复和负责人最终签署。

正确做法是先冻结“岗位 + 周次 + 天数 + 交付物”，再进行判断。

## 4. 让AI先读，再做，不要直接给结论

对于有完整设计文档的项目，提示词应明确执行顺序：

```text
第一步：阅读指定文档并提取验收条款。
第二步：核对交付包、代码、测试和交接单。
第三步：独立运行必要验证。
第四步：逐项给出PASS、BLOCKED或不在本轮范围。
第五步：形成结论和最小修复清单。
```

“先读文档”不能只是一句泛泛要求。最好直接给出文件编号、重点章节和权威顺序。

例如：

```text
主要依据27号总任务书、28号公共合同和29号A岗位任务书。
如果三者存在冲突，不要自行选择，列出冲突位置交负责人裁决。
```

## 5. 直接把任务交给AI，不必层层转写提示词

聊天中还提出了一个实用观点：通常不需要先让一个AI替另一个AI编写提示词，再把生成的提示词转发给执行AI。

如果任务本身已经明确，可以直接告诉执行AI：

```text
请先阅读指定文档，然后按照对应岗位任务书完成检查。
```

多一次提示词转写，可能带来：

- 原始要求被简化或遗漏；
- 文档编号、时间边界和岗位边界在转述中发生偏差；
- 执行AI只看到二手总结，没有直接接触权威文档；
- 团队难以追溯最终判断依据。

只有在任务非常复杂、需要统一多人输入格式时，才有必要先设计公共提示词模板。即使使用模板，执行AI仍应直接阅读正式文档。

## 6. 推荐的项目提示词结构

一个适合本项目的提示词，建议包含以下八项。

### 6.1 角色

告诉AI当前以什么身份工作。

```text
你现在作为岗位E的独立验证人员开展工作。
```

### 6.2 权威文档

指定必须阅读的合同和任务书。

```text
请先完整阅读27、28、33号和06号V2门禁，不要只依据成员交接单。
```

### 6.3 当前阶段

明确周次、天数、正式基线和候选状态。

```text
当前审核范围是第二周D2-D3，不审核D4-D7尚未发生的任务。
```

### 6.4 审核或开发对象

列出具体文件、压缩包、提交号或目录。

```text
审核对象是A的ZIP、sidecar、Manifest和最终交接单。
```

### 6.5 执行边界

明确只读还是允许修改，以及禁止事项。

```text
本轮只读审核，不修改A文件，不提交、不推送，不为了通过测试降低断言。
```

### 6.6 验收标准

把判断项写清楚，避免AI只看测试总数。

```text
重点检查V2-4、V2-5、首次提交不可覆盖、事务恢复、无半写入和非Pandas smoke。
```

### 6.7 输出格式

明确希望得到什么结果。

```text
先列阻塞问题，再给逐项验收表、验证命令、真实测试项数、最终结论和最小修复清单。
```

### 6.8 决策边界

避免AI越权替负责人签署。

```text
你可以判断技术项PASS或BLOCKED，但不能代替负责人批准上传锁或签署整周GO。
```

## 7. 可直接复用的提示词模板

```text
你现在作为【岗位/角色】开展【审核/开发/复验】。

请先完整阅读：
- 【权威文档1】
- 【权威文档2】
- 【岗位任务书】

权威顺序为：【决策清单 → 公共合同 → 总任务书 → 岗位任务书】。
如果发现冲突，不要自行裁决，请列出冲突条款和影响。

当前阶段是【第几周、D几到D几】。
本轮只判断【明确范围】，不要把【尚未开始或其他岗位任务】算作本轮欠交。

审核/开发对象：
- 【文件、目录、ZIP、提交号或交付物】

执行边界：
- 【只读或允许修改的范围】
- 不修改其他岗位文件；
- 不降低测试和合同标准；
- 不提交、不推送，除非负责人另行批准。

请按以下顺序执行：
1. 从文档提取逐项验收标准；
2. 核对交付物完整性和哈希；
3. 在隔离环境运行必要测试；
4. 补充合同反例，不只运行作者已有测试；
5. 区分作者缺陷、环境噪音和不在本轮范围的事项；
6. 输出PASS/BLOCKED结论、证据和最小修复清单。

最终报告至少包含：
- 审核基线；
- 合同版本；
- 文件和哈希；
- 实际命令与真实测试项数；
- 逐项结果；
- 越权和敏感信息检查；
- 是否存在技术阻塞；
- 需要负责人裁决的事项。
```

## 8. 本项目审核A交付物的示例

不够清晰的写法：

```text
帮我看看A做完了吗？
```

推荐写法：

```text
你现在作为岗位E进行独立复验。

请先完整阅读27号第二周总任务书、28号第二周公共合同、
29号A岗位任务书和33号E岗位任务书。

本轮只审核A在第二周D2-D3应完成的诊断、Evidence、
KnowledgeState、事务仓储和非Pandas smoke，
不要把A在D4-D7才执行的只读审计或条件修复算作当前欠交。

审核对象是以下ZIP、sidecar和交接单：【填写路径】。
请先核对外层SHA-256和包内Manifest，再在仓库外独立工作树复验。

重点执行V2-4和V2-5，并补充作者测试可能遗漏的合同反例，
包括并发首次提交、JSON合法但语义损坏候选恢复和完成事务中断。

本轮只读，不修改A文件、不降低断言、不提交、不推送。
最终先列阻塞问题，再给逐项结果、真实命令、测试项数和结论。
技术PASS不代表你有权批准上传锁或签署整周GO。
```

## 9. 常见问题及改进方式

| 常见问题 | 可能后果 | 改进方式 |
|---|---|---|
| 只说“检查一下” | AI不知道按什么标准检查 | 指定角色、文档和验收编号 |
| 只提供交接单 | AI可能相信作者自报PASS | 要求读取合同并独立运行测试 |
| 不写当前天数 | AI审核尚未开始的任务 | 明确只审D2-D3或当前阶段 |
| 不写岗位边界 | AI修改他人文件或代替负责人裁决 | 列出允许、禁止和最终决策人 |
| 只要求运行现有测试 | 作者测试遗漏的反例无法发现 | 要求补充合同反例和破坏性测试 |
| 让AI自由选择文档 | AI可能引用旧草稿或历史副本 | 直接列出权威文件和优先顺序 |
| 把“测试通过”等同于“任务完成” | 流程、哈希、交接和上传锁可能遗漏 | 同时检查代码、证据和流程状态 |
| 让一个AI层层转写给另一个AI | 要求在转述中失真 | 执行AI直接阅读权威文档 |

## 10. 发送提示词前的检查表

发送给AI前，至少确认：

- [ ] 已写明AI当前角色；
- [ ] 已列出必须阅读的权威文档；
- [ ] 已说明文档冲突如何处理；
- [ ] 已写明当前周次和天数；
- [ ] 已限定本轮任务范围；
- [ ] 已列出输入文件、目录、ZIP或提交号；
- [ ] 已说明只读或可修改范围；
- [ ] 已写明禁止提交、推送、越权和降低标准；
- [ ] 已列出关键验收项，而不是只说“测试一下”；
- [ ] 已要求记录真实命令和测试项数；
- [ ] 已区分技术结论与负责人最终批准；
- [ ] 已明确最终输出格式。

## 11. 最后总结

好的项目提示词不一定很长，但必须把以下关系说清楚：

```text
谁来做
→ 先读什么
→ 当前做到哪一天
→ 具体检查什么
→ 哪些内容不能碰
→ 用什么标准判断
→ 最后交付什么证据
→ 谁拥有最终决定权
```

对于本项目，最值得团队统一采用的习惯是：每次让AI工作前，都先让AI阅读对应的正式文档，让AI知道自己的岗位、任务范围和验收标准。提示词负责把AI引到正确的合同和上下文中，正式文档负责提供最终事实依据。
