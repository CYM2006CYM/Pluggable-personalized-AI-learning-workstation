# 审计后一次性整改提示词编写规范

状态：`[团队协作参考]`。本文约束技术负责人协作助手在完成交付审计后，如何把审计结论转换成准确、完整、可复验的整改指令。本文不是项目合同，不新增公共类型、岗位任务、上传权限或验收门禁；发生冲突时，仍按“负责人决策冻结清单 → 公共合同 → 06号六周计划 → 周总任务书 → 岗位任务书 → 专项设计 → 历史报告”的顺序执行。

相关参考：

- [AI协作提示词编写方法](./AI协作提示词编写方法-橘子zhen好吃观点提炼.md)负责一般任务提示词的角色、文档、阶段和权限表达；
- [负责人任务布置原则](./负责人任务布置原则-单日闭环与真实依赖.md)负责单日闭环、真实依赖和上传顺序；
- 本文只解决“审计已经完成后，怎样写出尽量一次闭合的整改指令”。

## 1. 目标

整改提示词不是审计报告的缩写，也不是把“哪里不对”转述给组员。它必须把每个已证实问题转换成一组可执行、可测试、可交付、可独立复验的后置条件，使组员不需要猜测以下事项：

- 哪个行为违反了哪一条现行合同；
- 实际结果和预期结果分别是什么；
- 根因位于哪里，影响了哪些相邻入口和出口；
- 哪些文件允许修改，哪些内容必须保持不变；
- 修复完成后必须通过哪些正例、反例、边界和回归测试；
- 交付包、证据、哈希和交接单应如何同步更新；
- 哪些事项仍需负责人裁决，不能由组员自行选择。

“一次性完成”在本文中的含义是：**当前审计已经发现且能够从现有合同确定的问题，应在同一轮整改中完整闭合，不因提示词遗漏、歧义或只修表象而再次返工。** 独立复验仍然必须执行；本文不承诺任何实现永远不存在新的、此前不可见的缺陷。

## 2. 适用边界

本规范适用于A—E岗位的代码、资产、标注、证据、文档、ZIP和交接材料整改。使用时必须遵守以下边界：

1. 只处理当前周次、当前工作日和当前交付包范围内的事项。
2. 不把后续工作日任务、其他岗位任务或赛后生产化建议夹带进整改。
3. 不以整改名义补写未冻结合同；确有合同冲突或缺口时，先列条款、影响和待裁决问题，等待负责人决定。
4. 不要求重做已经独立确认通过且未受修复影响的实现、证据或测试。
5. 不把改进建议、代码风格偏好或可选重构写成阻断项。
6. 不授权commit、push、上传锁、Profile激活、gold生成或负责人签署，除非负责人另行明确批准。
7. 以挑战杯MVP、研究验证和现场演示为尺度，不扩展为生产级商业系统。

## 3. 审计结论必须先标准化

编写整改提示词前，协作助手必须先把审计发现分为以下五类。分类没有完成时，不得直接生成给组员的指令。

| 分类 | 定义 | 是否写入整改任务 |
|---|---|---|
| `CONFIRMED_BLOCKER` | 有现行合同依据和可复现证据，阻止本轮技术PASS | 必须写入 |
| `CONFIRMED_REQUIRED` | 明确违反交付、证据或文档要求，但不单独破坏主体运行 | 必须写入 |
| `OWNER_DECISION_REQUIRED` | 权威文档冲突、缺口或两种方案会改变合同语义 | 不指定修法，只提交负责人裁决 |
| `ADVISORY` | 不影响本轮MVP验收的改进建议 | 默认不放入组员整改；必要时单列“非本轮任务” |
| `OUT_OF_SCOPE` | 后续日期、其他岗位或未经授权的事项 | 不写入整改 |

每个`CONFIRMED_BLOCKER`和`CONFIRMED_REQUIRED`必须同时具备：

1. 权威依据：文件、条款或冻结决策；
2. 实现证据：文件和位置，或资产/包内路径；
3. 复现证据：输入、命令、退出码或机械检查结果；
4. 预期与实际：必须能够明确比较；
5. 影响范围：至少说明直接出口和相邻出口；
6. 修复后置条件：描述可观察结果，而不是只描述动作。

缺少其中任一项时，应继续审计或降为待确认，不得用肯定语气要求组员修改。

## 4. 整改前先冻结三张清单

### 4.1 已确认通过清单

先列出已经独立确认通过的内容，并明确“保持不变，不得重做或改写”。至少包括：

- 已通过的业务行为和门禁；
- 已闭合的输入哈希、包哈希和运行次数；
- 不受本轮问题影响的证据文件；
- 不得修改的冻结输入、公共合同、SDK、依赖和其他岗位资产。

这样可以防止组员为了修一个局部问题，重新生成V3证据、覆盖封存件或扩大文件范围。

### 4.2 必须整改清单

只列`CONFIRMED_BLOCKER`和`CONFIRMED_REQUIRED`，每项分配稳定编号，例如`A-R5-01`。后续修复说明、测试、交付清单和复验结果都使用同一编号，避免问题在转述中改名或遗漏。

### 4.3 待裁决与禁止扩项清单

把以下内容从整改任务中隔离：

- 合同没有答案的问题；
- 存在两份权威文件冲突的问题；
- 生产化、性能优化或未来扩展；
- 与本轮缺陷无关的历史债务；
- 其他岗位拥有的文件和业务语义。

## 5. 每个问题必须写成“整改问题卡”

不得只写“修复路径边界”“补全校验”或“完善测试”。每个问题必须使用下面的结构。

### 5.1 问题卡模板

```text
【问题编号】A-R5-01
【级别】CONFIRMED_BLOCKER
【合同依据】文件、章节、条款原文或准确摘要
【证据位置】实现文件:行号 / 包内路径 / 证据字段
【最小复现】给定什么输入，执行什么入口，得到什么实际结果
【预期结果】依据合同必须得到什么结果
【根因】造成问题的实际控制流、数据流、类型或资产关系
【影响面】受影响的所有入口、公共出口、失败路径、恢复路径和证据
【必须修改】逐项写可观察的修复后置条件
【必须保持】不得变化的合同、文件、字段、哈希、行为和已通过项
【强制测试】测试输入、调用入口、关键断言、重复次数和预期退出状态
【交付更新】需要同步更新的实现、测试、报告、清单、Manifest和哈希
```

### 5.2 “必须修改”应写后置条件

错误写法：

```text
修复publicSnapshot，增加内部端口，补测试。
```

正确写法：

```text
1. 合法公共安全候选提交后，路径不得丢失，也不得静默降级为无路径提交。
2. getSnapshot、commit和recover的公共返回对象逐字段只包含公共安全DTO允许字段。
3. 内部完整快照只能通过显式内部端口读写，不得借公共DTO返回。
4. 应用层依赖内部端口抽象，不直接导入具体文件仓储类型，不运行时强转探测隐藏能力。
5. 21号公共类型保持不变。
```

后置条件必须让独立审核者不阅读组员解释也能机械判断PASS或FAIL。

## 6. 必须执行“相邻影响面闭环”

过去反复整改的主要原因，是指令只描述发现缺陷的那一行，没有检查同一数据或状态经过的其他入口和出口。每个问题卡完成后，必须沿真实调用关系检查以下八面。

| 检查面 | 必问问题 |
|---|---|
| 输入 | 合法输入、非法输入、缺字段、额外字段、边界值分别怎样处理？ |
| 内部转换 | 公共类型转内部类型、领域状态转仓储状态时是否丢字段、造字段或静默降级？ |
| 持久化 | 候选、正式快照、历史归档、指针和哈希是否保持一致？ |
| 公共输出 | 所有返回同类DTO的入口是否都裁剪一致，而不是只修一个方法？ |
| 失败与恢复 | 计算失败、校验失败、写入失败、CAS冲突和恢复后是否保持旧正式事实？ |
| 操作顺序 | 后续合并、覆盖、归档或恢复动作是否会破坏此前已经通过的校验？ |
| 类型与依赖 | 类型声明是否真实表达运行时需要的能力，是否依赖了具体实现或强制转换？ |
| 文档与证据 | 交接单、PASS声明、测试数、Manifest和SHA-256是否与整改后事实一致？ |

### 6.1 多出口规则

一个内部对象只要可能通过多个公共方法返回，整改指令必须逐个点名。例如同一会话快照可能由`getSnapshot`、`commit`和`recover`返回，不能只写“修复getSnapshot”。

### 6.2 双向边界规则

只要存在公共类型与内部类型转换，必须同时验证：

1. 公共输入进入内部时不被静默丢弃、不越权补值；
2. 内部对象返回公共边界时不泄漏额外字段；
3. 类型声明和运行时行为一致；
4. 无法转换时返回合同允许的明确错误，不能假装成功。

### 6.3 顺序后置条件规则

只要流程包含“先校验，后合并/恢复/覆盖/归档”，必须在最后一次状态变化后重新检查最终不变量。典型不变量包括：

- 总预算没有被后续固定节点合并重新突破；
- 已完成、进行中和锁定节点没有被后续排序移动；
- active切换后旧版本已经归档；
- 失败恢复后没有半写入或重复提交；
- 最终公共DTO仍满足安全裁剪。

## 7. 测试要求必须写成具体断言

每个阻断问题至少需要以下测试中的适用项，不能只说“补单测”。

### 7.1 最小正例

证明合同允许的最小合法输入能够成功，并且正式结果没有丢失。

### 7.2 最小反例

使用最小输入稳定触发原缺陷；整改前应失败，整改后应通过。必须写清关键断言，不允许只断言“没有抛异常”。

### 7.3 边界值

覆盖空集合、最小非空集合、预算临界值、版本临界值、重复请求、缺字段和额外内部字段等与问题有关的边界。

### 7.4 相邻出口一致性

对同一DTO或状态的所有公共出口使用同一字段白名单或共享断言，防止一个入口修好、另一个入口继续泄漏或丢失。

### 7.5 失败保持性

明确断言失败前后的正式状态、版本、指针、历史和哈希没有被错误改变。

### 7.6 回归测试

运行岗位定向测试和受影响模块测试；风险涉及公共仓储、Facade、公共DTO、事务或共享资产时，还必须运行全量测试。报告真实首次结果和最终结果，不得删除失败记录或把超时改写为PASS。

### 7.7 测试指令写法

整改提示词应写：

```text
新增测试必须至少包含：
- 输入：……
- 调用：……
- 断言：……
- 整改前可复现结果：……
- 整改后预期结果：……
```

不应替组员虚构尚未运行的测试项数、退出码或SHA-256。组员必须运行后据实填写。

## 8. 修复范围必须准确而克制

### 8.1 指定允许修改的所有权范围

整改指令应列出允许修改的模块或目录，但除非合同冻结具体实现，不应武断指定唯一代码写法。优先描述接口责任和最终不变量，让组员在既有架构内选择最小实现。

### 8.2 明确不得修改的内容

至少检查并按任务实际情况写明：

- 负责人冻结清单和公共合同；
- SDK源码、版本和依赖哈希；
- `package.json`、锁文件、`allowScripts`和依赖版本；
- 其他岗位资产、hidden tests、private CSV、reference solutions和Rubric；
- gold、盲标原件、封存文件和冻结输入；
- 已确认通过且不受影响的V3证据；
- Profile active状态和上传锁；
- 本地既有脏状态及未跟踪审计材料。

### 8.3 不扩大为生产级修复

只实现合同要求的MVP正确性、可复算性和演示闭环。除非现行任务明确要求，不得追加：

- 分布式事务、高可用、监控平台或多租户；
- 新数据库、消息队列或云部署；
- 通用插件市场、复杂权限系统或长期兼容层；
- 与当前反例无关的大规模重构。

## 9. 交付物和报告必须同步闭合

整改完成不等于代码通过。整改提示词必须要求组员同步更新：

1. 受影响的实现和作者测试；
2. 审计要求的独立可复现证据；
3. 交接单中的结论、已知限制、命令、退出码和测试项数；
4. 文件清单、Manifest、sidecar和包内外SHA-256；
5. 拟提交路径清单与明确排除项；
6. 原交付中的错误PASS声明或与新事实冲突的文字；
7. 若重新生成证据，登记生成输入、规则版本和新旧哈希关系。

不得要求组员删除历史失败事实来“保持报告整洁”。不得让新ZIP递归包含旧ZIP、缓存、整库副本或不在拟提交范围的审计材料。

## 10. 整改提示词的固定结构

每次发送给组员的正式整改提示词必须按以下顺序组织。

### 10.1 头部事实

- 岗位、周次、工作日和交付包版本；
- 当前合同版本、基线提交和审计对象SHA-256；
- 当前结论是候选整改，不代表上传授权；
- 只允许在现有交付物基础上最小整改。

### 10.2 保持不变

先告诉组员哪些内容已经通过，不得重新生成、改写或扩大。

### 10.3 问题卡

按严重性排序，逐项使用稳定编号。一个问题卡只描述一个可独立验收的问题；同源问题可以说明共同根因，但不能用一个大标题掩盖多个出口。

### 10.4 横向闭合要求

列出这批问题共同影响的输入、所有公共出口、事务、恢复、类型、证据和文档，防止逐卡修复后仍留下交叉缺口。

### 10.5 强制测试矩阵

逐项列出测试输入、入口、断言和应保持不变的正式状态。再列岗位定向测试、类型检查、全量测试、文档检查和`git diff --check`。

### 10.6 交付清单

明确重新交付哪些实现、测试、证据、报告、Manifest、哈希和ZIP；同时写明不得包含哪些文件。

### 10.7 Git和授权边界

除非负责人明确授权，只允许形成候选和报告实际HEAD、状态、拟提交清单；不得commit、push、强推、覆盖他人文件或清理本地遗留材料。

## 11. 可直接复用的整改提示词模板

```text
你现在作为【岗位】处理【周次-D日-交付版本】的一次性整改候选。

请先重新阅读：
- 【负责人决策冻结清单及条款】
- 【公共合同及条款】
- 【周总任务书】
- 【岗位任务书】

当前基线：
- 合同版本：【版本】
- 起点提交：【SHA】
- 审计对象：【路径】
- 审计对象SHA-256：【SHA】
- 当前结论：BLOCKED整改候选，不构成commit、push或上传锁授权。

一、已经通过并必须保持不变

1. 【通过项及证据】
2. 【冻结输入、哈希或证据】
3. 不得修改【其他岗位资产、公共合同、SDK、依赖等】。

二、必须一次性整改的问题

【问题编号】
【合同依据】……
【证据位置】……
【最小复现】……
【实际结果】……
【预期结果】……
【根因】……
【影响面】……
【必须修改】
1. ……
2. ……
【必须保持】……
【强制测试】
1. 输入……，调用……，断言……
2. 失败后必须保持……

三、横向闭合

请逐一核对并在交接单登记：
- 合法/非法输入；
- 公共→内部和内部→公共双向转换；
- 所有返回同类DTO的公共出口；
- 持久化、归档、指针和恢复；
- 最后一次合并或状态变化后的最终合法性；
- 类型声明与运行时能力；
- 报告、Manifest、文件清单和哈希。

四、必须运行并如实报告

1. 【问题定向测试】
2. 【受影响模块测试】
3. 【岗位门禁】
4. 公共仓储、Facade、事务或DTO受影响时运行全量测试
5. typecheck / 文档检查 / git diff --check（按本岗位合同适用项）

不得预填未实际运行的PASS、测试项数、退出码或SHA-256。首次失败和复跑结果都要如实记录。

五、重新交付

- 修改后的实现和测试；
- 问题编号到测试用例的映射表；
- 更新后的交接单和验证证据；
- 完整文件清单、包内Manifest及新SHA-256；
- 实际HEAD、git status和拟提交文件清单；
- ZIP不得包含旧ZIP、缓存、整库副本、其他岗位文件或安全材料。

六、禁止事项

- 不修改未授权合同、公共类型、SDK或依赖；
- 不修改其他岗位资产或冻结输入；
- 不以降低断言、删除测试或改写数据制造PASS；
- 不删除、回退、暂存或上传负责人已登记的本地遗留材料；
- 未获明确授权不得commit、push或申请上传锁；
- 遇到合同没有答案或相互冲突时停止该项实现，列出条款和影响交负责人裁决。
```

## 12. 发送前强制自检

协作助手生成整改提示词后，必须逐项回答下面的问题。任一关键项为“否”时，不得把指令发送给组员。

### 12.1 事实准确性

- [ ] 每个阻断都有现行合同依据，不依赖历史报告或个人偏好；
- [ ] 每个阻断都有实际复现或机械证据；
- [ ] 预期和实际结果已经明确分开；
- [ ] 没有把环境噪音、尚未开始任务或其他岗位事项算作当前缺陷；
- [ ] 没有把需要负责人裁决的问题擅自写成确定修法。

### 12.2 修复完整性

- [ ] 每个问题都写了根因，不只写表面现象；
- [ ] 已枚举同类数据的所有输入和公共出口；
- [ ] 已检查公共/内部双向转换；
- [ ] 已检查失败、恢复、幂等、版本和归档路径；
- [ ] 已检查最后一次状态变化后是否需要重新校验；
- [ ] 类型声明与运行时依赖都纳入整改；
- [ ] 报告、Manifest、哈希和ZIP更新要求已经写明。

### 12.3 测试可执行性

- [ ] 每个问题至少有一个整改前可失败、整改后应通过的最小反例；
- [ ] 测试写明输入、调用入口和关键断言；
- [ ] 涉及多个公共出口时有共享白名单或一致性断言；
- [ ] 涉及事务或重规划时有失败保持性断言；
- [ ] 已列出受影响测试和必要全量门禁；
- [ ] 没有虚构测试数量、退出码或新哈希。

### 12.4 范围与权限

- [ ] 已确认哪些通过项必须保持，不要求无关重做；
- [ ] 允许修改范围与岗位所有权一致；
- [ ] 已列明冻结输入、其他岗位文件、SDK、依赖和安全材料；
- [ ] 没有扩展为生产级系统或无关重构；
- [ ] 没有擅自授权commit、push、上传锁、Profile激活或最终GO。

### 12.5 表达质量

- [ ] 没有使用“完善一下”“自行处理”“补充必要测试”等无法验收的表达；
- [ ] 每项要求都能被独立审核者判断PASS或FAIL；
- [ ] 稳定问题编号贯穿修复、测试和交付；
- [ ] 指令没有相互矛盾，也没有同时要求保持和修改同一文件或事实；
- [ ] 组员无需查看聊天截图即可完整理解并执行。

## 13. 组员重新交付后的复验规则

一次性整改指令的质量不能只看组员是否回复“完成”。复验时必须：

1. 按问题编号逐项重跑强制反例；
2. 对照“必须保持”清单确认没有扩大修改；
3. 检查相邻出口，而不是只检查原失败调用；
4. 独立复算哈希、Manifest和测试统计；
5. 将新发现区分为：原指令遗漏、组员未按指令完成、修复引入回归、此前不可见的新缺陷；
6. 如果原指令已经明确覆盖而组员未完成，下一次反馈应指出未满足的原问题编号，不重新发明一套要求；
7. 如果确属原指令遗漏，协作助手必须说明遗漏原因并更新本规范适用的检查项，不能把全部责任转给组员。

## 14. 本次A整改事件的通用教训

以下教训只用于说明规范来源，不新增A岗位合同：

1. “增加内部读取端口”只是实现方向，不是完整验收条件；还必须验证公共输入不丢失、公共输出不泄漏、类型能力显式表达。
2. “预算校验通过”和“固定节点保持不变”分别实现，不代表合并后的最终路径仍合法；最后一次合并后必须重验不变量。
3. 作者测试可能把错误行为写成断言。整改提示词必须给出合同预期字段，而不是只要求增加测试数量。
4. 一个问题同时影响`get`、`commit`和`recover`时，只点名其中一个方法必然容易留下第二轮缺陷。
5. 已通过的V3证据和PathEngine主体应明确冻结，避免局部整改引起无关重做和哈希漂移。

## 15. 最终原则

审计后的整改提示词必须完成下面这条闭环：

```text
权威条款
→ 可复现事实
→ 根因与完整影响面
→ 可观察修复后置条件
→ 正例、反例、边界、失败保持和回归测试
→ 文件、证据、Manifest、哈希与权限边界
→ 独立复验
```

凡是不能进入这条闭环的内容，要么继续调查，要么交负责人裁决，要么移出本轮整改；不能用模糊措辞交给组员自行猜测。
