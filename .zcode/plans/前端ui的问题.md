# 前端 UI 问题

## 总体修改原则

- 本文记录的问题、期望表现和示例方案均用于说明当前体验痛点与设计方向，不是必须逐字、逐项照搬的固定实现清单。
- 具体修改权交由实际修改者。修改者可以结合现有组件结构、页面空间、响应式布局、数据来源和整体设计语言，选择更合理的实现方式，也可以合并、替换或简化本文提出的参考方案。
- 不要求为了“完成条目”机械地增加按钮、卡片、边框、动画或说明文字；每个元素都应有明确的信息价值或交互价值。
- 总体目标是让页面美观、自然、清晰、有适度活力，减少死板、僵硬、拥挤、重复和装饰含义不明的问题。
- 动态效果应克制并服务于状态反馈、操作引导和信息层级，不能为了动画而动画，也不能引发布局跳动、文字遮挡、视觉干扰或性能问题。
- 所有页面应保持统一的字体、颜色、间距、圆角、阴影、按钮和状态表达，但允许不同功能区域根据内容特点形成适当差异。
- 视觉调整不能破坏原有业务流程、真实数据、Session绑定、多 Agent 状态、审计证据、断点恢复和异常处理，也不能用静态演示数据代替真实结果。
- 修改者应同时考虑桌面端、移动端、键盘操作、文字可读性和减少动态效果等情况，最终以真实页面中的整体观感和实际使用体验为判断标准。
- 当本文中的具体建议与实际页面效果冲突时，以“功能正确、信息真实、操作清楚、视觉协调、使用舒适”的最终效果为准，不必拘泥于原建议的表现形式。

## 1. AI 个性化课前导学中的部分内容存在多余边框

涉及位置：章节学习页的“AI 个性化课前导学”区域。

当前表现：

- “本节主线”和“学习建议”分别被放在带有完整边框的独立矩形区域中。
- 同一区域内的“承接前文”和“下一步去哪里”采用无边框的正文样式，导致四部分内容的视觉样式不统一。
- 两个独立边框会把连续的课前导学内容切割成多个块，使页面显得零碎，并让“本节主线”和“学习建议”看起来像可交互卡片或额外组件。


期望表现：

- 删除“本节主线”和“学习建议”外围的独立矩形边框。
- 四部分内容保持一致、连续的正文排版层级，同时保留各自的小标题和必要的段落间距。
- 调整后不应影响文字内容、生成状态或“AI 个性化课前导学”整体容器。

## 2. 多 Agent 工作流展开后的结果摘要区布局不协调

涉及位置：多 Agent 工作流节点展开后的上方执行结果摘要区。

当前表现：

- “提醒来源”和 `ai_live` 被放在单独的矩形边框中，但这组信息只是普通的来源属性，并不是需要强调或交互的独立卡片，边框显得突兀且含义不明确。
- `ai_live` 等内部技术标识直接面向用户展示，缺少易懂的显示名称，用户难以判断它代表“实时 AI 生成来源”还是某种运行状态。
- 执行结果摘要采用左右分栏，但右侧只有一个较小的信息框，剩余区域大面积留白，左右视觉重量明显失衡。
- “已完成”状态、结果说明、开始时间、处理耗时、执行轮次、事件序号和提醒来源分散在多个视觉块中，边框、分割线和留白同时存在，信息关系不够清晰。
- 上方结果摘要区的视觉组织不够集中，用户需要在多个框、分割线和字段之间寻找当前结论。

范围说明：

- 页面上方已经存在的多 Agent 逻辑链路，其流程、节点信息和交互逻辑可以保持不变。
- “查看完整安全时间线”的数据内容、展开逻辑和信息结构可以保持不变，不属于本问题要求必须重做的部分。
- 如需统一页面观感，可以对逻辑链路和完整时间线进行间距、对齐、字号、分隔线等纯视觉优化，但不应改变现有功能或删减审计信息。

期望表现：

- 删除没有独立交互或强调意义的装饰性边框，尤其是 `ai_live` 所在的单独矩形框。
- 将来源、轮次、耗时、事件序号等同类元数据组织为统一、紧凑的摘要信息，不再形成孤立卡片或大面积空白。
- 面向用户的界面使用易懂的来源名称；如确需保留 `ai_live` 等技术标识，应降低其视觉权重，避免将其表现为核心信息。
- 重新梳理展开区的信息层级，使用户优先看到执行结论和当前状态，其次查看关键元数据，最后按需展开审计详情与完整时间线。
- 逻辑链路和完整时间线若参与调整，应仅做一致性和美观性优化，并保持原有流程、交互与数据完整性。
- 布局调整不应删除真实的审计数据，也不应影响工作流状态、实时更新或详情展开功能。

## 3. 学习总结页的“复习本节”入口不够明显

涉及位置：最终学习总结页“仍需处理”区域中，每个待复习知识点右侧的“复习本节”入口。

当前表现：

- “复习本节”目前以普通文字形式显示，字号、颜色和周围正文接近，缺少明确的按钮外观。
- 入口的可点击性不明显，用户容易把它当作状态标签或补充说明，而不知道可以点击后返回对应章节重新学习。
- “仍需处理”是总结页中需要用户继续采取行动的重要区域，但当前操作入口的视觉优先级偏低，不能有效引导用户进行下一步补救学习。
- 多条待复习记录连续排列时，右侧文字入口不够醒目，也不利于用户快速定位每条记录对应的操作。

期望表现：

- 将“复习本节”设计为具有明确边界、点击反馈和稳定尺寸的操作按钮，使其与普通状态文字清楚区分。
- 按钮可以使用“返回复习”语义的图标配合“复习本节”文字，直观表达“返回该章节重新学习”的功能。
- 按钮应在每条待复习记录中保持统一的位置、尺寸和对齐方式，确保多条记录下仍能快速扫描和操作。
- 按钮需要具有足够的视觉对比度，但不应压过总结页的主要结论，也不应被设计成表示危险操作的样式。
- 用户点击后仍应准确返回该知识点所属章节的可学习位置，不改变原有回退学习逻辑。

## 4. 教学正文和代码的字体与阅读体验不佳

涉及位置：各章节正式教学正文，包括中文段落、标题、行内代码和独立代码片段。

当前表现：

- 中文正文字体在页面中显得偏窄、偏长，部分文字有被纵向拉伸的观感，连续阅读时不够自然舒适。
- 正文字号整体偏小，长段落排列紧密，用户进入教学页后容易感到内容多、阅读压力大。
- 中文正文与其中的英文术语、函数名和变量名在字形、基线及视觉重量上不够协调，影响句子的连续阅读。
- 代码部分字号明显过小，是当前页面中最难阅读的内容；变量名、注释和符号需要用户靠近或仔细辨认。
- 代码片段与普通正文之间缺少足够明确的背景和容器区分，用户不能快速识别哪里是讲解、哪里是需要重点查看的代码。
- 代码字体的字形辨识度不足，数字、字母、下划线、括号和引号在较小字号下更难区分，不符合常见编程学习环境的阅读习惯。
- 当前整体排版容易让用户第一眼产生内容拥挤、学习负担较重的感受，不利于持续阅读和理解。

整体体验目标：

- 中文正文和代码都需要同步优化，使教学页面第一眼显得清晰、轻松、有层次，避免给用户造成压迫感或厌学感。
- 增大中文正文的基础字号并调整行高、段落间距和每行有效宽度，使长段落更容易逐行阅读。
- 中文字体应保持自然比例和稳定字重，避免字形偏窄、拉长或过度纤细；标题与正文需要形成清楚但不过度夸张的层级。
- 明显增大代码字号和行高，使代码成为可以直接阅读的教学内容，而不是页面底部难以辨认的附属小字。
- 代码字体优先采用编程环境常见的等宽字体，例如 `JetBrains Mono`；也可以根据实际显示效果选用 `Fira Code`、`Source Code Pro` 或 `Consolas`，并提供可靠的等宽字体回退顺序。
- 为独立代码片段增加比正文区域更深、但对比度舒适的背景，通过适当的内边距和边界区分突出代码内容。
- 代码背景、文字颜色和字号需要兼顾可读性，不能因背景加深而出现低对比度、刺眼或与全站视觉风格割裂的问题。
- 行内代码和独立代码块应采用不同强度的强调方式：行内代码保持轻量识别，独立代码块承担完整代码阅读。
- 字体与排版调整应覆盖桌面端和移动端，并确保代码不会被裁切、溢出或挤压正文布局。

## 5. 题组生成等待区状态重复，且缺少实时多 Agent 审核过程的查看引导

涉及位置：章节正式正文页面底部的题组生成与审核等待区。

当前表现：

- 页面底部同时出现两处“正在生成并审核题组（已处理 16 秒）”：一处是按钮前方的普通状态文字，另一处是按钮内部文字。
- 两处内容表达完全相同，并且读秒同步变化，造成信息重复和视觉拥挤，也让用户不清楚按钮前的文字与按钮是否代表两个不同任务。
- 当前正文页面只能看到笼统的“正在生成并审核题组”状态，无法直接看到 Generator、Hunter、Defender、Judge 等多 Agent 的实时工作进度。
- 实时多 Agent 任务链位于简报界面，但当前等待区没有说明这一点；用户可能不知道可以点击“返回简报”查看，也可能误以为系统只有读秒而没有实际执行审核链。
- 当生成和审核耗时较长时，缺少过程入口或查看提示会降低系统工作的可感知性，增加用户对页面卡住的担忧。

期望表现：

- 删除按钮前方重复的“正在生成并审核题组（已处理 N 秒）”普通状态文字，只保留按钮中的动态状态和读秒。
- 保留按钮原有的实时读秒和不可重复触发状态，避免删除重复文字后失去等待反馈。
- 用户在正文页面等待题组时，应能明确知道多 Agent 审核链正在运行，并知道在哪里查看实时过程。
- 可接受的呈现方式之一：将实时多 Agent 审核链工作台同步展示在当前正文页面的等待区域，使用户无需离开正文即可查看进度。
- 可接受的呈现方式之二：继续将工作台保留在简报界面，并在生成按钮旁增加清晰提示，例如“可返回简报界面查看实时多 Agent 任务链”。
- 如果采用返回简报查看的方式，提示文字应与页面现有的“返回简报”入口形成明确关联，但不能被误解为必须中断或重新开始题组生成。
- 无论采用哪种方式，都应复用同一份实时任务状态，不能创建第二套独立审核流程，也不能因页面切换导致生成任务重启、丢失或重复执行。

## 6. 首页“继续学习”卡片组缺少动态反馈和真实学习信息

涉及位置：首页右上方由“上次读到/继续学习”卡片、上方横线卡片和学习阶段卡片组成的视觉区域。

当前表现：

- “继续学习”卡片虽然是首页的重要恢复入口，但静止状态与鼠标触及时几乎没有明显变化，交互反馈偏弱，用户不容易第一眼意识到整张卡片可以点击。
- 上方横线卡片目前主要表现为几条静态占位线，没有显示具体内容，看起来像尚未加载完成的空白骨架屏，也没有为用户提供实际信息。
- “继续学习”卡片、上方空白卡片和右侧学习阶段卡片彼此靠近，但缺少统一的动态关系，整体更像几张固定贴图，视觉表现较僵硬。
- 上方卡片没有展示最近一次学习时间、当前完成进度等与继续学习直接相关的信息，浪费了首页最显眼区域的信息承载能力。
- 如果存在多个历史Session，当前视觉区域没有清楚表达这些信息究竟对应哪一个会话，容易出现数据与“继续学习”目标不一致的风险。

期望表现：

- “继续学习”卡片在鼠标悬停、聚焦和按下时提供明显但克制的动态反馈，例如轻微上浮、倾斜、回弹或小幅摆动，让用户自然感知它可以点击。
- 上方横线卡片不再只是静态空白装饰，应动态展示与“继续学习”目标相关的真实信息，例如最后一次学习时间、课程完成进度、已完成章节数、当前章节或当前学习阶段。
- 上方信息卡片与“继续学习”卡片必须绑定同一个最近有效Session；首页断点发生变化后，卡片内容也应同步更新，不能显示其他会话或过期数据。
- 进度信息应来自真实学习状态，不应使用固定百分比、演示数字或仅靠前端猜测生成的数据。
- 这一组卡片可以具有轻量、相互协调的动态效果，使页面更有活力，但不能持续大幅晃动、遮挡文字、改变点击区域或让布局发生跳动。
- 动画应服务于信息层级和可点击性：主要操作“继续学习”的反馈最明显，辅助信息卡片和阶段卡片的动画更轻，避免多个元素同时争夺注意力。
- 鼠标移出、失去焦点或动画结束后，卡片应平滑回到稳定位置；键盘操作也需要有清晰的焦点反馈。
- 对系统启用“减少动态效果”的用户，应自动减弱或关闭位移、倾斜和晃动动画，同时保留必要的颜色、边框或阴影反馈。
- 桌面端可以使用悬停互动，触屏和移动端不能依赖鼠标悬停才能看到关键信息，也不能因动画导致卡片内容溢出或重叠。

## 7. 短暂处理过程会切换到独立加载页，造成闪屏和无意义跳转

涉及位置：诊断题提交后进入下一题的过程，以及产品中其他仅因短暂后台处理而临时切换到“正在加载证据”等独立界面的流程。

当前表现：

- 用户每完成一道诊断题后，页面会先切换到“正在加载证据”等独立加载界面，约极短时间后又跳转到下一道题。
- 这类加载界面出现时间可能只有约 `0.1` 秒，用户来不及读懂内容，只能感受到页面突然闪烁和跳转。
- 用户刚刚作答的题目、所选选项和操作位置会瞬间消失，随后新题再次出现，视觉上下文不连续。
- 类似的临时整页加载界面不只出现在诊断题完成后；凡是短暂处理就替换整个页面的流程，都可能产生相同的闪屏问题。
- 独立加载页没有提供足够的信息价值，反而容易让用户误以为发生了异常跳转、页面刷新或流程错误。
- 如果直接删除所有等待反馈，处理时间稍长时用户又可能误以为点击没有生效或页面卡住。

期望表现：

- 删除诊断题之间以及其他相同场景中的短暂独立加载页，不再为了极短的后台处理切换整个页面。
- 用户提交后保持当前页面、题目和选项位置稳定，后台处理完成后再自然切换到下一题或下一环节。
- 等待反馈应出现在用户刚刚操作的选项或提交按钮上，例如将其变为不可重复点击的“正在处理”状态，并配合加载动效。
- 对非常短的处理过程，只需将选项或按钮临时变为“正在处理”样式，不必强制显示来不及辨认的独立加载界面。
- 对能够被用户明显感知的等待过程，在同一位置显示动态读秒，例如“正在处理（已处理 2 秒）”，让用户确认系统仍在工作。
- 处理状态开始后应立即响应，按钮或选项的尺寸保持稳定，不能因状态文字变化导致页面布局跳动。
- 处理期间应阻止重复提交；成功后平滑进入下一题，失败时在原页面提供明确错误信息和重试入口。
- 该规则应统一应用于诊断、学习、活动提交和其他短暂异步跳转场景，避免不同页面分别出现风格不一致的临时加载页。
- 调整仅改变等待过程的呈现方式，不能跳过证据保存、学情画像更新、Agent处理或其他必要的后台步骤。
